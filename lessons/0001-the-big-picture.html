Lesson 1 · Introduction

What an OS actually does

One CPU, one RAM, one disk, and many programs that each want all three. The OS's job is to make every program believe it has the machine to itself.

The one-sentence version The operating system sits between programs and hardware. It takes a physical resource and turns it into an easier, more general virtual version, and it acts as a resource manager that decides who uses what, when, and for how long.OSTEP §2

OSTEP organises the whole course around three easy pieces. Your midterm covers the first one, virtualization, in depth. The other two only need a sentence each for now.

Piece 1 · Virtualization

The problem: there is one CPU and one memory, but many programs each want them all to themselves. How do we share them so every program feels it owns the machine?

The book's analogy: the peach There is one real peach and many people who want to eat it. You give each person a virtual peach. Most of the time each eater is napping or busy. So you quietly take the peach away and hand it to someone else for a while. Each eater thinks they have their own peach. In reality, they share one.OSTEP Ch 3 The CPU and memory are the peach. The programs are the eaters.

Virtualizing the CPU

Your laptop may have 8 cores but 300 running programs. So programs must share. The OS runs one program for a few milliseconds. Then it switches to the next one, and so on. It switches so fast you never notice. Each program seems to have its own CPU. This trick is called time sharing: programs take turns on the same CPU.

Four programs, one CPU. Each one thinks it is running all the time, but really they take turns. Hover a block to see when it ran.

To make time sharing work, the OS needs two different things. One is the tool for switching. The other is the rule for choosing who goes next. A mechanism is the low-level "how". A policy is the decision "which". This split comes back in every chapter:

Answers the question…Example
MechanismHow do we do it?The context switch: save one process's registers, load another's
PolicyWhich one do we pick?The scheduler decides who runs next (FIFO, round robin, MLFQ…)

Lesson 4 covers the mechanism, and Lessons 5–9 cover the policies.

Virtualizing memory

Physical memory is just one big array of bytes. Every program has to share it. But no program should see or break another's data.

So the OS gives each process its own address space: a private, pretend memory that starts at 0 and belongs only to that process. The addresses a program uses are virtual. On every memory access, the OS and hardware translate the virtual address into a real physical one.

The book's demo is mem.c. It allocates one integer and adds 1 to it every second.OSTEP Fig 2.3 Run two copies at once:

$ ./mem & ./mem &
(2134) addr 0x200000: 1
(2135) addr 0x200000: 1
(2134) addr 0x200000: 2
(2135) addr 0x200000: 2
Analogy Two people both live at "Flat 2". One is in Building A and one is in Building B. The flat number is the virtual address. The building is the hidden part the OS fills in. Lessons 10–13 show exactly how that translation works.

In short: the OS virtualizes the CPU by time sharing (taking turns fast) and virtualizes memory by giving each process its own address space (same virtual address, different physical memory).

What is time sharing, and which resource does it virtualize?

It virtualizes the CPU. The OS runs one program for a few milliseconds, then switches to the next, and so on. Done fast enough, every program seems to have its own CPU.

Mechanism vs policy: which one is the context switch, and which one is the scheduler? Say what question each answers.

The context switch is a mechanism: it answers how (save one process's registers, load another's). The scheduler is a policy: it answers which process runs next.

What is a process's address space, and why can two processes use the same virtual address without clashing?

An address space is a private, pretend memory that starts at 0 and belongs only to that process. The OS and hardware translate each virtual address to a different physical address for each process, so the same virtual address lands in different real memory.

Which correctly describes time sharing?

  • The OS runs one program for a short while, then switches to another, so each seems to have its own CPU. Taking turns on the CPU, fast enough that nobody notices, is how one CPU is virtualized into many.
  • The OS gives each program its own CPU core for its whole run, so each seems to have its own CPU. That is splitting in space, and there are far more programs than cores. Time sharing means programs take turns on the same CPU.
  • The OS runs one program until it finishes, then starts another, so each seems to have its own CPU. Running to completion is not sharing. The OS switches after a short while, long before the program finishes.
  • The OS runs one program for a short while, then switches to another, so each seems to have its own memory. Time sharing virtualizes the CPU. A private memory comes from each process's address space.

Which is TRUE about mechanism vs policy?

  • The context switch is a mechanism, answering how; the scheduler is a policy, answering which. Saving one process's registers and loading another's is the how; choosing who runs next is the which.
  • The context switch is a policy, answering which; the scheduler is a mechanism, answering how. Swapped: the context switch is the mechanism and the scheduler is the policy.
  • The context switch is a mechanism, answering which; the scheduler is a policy, answering how. The labels are right but the questions are swapped: a mechanism answers how, a policy answers which.
  • The context switch is a mechanism, answering how; the scheduler is a mechanism, answering when. The scheduler is a policy: it decides which process runs next.

Which correctly describes a process's address space?

  • A private, pretend memory that starts at address 0 and belongs only to that one process. Each process sees its own virtual memory from 0 upward; the OS and hardware translate it to real RAM.
  • A private, pretend memory that starts at address 0 and is shared by every copy of the program. Each process gets its own, even two copies of the same program (that is the mem.c demo).
  • A real, physical region of RAM that starts at address 0 and belongs only to that one process. It is virtual: it starts at 0 only in the process's view, and each address is translated to a different physical one.
  • A private, pretend memory that starts at address 0 and is never translated by the hardware. Every virtual address is translated into a physical address by the OS and hardware.

Piece 2 · Concurrency

The problem: when several things run at once and share the same data, how do we keep the result correct?

A thread is one stream of execution inside a program. Think of it as a function that runs at the same time as other functions, in the same memory.OSTEP §2.3 One process can have several threads. Here is what they share and what they don't:

Two processesTwo threads in one process
Address space (code, heap, globals)SeparateShared
Open filesSeparateShared
Stack, registers, PCSeparateSeparate (each thread has its own)

Sharing memory is fast. It is also dangerous. Here is the program from the slides. Two threads share one global counter. Each thread runs counter++ ten million times.OSTEP Fig 2.5Zafar Lecture 1, slides 13–14 You'd expect 20,000,000. Instead you get a different wrong number almost every run.

Why? counter++ looks like one step. But the CPU does it in three:

  1. LOAD: copy counter from memory into this thread's private register
  2. ADD: add 1 to the register
  3. STORE: write the register back to counter

The OS can switch threads at any moment, even between those steps. Then both threads can LOAD the same old value. Both add 1 to it. Both store the same answer. One increment is lost. This is a race condition: the result depends on the timing of the switches. Here is one bad timing, with counter starting at 10:

#StepA's registerB's registercounter (memory)
0start––10
1A: LOAD10–10
2A: ADD11–10
3⚡ switch! B: LOAD111010
4B: ADD111110
5B: STORE111111
6A: STORE111111 (should be 12)
How to fill these tables Three rules. (1) Each thread has its own register. (2) counter in memory only changes on a STORE. (3) On every LOAD, copy whatever value is in memory right now. That's the whole trick.

The fix (locks) is in a later part of the course and isn't on this midterm.

In short: threads share memory, and counter++ is really LOAD, ADD, STORE. A switch between those steps can lose an update. That is a race condition.

List the three machine steps hidden inside counter++, and say what a race condition is.

LOAD (memory → register), ADD 1 to the register, STORE (register → memory). A race condition is when the result depends on the timing: a switch between those steps can make an increment get lost.

counter starts at 7. Threads A and B each run counter++ once, in this order: A LOAD → B LOAD → B ADD → B STORE → A ADD → A STORE. What is the final value of counter?

8 (not 9). A loads 7 and B loads 7. B stores 8. A then adds 1 to its own old 7 and also stores 8, overwriting B's work.

Which is TRUE about two threads in the same process?

  • They share the heap and global variables, but each one has its own stack and PC. Threads share the address space (code, heap, globals) and open files; each has its own stack, registers and PC.
  • They share the stack and PC, but each one has its own heap and global variables. Swapped: the heap and globals are shared, the stack and PC are per thread.
  • They share the heap, global variables and stack, but each one has its own PC. Each thread also has its own stack, because each is at a different point in its own function calls.
  • They share nothing in memory, and each one has its own heap, globals, stack and PC. That describes two processes. Threads share the address space (code, heap, globals).

A global int counter is incremented by two threads of one process, and, in a separate run, by two processes running the same program. Which is TRUE?

  • The two threads update one shared counter; the two processes each update their own copy. Threads share globals, so they can race on one counter; processes have separate address spaces.
  • The two threads each update their own copy; the two processes update one shared counter. Swapped: threads share the counter; processes each have their own.
  • The two threads update one shared counter; the two processes update one shared counter too. Two processes have separate address spaces, just like the two copies of mem.c.
  • The two threads each update their own copy; the two processes each update their own copy. Threads share globals; that sharing is exactly what makes the race possible.

Which sequence is right for the machine steps inside counter++?

  • LOAD counter into this thread's register, ADD 1 to that register, STORE the register back to counter. Three separate steps, and memory only changes on the STORE.
  • LOAD counter into this thread's register, STORE the register back to counter, ADD 1 to that register. Wrong order: the ADD comes before the STORE, otherwise the old value is written back.
  • LOAD counter into a register both threads share, ADD 1 to that register, STORE the register back to counter. Each thread has its own registers. Only counter in memory is shared.
  • LOAD counter into this thread's register, ADD 1 to counter in memory, STORE the register back to counter. The ADD changes the register, not memory. counter only changes on the STORE.

counter starts at 4. Threads A and B each run counter++ once: A LOAD → B LOAD → B ADD → A ADD → A STORE → B STORE. Which is TRUE?

  • counter ends at 5: both threads loaded 4, so both store 5. Both registers start from the same old 4, so one increment is lost.
  • counter ends at 6: each thread adds 1, so the two adds give 6. Both ADDs work on a register that holds the old 4, so both produce 5.
  • counter ends at 4: B's STORE overwrites A's STORE with the old value. B stores its register, which holds 5, not the old 4.
  • counter ends at 6: A stores 5, then B loads 5 and stores 6. B loaded before A stored, so B's register holds 4, not 5.

Which is TRUE about a race condition?

  • The result depends on how the threads' steps happen to interleave, so it can differ from run to run. Where a switch lands between a LOAD and its STORE decides how many increments are lost.
  • The result depends on which thread was created first, so it is the same on every run. It depends on the timing of the interleaving, which changes from run to run.
  • The result depends on how the threads' steps happen to interleave, but only on a machine with several CPUs. It happens on one CPU too: a switch between a thread's LOAD and STORE is enough.
  • The result is always exactly half the expected value, because one thread's work is lost. Only some increments are lost, a different number each run (e.g. 18,921,533 instead of 20,000,000).

Piece 3 · Persistence

The problem: how do we keep data safe when the power goes off or the machine crashes?

RAM is volatile: it forgets everything when the power goes. Disks and SSDs are persistent: they keep data with the power off. The part of the OS that manages persistent data is the file system. It does three jobs:

  • It organises files and directories.
  • It tracks where each file's data lives on the disk.
  • It stays consistent even if the machine crashes mid-write.

In short: RAM is volatile, disks are persistent, and the file system manages persistent data. That's all you need for now.

RAM is volatile, a disk is persistent. What do those words mean, and which part of the OS manages persistent data?

Volatile: loses its contents when the power goes. Persistent: keeps data across power loss. The file system manages persistent data (files, directories, staying consistent after a crash).

Which is TRUE about persistence?

  • RAM is volatile and a disk is persistent; the file system is the part of the OS that manages persistent data. RAM forgets everything on power loss; disks and SSDs keep data, and the file system organises it.
  • RAM is persistent and a disk is volatile; the file system is the part of the OS that manages persistent data. Swapped: RAM is volatile and the disk is persistent.
  • RAM is volatile and a disk is persistent; the virtual memory system is the part of the OS that manages persistent data. Address spaces virtualize RAM. Persistent data is managed by the file system.
  • RAM is volatile and a disk is persistent; the file system manages persistent data and assumes no crash mid-write. The file system must stay consistent even if the machine crashes mid-write.

What a good OS aims for

The problem: how do we judge whether an OS is good? We need a list of goals.

AbstractionMake hardware easy to use: processes, address spaces and files instead of raw registers and disk blocks
PerformanceKeep the OS's own overhead (time and space) low
Protection / isolationOne program can't harm another program or the OS
ReliabilityThe OS must not crash, because if it fails, everything fails
AlsoEnergy efficiency, security, mobility

In short: learn the four main goals: abstraction, performance, protection / isolation, reliability. A program harming another program is a protection failure.

List four design goals of a good operating system.

Abstraction (easy to use), performance (low overhead), protection / isolation (programs can't harm each other or the OS), reliability (the OS must not crash). Also: energy efficiency, security, mobility.

A buggy game overwrites memory belonging to your text editor. Which OS design goal has failed?

Protection / isolation: one program should never be able to harm another program or the OS.

Which correctly matches an OS design goal to its meaning?

  • Protection / isolation: one program can't harm another program or the OS. Isolating processes from one another is the key to protection.
  • Reliability: one program can't harm another program or the OS. Reliability means the OS itself must not crash. Not harming each other is protection / isolation.
  • Protection / isolation: the OS keeps its own time and space overhead low. Low overhead is performance.
  • Abstraction: one program can't harm another program or the OS. Abstraction means making the hardware easy to use (processes, address spaces, files).

Practice

Answer from memory first, then check. Struggling a little is what makes it stick.

1. Two copies of mem.c both print addr 0x200000 yet count independently. Why?

Each process has its own address space. The OS maps the same virtual address to a different physical location for each one, so they never collide. This is memory virtualization.

2. counter starts at 5. Threads A and B each run counter++ once, interleaved like this: A LOAD → B LOAD → A ADD → A STORE → B ADD → B STORE. What is the final value of counter?

A loads 5, B loads 5 (A hasn't stored yet). A stores 6, then B adds 1 to its own 5 and also stores 6. One increment is lost: 6, not 7.

3. Which of these do two threads in the same process NOT share?

Threads share the address space (code, heap, globals) and open files, but each thread has its own stack, registers and PC, because each one is at a different point in its own function calls.

4. "Pick the job with the least remaining time to run next." Is that a mechanism or a policy?

Choosing which process runs is a policy (scheduling). How the switch is carried out (saving and restoring registers) is the mechanism (context switch).
5. Name the three easy pieces and say what each one means in a single line.
Virtualization: turn one physical CPU or memory into many private virtual ones. Concurrency: get several threads that share data to behave correctly. Persistence: keep data safe on disk across crashes and power loss (the file system).
6. Give two reasons an OS bothers virtualizing resources at all.
(1) Sharing: many programs can use one physical CPU or memory (e.g. time-slicing the CPU). (2) Isolation and ease of use: each program gets a simple, private, uniform view (like its own address space), so programs can't interfere with each other and are easier to write.
