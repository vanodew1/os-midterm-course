Lesson 2 · Virtualizing the CPU

The process

A program on disk does nothing. The moment the OS loads it and starts it, it becomes a process: a living thing with memory, registers and open files that the OS can pause and resume at will.

The one-sentence version A process is a running program. It is the OS's abstraction for everything a running program needs: its memory, its registers, and its open files. The OS tracks each one in a Process Control Block and moves it between the states Running, Ready and Blocked.OSTEP §4Bilal slides, Ch 4

What does it mean for the OS to virtualize a resource? Give the CPU example and the memory example.

It turns one physical resource into many easy-to-use virtual copies. CPU: time sharing makes each program feel it has its own CPU. Memory: each process gets its own private address space, translated to different physical memory.

counter starts at 3. Threads A and B each run counter++ once, in this order: A LOAD → A ADD → B LOAD → A STORE → B ADD → B STORE. What is the final value?

4 (not 5). B loads 3 before A stores, so both registers end up holding 4, and both store 4. One increment is lost: a race condition.

Program vs process

The problem: there are only a few physical CPUs. How can the OS give the illusion of a nearly endless supply of them?OSTEP §4

First we need a name for "a program that is running". A program on disk is lifeless. It just sits there, a bunch of instructions waiting to spring into action. When the OS loads it and starts it, it becomes a process: a running program.

ProgramProcess
Where it livesOn disk (a file like ./a.out)In memory, using the CPU
What it isStatic bytes: instructions + static dataA running instance with its own state
How manyOne fileCan be many at once (run ./a.out twice → two processes)
Analogy A program is a recipe printed in a book. A process is someone actually cooking it. There's a half-filled pot (memory). There's a finger on step 7 (program counter). The oven door is open (open files). Two cooks can follow the same recipe at the same time. Each one has their own pot.

How can one CPU run hundreds of processes?

By time sharing. The OS runs one process for a little while. Then it stops it and runs another, and so on. Each process gets the illusion of its own CPU. The cost: each one runs a bit slower, because the CPU is shared.OSTEP §4.1

The other way to share is space sharing. Here a resource is split into pieces, and each process gets its own piece. Example: disk blocks or memory divided between processes.Bilal slides, Ch 4 Quick test: CPU = take turns (time). Disk = split up (space).

Time sharing needs two things, as in Lesson 1:

  • A mechanism, the how: the context switch stops one process and starts another.
  • A policy, the which: the scheduler decides who goes next.

In short: a program is a file on disk; a process is that program running. The OS shares one CPU among many processes by time sharing.

What is the difference between a program and a process?

A program is static bytes on disk (instructions + static data). A process is a running instance of it, in memory with its own state. One program can be running as many processes at once.

Time sharing vs space sharing: define each and give one example.

Time sharing: take turns using a resource over time (the CPU runs one process, then another). Space sharing: split a resource into pieces that each get a part of (memory or disk blocks divided between processes).

Which is TRUE about programs and processes?

  • A process is a running program; one program on disk can be running as several processes at once. Run ./a.out twice and there is one program file but two processes, each with its own state.
  • A process is a running program; one program on disk can be running as only one process at a time. Run it twice and you get two processes from one program.
  • A process is a program stored on disk; it becomes a program once the OS loads and starts it. Swapped: the program is on disk; it becomes a process when it runs.
  • A process is a running program; it holds the program's code and data but not its registers or open files. A process's state also includes its registers and its open files.

What's inside a process: machine state

The problem: the OS will pause a process and resume it later. To do that, it must know exactly what makes up a running process.

So take an inventory. List everything the process can read or change while it runs. OSTEP calls this its machine state. It has three parts:OSTEP §4.1

PartWhat it is
Memory (the address space)The instructions and the data the process reads and writes: code, static data, heap, stack
RegistersThe CPU's registers while this process runs. The special ones are below.
I/O informationThe list of files the process currently has open

Three registers matter most:

  • The program counter (PC) holds the address of the next instruction to run. Its other name is the instruction pointer. Think of it as your finger on the recipe step.
  • The stack pointer (SP) points to the top of the stack. The stack holds function parameters, local variables and return addresses.Bilal slides, Ch 4
  • The frame pointer also helps manage the stack. It marks the current function's frame.OSTEP §4.1
This is how it's asked "Explain the roles of the PC and the SP." Two lines are enough:
PC: holds the address of the next instruction to fetch and execute.
SP: points to the top of the current stack, which tracks function calls: their local variables, parameters and return addresses.

Why care? This machine state is exactly what the OS must save when it stops a process. It is also what the OS must restore when it resumes it. Save it perfectly, and the process never notices it was paused. It is like a bookmark: put it back on the same page and the reader carries on.

In short: machine state = memory + registers (PC, SP, frame pointer) + I/O information (open files). It is what the OS saves and restores.

List the three parts of a process's machine state.

Memory (its address space: code, static data, heap, stack), registers (especially PC, SP, frame pointer), and I/O information (its list of open files).

Why does the OS care so much about a process's machine state?

Because it is exactly what the OS must save when it stops a process and restore when it resumes it. Save it perfectly and the process never notices it was paused.

Which is TRUE about the program counter (PC)?

  • It holds the address of the next instruction to run, and is also called the instruction pointer. The CPU fetches from the address in the PC; x86 calls it eip, the instruction pointer.
  • It holds the address of the instruction that just finished, and is also called the instruction pointer. It holds the next instruction to fetch and execute.
  • It holds the address of the top of the stack, and is also called the instruction pointer. The top of the stack is the stack pointer's job.
  • It holds the address of the next instruction to run, and is also called the frame pointer. Its other name is the instruction pointer. The frame pointer marks the current function's stack frame.

Which is TRUE about the stack pointer (SP) and the stack?

  • SP points to the top of the stack, which holds function parameters, local variables and return addresses. The stack tracks function calls, and SP marks where its top currently is.
  • SP points to the top of the stack, which holds function parameters, local variables and malloc()'d blocks. malloc() memory comes from the heap, not the stack.
  • SP points to the next instruction to run, and the stack holds parameters, local variables and return addresses. The next instruction is the PC. SP points to the top of the stack.
  • SP points to the top of the stack, which holds the program's code, static data and return addresses. Code and static data are loaded into their own region. The stack holds parameters, locals and return addresses.

Which list is a process's machine state (OSTEP)?

  • Its memory (code, static data, heap, stack), its registers (PC, SP, …), and its I/O information (open files). These three are everything the process can read or change, so they are what the OS saves and restores.
  • Its memory (heap and stack only), its registers (PC, SP, …), and its I/O information (open files). Memory is the whole address space: code and static data too.
  • Its memory (code, static data, heap, stack), its PC only, and its I/O information (open files). All the registers are part of it (PC, SP, frame pointer, general-purpose).
  • Its memory (code, static data, heap, stack), its registers (PC, SP, …), and its program file on disk. The file on disk is the program. The third part is I/O information: the files it has open.

The process API

The problem: users and programs need a way to ask the OS to start, stop and check on processes.

An API is the set of requests you are allowed to make. Bilal's restaurant analogy:Bilal slides, Ch 4

  • The menu lists what you can ask for. (API)
  • The waiter carries your request and brings back the answer. (API)
  • The kitchen does the real work. (the OS)

Every OS offers these process requests in some form:

CallWhat it does
CreateMake a new process to run a program (typing a command, double-clicking an icon)
DestroyForcefully halt a runaway process
WaitWait for a process to stop running
StatusGet info about a process: how long it has run, what state it's in
Misc. controle.g. suspend and resume a process (listed in OSTEP, not on Bilal's slide)

The UNIX versions of these, fork(), exec() and wait(), are the whole of Lesson 3.

In short: learn Bilal's four calls, Create, Destroy, Wait, Status, plus OSTEP's misc. control (suspend / resume).

List the process API calls that every OS offers (Bilal's four, plus OSTEP's extra one).

Create, Destroy (halt a runaway process), Wait (for it to stop), Status (how long it ran, what state). OSTEP adds misc. control, e.g. suspend and resume.

Which is TRUE about the process API calls (both OSTEP and Dr. Bilal's slide list these)?

  • Destroy forcefully halts a runaway process, and Status reports info such as how long it has run. Destroy = "halt a runaway process"; Status = "get some status info" (how long it has run, what state it is in).
  • Destroy forcefully halts a runaway process, and Status suspends it so it can be resumed later. Suspend/resume is OSTEP's misc. control. Status only reports info (run time, state).
  • Wait forcefully halts a runaway process, and Status reports info such as how long it has run. Halting a runaway process is Destroy. Wait waits for a process to stop running.
  • Destroy frees the entry of a process that has already exited, and Status reports info such as how long it has run. Destroy stops a process that is still running (a runaway) forcefully. Cleaning up after an exit is not Destroy's job.

Which is TRUE about Dr. Bilal's restaurant analogy for the process API?

  • The menu and the waiter are both the API; the kitchen is the OS, which does the real work. Menu = what you can ask for, waiter = carries the request and the response (both API), kitchen = the OS.
  • The menu is the API and the waiter is the OS; the kitchen is the hardware, which does the real work. The waiter is the API too (the messenger), and the kitchen is the OS.
  • The menu and the waiter are both the API; the kitchen is the user program, which does the real work. The kitchen is the OS: it has the data and does the complex work. The program is the customer ordering.
  • The menu and the kitchen are both the API; the waiter is the OS, which carries the request. Swapped: the waiter is the API (the messenger) and the kitchen is the OS.

How the OS creates a process

The problem: a program is just bytes in a file on disk. What exactly does the OS do to turn it into a running process?

It sets the stage, then hands over the CPU. That takes five steps:OSTEP §4.3

  1. Load code and static data from disk into the process's memory. (Static data = initialised global variables.) Early OSes did this eagerly: all at once, before running. Modern OSes do it lazily: they load each piece only when the program actually needs it. (Lazy loading uses paging and swapping, which come later.)
  2. Allocate the stack. Fill it with the arguments to main(): argc and the argv array. The stack holds local variables, parameters and return addresses.
  3. Allocate a small heap for dynamic memory. It grows when the program calls malloc(). It shrinks back when the program calls free().
  4. Set up I/O. Every UNIX process starts with three files already open. Each has a number, called a file descriptor: 0 = standard input, 1 = standard output, 2 = standard error. That's why a program can read the keyboard and print to the terminal without opening anything.
  5. Jump to main(). The OS hands the CPU to the new process, and it starts running.
Bilal's question: "why the empty space?" The free gap between heap and stack lets both grow. The heap grows as you malloc() more. The stack grows as you call deeper functions. They sit at opposite ends and grow toward each other, so neither has to guess its size in advance.

In short: load code + static data (lazily), make the stack (argc/argv), make the heap (malloc), open fds 0/1/2, jump to main().

When the OS creates a process, which memory region gets argc/argv, and which region serves malloc()?

The stack is filled with the arguments to main() (argc, argv). The heap serves malloc(); it starts small and grows as needed.

Why does a process's address space leave an empty gap between the heap and the stack?

So that both can grow toward each other: the heap grows with malloc(), the stack grows with deeper function calls. Neither has to guess its size in advance.

Every UNIX process starts with three open file descriptors. Give each number and its name.

0 = standard input, 1 = standard output, 2 = standard error.

Which is TRUE about the three file descriptors every UNIX process starts with?

  • 0 is standard input, 1 is standard output, 2 is standard error. They are already open, so a program can read the keyboard and print without opening anything.
  • 0 is standard output, 1 is standard input, 2 is standard error. Swapped: 0 is input and 1 is output.
  • 1 is standard input, 2 is standard output, 3 is standard error. Numbering starts at 0: 0, 1, 2.
  • 0 is standard input, 1 is standard error, 2 is standard output. 1 is standard output and 2 is standard error.

Which is TRUE about how the OS sets up a new process's memory?

  • It fills the stack with argc and argv, and gives it a small heap that grows with malloc(). Arguments to main() go on the stack; dynamic memory comes from the heap.
  • It fills the heap with argc and argv, and gives it a small stack that grows with malloc(). Swapped: argc/argv go on the stack, and malloc() uses the heap.
  • It fills the stack with argc and argv, and gives it a fixed heap that malloc() can never grow. The heap starts small and grows as the program asks for more.
  • It fills the stack with argc and argv, and places the heap right next to the stack with no gap. There is a free gap between heap and stack so both can grow toward each other.

From your lab: the File Descriptor Monster

In Lab 3, Task 5, your fd_monster.c did three things:

  1. Open log.txt 50 times, without closing it.
  2. Print each file descriptor number it got back.
  3. Close them all at the end.

It shows step 4 above ("Set up I/O") and the I/O information part of machine state.

Your output, from the write-up:

$ ./monster
Monster opened file descriptor: 3
Monster opened file descriptor: 4
   ... 5 to 51 ...
Monster opened file descriptor: 52

Why does it start at 3? Two facts:

  • The OS already opened 0, 1 and 2 (stdin, stdout, stderr) when it created the process.
  • open() always returns the lowest free number.

So 50 opens get 3, 4, 5, … up to 52.

What if you open more than you're allowed? Your limit (ulimit -n) was 524288. Numbers start at 0, so 524288 descriptors are 0 to 524287. When you raised MAX_FILES past the limit, the last success was descriptor 524287. The next open() failed with "Too many open files".

Bug when open() fails. Here is what happens, step by step:
  1. The failing slot gets fds[i] = −1, and the break stops the loop.
  2. The slots after it were never set. They hold leftover stack garbage.
  3. The cleanup loop calls close() on those garbage numbers.
I ran a copy with a low limit (ulimit -n 12). The unset slots held values like 0 and 6. So the loop called close(0) and closed standard input. If a slot happens to hold 1, standard output closes and later printf lines vanish. That fits the missing last two lines you saw in Mission 3.
Fix (either one): set every slot to −1 before the open loop (for (int i = 0; i < MAX_FILES; i++) fds[i] = -1;). Or remember how many opened (count = i) and close only fds[0] to fds[count-1].
Exam angle: "A process with only 0, 1, 2 open calls open() three times, then closes one. What does the next open() return?" The rule is always the same: the lowest free number. Example: the opens get 3, 4, 5; close 3; the next open gets 3, not 6.

The monster opens log.txt 4 times, then calls close(4), then opens it once more. What does that last open() return?

The 4 opens return 3, 4, 5, 6. After close(4), the lowest free number is 4, so the last open() returns 4 (not 7).

Write the fix for the monster's cleanup bug from memory (either version).

Before the open loop: for (int i = 0; i < MAX_FILES; i++) fds[i] = -1; so the existing if (fds[i] >= 0) skips unused slots. Or: after the open loop, keep count = number opened and loop for (int i = 0; i < count; i++) close(fds[i]);.

Your ulimit -n was 524288. Why was the last descriptor you got 524287 and not 524288?

The limit is how many descriptors a process may hold. They are numbered from 0, so 524288 descriptors are 0 to 524287. (0, 1, 2 were already in use, so the monster itself got 3 to 524287.)

Your monster runs with MAX_FILES = 50 and nothing else open. Which is TRUE?

  • The opens return 3 through 52, because 0, 1 and 2 are already open. 50 numbers starting at 3 end at 52, as in your output.
  • The opens return 0 through 49, because the monster opens 50 files. 0, 1 and 2 are already open (stdin, stdout, stderr), so the first free number is 3.
  • The opens return 3 through 53, because 0, 1 and 2 are already open. Off by one: 50 numbers from 3 are 3 to 52.
  • The opens return 1 through 50, because descriptor 0 is reserved for errors. Numbering starts at 0, and 0 is standard input; errors go to 2.

In the monster, open() fails when i = 7 and the loop breaks. Which is TRUE about the cleanup loop?

  • fds[7] is −1 and skipped, but fds[8] to fds[49] were never set, so close() may get garbage. Only the failing slot was written; the rest still hold whatever was on the stack.
  • fds[7] to fds[49] are all −1 and skipped, so only fds[0] to fds[6] are closed. Only fds[7] got −1. Slots 8 to 49 were never assigned.
  • fds[7] is −1, so close(-1) runs and the program crashes before the other slots. The if (fds[i] >= 0) check skips −1; the problem is the unset slots after it.
  • fds[7] is −1 and skipped, and the cleanup loop stops there, so slots 8 to 49 are never touched. The cleanup loop has no break; it visits all 50 slots, including the garbage ones.

Each successful open() in the monster grows which part of the process's machine state?

  • Its I/O information: the list of files the process has open. Open files are the third part of machine state, next to memory and registers.
  • Its registers: each open file is held in a CPU register until it is closed. The descriptor number is just an int; the open file is recorded in the process's I/O information.
  • Its heap: each open file is a block that open() allocates with malloc(). open() is a system call; the OS records the file in the process's open-file list, not in your heap.
  • Its code: each open file is loaded into the code region until it is closed. Opening a file doesn't load it as code; it adds an entry to the open-file list.

Process states

The problem: many processes exist, but only one can use the CPU at a time. The OS needs to track what each one is doing right now.

Think of a doctor's clinic with one doctor. One patient is with the doctor. Others sit in the waiting room, ready to go in. One patient was sent off for a blood test and can't see the doctor until the result comes back. A process has the same three states:OSTEP §4.4

RunningOn a CPU right now, executing instructions. (With the doctor.)
ReadyCould run right now, but the OS has chosen not to run it at this moment. (Waiting room.)
BlockedDid something that means it can't continue until some event happens. Usually it started an I/O request to a disk. Meanwhile, another process can use the CPU. (Away at the blood test.)

Press Step to watch two processes move around the state diagram. This is OSTEP's own example. Figure 4.3 has two CPU-only processes. Figure 4.4 adds I/O.

Notice three things in Figure 4.4:

  • At time 3, P0 starts I/O. From time 4 it is Blocked. The OS runs P1 at once, instead of leaving the CPU idle. That's the whole point of the Blocked state: it keeps the CPU busy.
  • At time 7, the I/O finishes. P0 goes to Ready, not straight to Running. It waits until the scheduler picks it.
  • The OS made a policy decision there: it let P1 finish before switching back to P0. Whether that's a good choice is a scheduling question (Lessons 5–9).OSTEP §4.4
TransitionNameCaused by
Ready → RunningscheduledThe OS picks this process
Running → ReadydescheduledThe OS takes the CPU away (e.g. its time slice is up)
Running → BlockedI/O: initiateThe process starts I/O (or waits for some event)

Trap There is no arrow from Blocked to Running and no arrow from Ready to Blocked. Why? A process must be running to start I/O. And after I/O it must queue up in Ready again. (The patient back from the blood test returns to the waiting room, not straight into the doctor's room.)

In short: Running ⇄ Ready (scheduled / descheduled), Running → Blocked (I/O starts), Blocked → Ready (I/O done). Nothing else.

Name the three basic process states and the event that causes Running → Blocked and Blocked → Ready.

Running, Ready, Blocked. Running → Blocked: the process initiates I/O (or waits for an event). Blocked → Ready: the I/O is done.

Which two arrows do NOT exist in the Running/Ready/Blocked diagram, and why?

No Blocked → Running: after I/O a process must queue in Ready until the scheduler picks it. No Ready → Blocked: a process has to be running to start I/O.

One CPU. P0 runs 1 tick, then starts I/O that keeps it Blocked for 3 ticks, then needs 1 more tick. P1 needs 4 ticks of CPU, no I/O. P0 starts first; the OS runs P1 while P0 is blocked and lets P1 finish. What state is P0 in during tick 5, and when does P0 finish?

Tick 1: P0 runs. Ticks 2–4: P0 Blocked, P1 runs. The I/O is done after tick 4, so in tick 5 P0 is Ready (P1 still has the CPU for its 4th tick). P0 runs in tick 6 and finishes at the end of tick 6.

Which correctly describes the Ready state?

  • The process could run right now, but the OS has chosen not to run it at this moment. It is waiting only for the scheduler, not for any event.
  • The process can't run right now, because it is waiting for an I/O request to finish. Waiting for I/O is Blocked.
  • The process could run right now, and the OS must run it next because it has been waiting. The scheduler decides; being Ready gives no guarantee of running next.
  • The process could run right now, but it has given up the CPU until some event happens. Waiting for an event is Blocked. In Ready, it is the OS that chose not to run it.

Which correctly describes the Blocked state?

  • The process started an I/O request and can't continue until it is done; meanwhile another process can use the CPU. Blocking frees the CPU for someone else, which is the whole point of the state.
  • The process started an I/O request and can't continue until it is done; meanwhile the CPU must stay idle. The OS runs another process meanwhile, so the CPU stays busy.
  • The OS took the CPU away because its time slice ran out, and it waits to be scheduled again. That is being descheduled: Running → Ready, not Blocked.
  • The process started an I/O request and, as soon as it is done, goes straight back to Running. When the I/O is done it goes to Ready and waits for the scheduler.

Which transition really exists in the Running / Ready / Blocked diagram?

  • Blocked → Ready, when the I/O the process was waiting for is done. "I/O: done" puts it back in the Ready queue; the scheduler picks it later.
  • Blocked → Running, when the I/O the process was waiting for is done. There is no such arrow: it must go to Ready first.
  • Ready → Blocked, when the process starts an I/O request while waiting. A Ready process isn't running, so it can't start I/O. Only Running → Blocked exists.
  • Running → Ready, when the process starts an I/O request. Starting I/O is Running → Blocked. Running → Ready is the OS descheduling it.

Real systems: two more states (and xv6's six)

The problem: the three states cover a process's middle life. But what about while it is being born, and just after it dies?

Real OSes add one state at each end of a process's life:OSTEP §4.5

  • Initial (also called embryo): the process is still being created.
  • Final, called the zombie state: the process has exited but hasn't been cleaned up yet. Why keep it? Its parent may want to know how it ended. So the OS keeps its exit status until the parent collects it with wait(). Lesson 3 picks this up.

Bilal's slides list six states from xv6. xv6 is a small teaching OS that re-implements classic Version 6 UNIX (hence the name).Bilal slides, Ch 4 Each xv6 state maps onto the model above:

EMBRYOJust created (e.g. by fork), still being set up, not yet ready to runInitial
SLEEPINGWaiting for an event: data from the disk, a keystrokeBlocked
RUNNABLEFully loaded and able to run, waiting for the CPUReady

Map the xv6 states SLEEPING, RUNNABLE and EMBRYO onto the basic process-state model.

SLEEPING = Blocked, RUNNABLE = Ready, EMBRYO = Initial (still being created).

What is a zombie process, and what makes it go away?

A process that has exited but whose exit status hasn't been collected yet. It stays in the table until its parent calls wait() to reap it.

Which correctly maps xv6 states?

  • SLEEPING = Blocked, RUNNABLE = Ready, UNUSED = a free process-table slot. Sleeping waits for an event, runnable waits for the CPU, and unused means no process is in that slot.
  • SLEEPING = Ready, RUNNABLE = Blocked, UNUSED = a free process-table slot. Swapped: SLEEPING is Blocked and RUNNABLE is Ready.
  • SLEEPING = Blocked, RUNNABLE = Running, UNUSED = a free process-table slot. RUNNABLE = Ready (waiting for the CPU). Running has its own state, RUNNING.
  • SLEEPING = Blocked, RUNNABLE = Ready, UNUSED = a process still being created. A process still being set up is EMBRYO.

Which is TRUE about a zombie process?

  • It has exited, but its parent hasn't called wait() yet, so its entry stays to hold the exit status. The entry lingers until the parent reaps it with wait().
  • It has exited, and its parent has already called wait(), so its entry stays to hold the exit status. wait() reaps it; a zombie is one that has not yet been waited for.
  • Its parent has exited, but it is still running, so its entry stays until init collects it. That is an orphan. A zombie has itself exited.

Data structures: the process list and the PCB

The problem: the OS is a program too. Where does it write down everything it knows about each process?

The OS keeps a process list (or task list). It has one entry for every process. Like a clinic's patient register, it is used in two ways:Zafar slides, Lecture 2

  • The scheduler reads it to choose who runs next.
  • The OS uses it to find a process again, for example to check its status.

Each entry is a Process Control Block (PCB), also called a process descriptor. In Bilal's words, it is "a fancy way of talking about a C structure that contains information about each process".Bilal slides, Ch 4 It holds two kinds of thing:

  • the machine state from earlier: saved registers, memory info, open files;
  • bookkeeping: PID, state, parent.

Here is xv6's real one, exactly as on Bilal's slide (OSTEP Figure 4.5):OSTEP Fig 4.5

struct proc {
  char *mem;                   // Start of process memory
  uint sz;                     // Size of process memory
  char *kstack;                // Bottom of kernel stack for this process
  enum proc_state state;       // Process state
  int pid;                     // Process ID
  struct proc *parent;         // Parent process
  void *chan;                  // If !zero, sleeping on chan
  int killed;                  // If !zero, has been killed
  struct file *ofile[NOFILE];  // Open files
  struct inode *cwd;           // Current directory
  struct context context;      // Switch here to run process
  struct trapframe *tf;        // Trap frame for the current interrupt
};

In OSTEP the figure also shows the two helper types it uses:

// registers xv6 saves and restores when it stops and restarts a process
struct context {
  int eip;   // the PC (instruction pointer)
  int esp;   // the stack pointer
  int ebx, ecx, edx, esi, edi, ebp;
};
enum proc_state { UNUSED, EMBRYO, SLEEPING, RUNNABLE, RUNNING, ZOMBIE };

When the OS stops a process, it saves the registers into that process's context. To resume it, the OS loads them back into the CPU. That save-and-restore is the context switch. Lesson 4 covers it in detail.

In short: one PCB per process, kept in the process list. Remember five groups: identity, state, registers, memory, files.

What is a PCB, and what groups of information does it hold?

A Process Control Block (process descriptor) is the C struct the OS keeps for each process in the process list. It holds: identity (pid, parent), state, saved registers (context), memory info (start, size), and open files.

In xv6's struct proc, which field does the OS save a process's registers into when it stops it?

The context field (struct context: eip = PC, esp = SP, plus the other registers). Loading it back is part of the context switch.

Which is TRUE about the Process Control Block (PCB)?

  • It is a C struct kept for each process in the process list; xv6 saves the process's registers in its context field. One PCB per process, holding identity, state, saved registers, memory info and open files.
  • It is one C struct shared by all processes in the process list; xv6 saves the registers in its context field. There is one PCB per process: each entry in the process list is a PCB.
  • It is a C struct kept for each process in the process list; xv6 saves the process's registers in its chan field. chan is what a sleeping process waits on. Registers go in context.
  • It is a C struct kept for each process in the process list; it holds the saved registers but not the PID or state. It holds the PID, state and parent too, alongside registers, memory info and open files.

struct proc {

    struct proc *parent;          // who made me
    int state;                    // UNUSED, RUNNABLE, RUNNING, SLEEPING ...

In your process_manager.c, which is TRUE about is_active?

  • is_active == 0 means the slot is free, like xv6's UNUSED; create takes the first such slot. Line 54 picks the first slot with !is_active, just as a new process needs a free (UNUSED) entry.
  • is_active == 0 means the process has exited but not been reaped, like xv6's ZOMBIE. terminate frees the slot at once; no parent has to collect anything. That is UNUSED.
  • is_active == 0 means the process is still being set up, like xv6's EMBRYO. create fills the fields and sets is_active = 1 in one go; 0 means no process in the slot.
  • is_active == 1 means the slot is free, like xv6's UNUSED; create takes the first such slot. Reversed: 1 means a process is using the slot, 0 means free.

  • heap: [141-200] and stack: [201-220], and next_address becomes 221. Each segment starts exactly at the previous base + size (line 72), with no gap byte.
  • heap: [140-199] and stack: [200-219], and next_address stays 100. Line 77 adds the total (120) to next_address.

You type terminate 5 for a running PID 5. Which is TRUE?

  • Its slot can be reused at once, but its memory is not given back, because next_address never goes down. Line 89 only clears is_active; nothing touches next_address.
  • Its slot can be reused at once, and its memory is given back, because next_address goes down. No line lowers next_address; the memory is never reused.
  • Its memory can be reused at once, but its slot is not given back, because is_active stays 1. Reversed: line 89 sets is_active = 0, freeing the slot; the memory is what stays lost.

Process vs thread (link back to Lesson 1)

The problem: a process can do several things at once using threads. Which parts of the process does each thread get for itself, and which parts are shared?

A process can contain several threads. Each thread is a separate stream of execution. It is at its own point in the code, inside its own function calls. So each thread needs its own PC, registers and stack. But all the threads of one process share that process's address space and open files.

In struct proc terms: each thread gets its own context and stack. Everything else is shared.

Two processesTwo threads in one process
Address space (code, heap, globals)SeparateShared
Open filesSeparateShared
PC, registers, stackSeparateSeparate

In short: threads share memory and files; each thread has its own PC, registers and stack. Example: 4 threads = 4 stacks, 1 address space.

A process runs 3 threads. How many stacks, sets of registers, and address spaces does it have?

3 stacks and 3 sets of registers (one per thread, each with its own PC), but only 1 address space, shared by all three threads (along with the open files).

Two threads run inside one process. Which is TRUE?

  • They share the heap, globals and open files, but each has its own PC, registers and stack. One address space and one set of open files per process; each thread is its own stream of execution, so it needs its own PC, registers and stack.
  • They share the heap, globals and stack, but each has its own PC and registers. Each thread has its own stack: it calls its own functions, with its own locals and return addresses.
  • They share the heap and globals, but each has its own PC, registers, stack and open files. Open files belong to the process, so the threads share them.
  • They share the code and globals, but each has its own heap, PC, registers and stack. The heap is part of the process's address space, so it is shared (that is why threads can pass malloc()'d data to each other).

Why can two threads race on a global counter, while a parent and its fork()ed child each doing counter++ cannot?

  • The threads share one address space, so both update the same counter; each process updates its own copy. fork() gives the child its own copy of the address space, so there is no shared variable to race on.
  • The threads share one stack, so both update the same counter; each process updates its own copy. Each thread has its own stack, and a global isn't on the stack anyway. What they share is the address space (globals, heap).
  • The threads share one set of registers, so both update the same counter; each process updates its own copy. Registers are per thread (each has its own A_reg/B_reg in the trace). The race is on the shared memory value.
  • The threads share one address space, so both update the same counter; the processes never run interleaved. Processes are interleaved too (time sharing). They don't race because each has its own copy of counter.

Practice

Answer from memory first, then check.

1. You start ./calc in two terminal windows at once. How many programs and processes are there?

There is one file on disk (one program), but two running instances. Each has its own memory, registers and open files, so there are two processes.

2. Which register tells the CPU which instruction to execute next?

The program counter (instruction pointer) holds the address of the next instruction. The stack pointer tracks the top of the stack (locals, parameters, return addresses).

3. A program writes an error message with write(?, msg, len) without opening any file. Which file descriptor number does it use for standard error?

Every process starts with three open descriptors: 0 = stdin, 1 = stdout, 2 = stderr.

4. A process is Blocked waiting for a disk read. The read completes. Where does it go?

"I/O: done" moves Blocked → Ready. It only runs again when the scheduler picks it. There is no Blocked → Running arrow.

5. One CPU. P0 runs for 2 ticks, then starts an I/O that keeps it Blocked for the next 4 ticks, then needs 2 more ticks of CPU. P1 needs 3 ticks of CPU and does no I/O. P0 runs first, and the OS runs P1 whenever P0 is blocked. How many ticks is the CPU idle before both finish?

TickP0P1
1–2RunningReady
3–5BlockedRunning (done at 5)
6Blocked– ← CPU idle
7–8Running (I/O done)–
P0 is blocked during ticks 3, 4, 5 and 6, but P1 only has 3 ticks of work, so tick 6 has nothing to run: 1 idle tick.

6. In xv6, a process waiting for a keystroke is in which state?

Waiting for an event = SLEEPING = Blocked. RUNNABLE is Ready (could run right now), EMBRYO is still being created, ZOMBIE has exited.

7. What does it mean that modern OSes load programs "lazily"?

Lazy loading brings code and data into memory only when the running program actually touches them (using paging and swapping). Early OSes loaded everything eagerly, up front.
8. List, in order, the steps the OS takes to turn a program into a running process.
(1) Load code and static data from disk into memory (lazily in modern OSes). (2) Allocate the stack and initialise it with argc/argv. (3) Allocate a small heap (grows with malloc). (4) Set up I/O: file descriptors 0, 1 and 2 (stdin, stdout, stderr). (5) Jump to main() and give the process the CPU.
9. Without looking, write a basic struct proc with at least six fields and a comment on each.
Something like: int pid; (ID), int state; (Running/Ready/Blocked), void *pc; and void *sp; (saved registers, or struct context context), struct proc *parent;, void *base; int size; (memory), int open_files[16]; or struct file *ofile[NOFILE], char name[20];. You need the groups identity, state, registers, memory, files.
