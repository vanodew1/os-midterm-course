Lesson 3 · Virtualizing the CPU

fork, exec and wait

The question for this lesson: how does a program start another program? UNIX does it in a strange way. First it makes a copy of the process that asked. Then the copy can turn itself into a different program. Three system calls do the whole job. OSTEP calls fork() "certainly the strangest routine you will ever call".OSTEP §5.1

The one-sentence version fork() creates a child that is a near-copy of the parent (new PID, returns twice). wait() makes a parent pause until its own child finishes. exec() replaces the current program with a new one (same PID, never returns on success). A shell uses all three together.OSTEP §5Bilal slides, Ch 5

A running process's time slice runs out and the OS takes the CPU away. What is that transition called, and which state does the process move to?

It is descheduled: Running → Ready. It can run again as soon as the scheduler picks it (it is not waiting for any event).

Which file descriptor number does every UNIX process use for standard output, and what are the other two default ones?

1 = standard output. The others: 0 = standard input, 2 = standard error.

Two threads each run counter++ 1,000 times on a shared counter that starts at 0. Why can the final value be less than 2,000?

counter++ is really LOAD, ADD, STORE. If the OS switches threads between those steps, both threads can load the same old value and one increment is lost. This is a race condition.

System calls and <unistd.h>

The problem: your C program wants the OS to do something for it, like make a new process. How does it ask?

It calls a function that the OS offers. A set of functions like that is called an API (Application Programming Interface).

The OS's API is its set of system calls. A system call is a function that asks the OS to do privileged work for you, such as touching the hardware. Because the work is privileged, system calls always run in kernel mode (the CPU's privileged mode; Lesson 4 explains it).Bilal slides, Ch 5

In C, the process-related system calls come from two headers:

HeaderGives you
<unistd.h>fork(), the exec family, getpid(), getppid(), read(), write(), close()
<sys/wait.h>wait(), waitpid() ("We need wait.h", says Bilal's slide)
This is how it's asked: "What is <unistd.h> for?" It's the UNIX standard header. It gives a C program access to the POSIX operating-system API. That means two groups of basic system calls:
  • process management: fork, exec, getpid
  • low-level file I/O: read, write, close

In short: system calls are how a program asks the OS for help, and they always run in kernel mode. <unistd.h> gives fork/exec/getpid; <sys/wait.h> gives wait/waitpid.

In C, which header gives you fork(), exec and getpid(), and which one gives you wait()/waitpid()?

<unistd.h> (the UNIX standard header, POSIX OS API) for fork, exec, getpid, read, write, close. <sys/wait.h> for wait and waitpid.

In which CPU mode do system calls run?

Always in kernel mode (privileged mode), because they access hardware and other privileged operations.

Which is TRUE about system calls in C?

  • They always run in kernel mode, and fork() and getpid() come from <unistd.h>. System calls do privileged work; <unistd.h> is the POSIX header for the process calls.
  • They always run in user mode, and fork() and getpid() come from <unistd.h>. System calls run in kernel (privileged) mode.
  • They always run in kernel mode, and fork() and getpid() come from <sys/wait.h>. <sys/wait.h> gives wait()/waitpid(). fork and getpid are in <unistd.h>.
  • They run in kernel mode only when they touch a device, and fork() comes from <unistd.h>. They always run in kernel mode, whatever they do.

fork(): one call, two processes

The problem: a running process wants a second process. How does UNIX make one?

It makes a copy. Think of a photocopier: you put in one page and get two that look the same.

  • The process that calls fork() is the parent. The new process is the child.
  • The child is nearly identical to the parent. It has the same code and the same variable values.
  • But the child gets its own copy of the memory (address space) and registers. So changing a variable in one process doesn't change it in the other.
  • The child does not start at main(). It starts right after the fork() call, because that is the moment it was copied.Bilal slides, Ch 5

Now both processes run the same code from the same line. How does each one know which one it is? By the value fork() returns.

Bilal's first example (p1.c), trimmed:Bilal slides, Ch 5

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main(int argc, char *argv[])
{
    printf("[pid:%d] - Hello Students\n", (int) getpid());

    int return_child = fork();

    if (return_child < 0) {                 // fork failed
        fprintf(stderr, "fork failed\n");
        exit(1);
    }
    if (return_child == 0)                  // only the child runs this
        printf("[pid:%d] - I am child. return_child = [%d]\n",
               (int) getpid(), return_child);
    else                                    // the parent continues here
        printf("[pid:%d] - I am parent of [%d]\n",
               (int) getpid(), return_child);
    return 0;
}
$ ./p1
[pid:6318] - Hello Students
[pid:6318] - I am parent of [6319]
[pid:6319] - I am child. return_child = [0]

"Hello Students" prints once. When that line ran, the child didn't exist yet. Everything after the fork runs in both processes.

Trap: the order is not guaranteed Run it again and the child may print first. Why? After fork() there are two separate processes. The scheduler (the part of the OS that picks who runs next) decides which goes first. So the output is non-deterministic: it can change from run to run. It's the same idea as the race in Lesson 1, but with whole processes.OSTEP §5.1 Only wait() (below) can force an order.

In short: fork() copies the caller. The child gets 0, the parent gets the child's PID, and −1 means it failed. The child starts just after the fork, with its own copy of every variable, and nobody knows who prints first.

What does fork() return in the parent, in the child, and when it fails?

Parent: the child's PID (positive). Child: 0. Failure: −1 (negative), and no child is created.

Where does a newly forked child start executing?

Right after the fork() call, not at main(), because that is the moment it was copied from the parent.
Predict the output:

else         { x = x - 1; printf("parent %d\n", x); }
It prints child 15 and parent 9, in either order (the scheduler decides). Each process has its own copy of x, so one change doesn't affect the other.

int rc = fork(); Which is TRUE about the value of rc?

  • In the child it is 0; in the parent it is the child's PID; −1 means no child was created. 0 tells the child who it is; the parent needs the child's PID (for wait/waitpid).
  • In the parent it is 0; in the child it is the child's PID; −1 means no child was created. Swapped: the child gets 0 and the parent gets the child's PID.
  • In the child it is 0; in the parent it is the parent's own PID; −1 means no child was created. The parent gets the child's PID, so it knows which child it made.
  • In the child it is 0; in the parent it is the child's PID; −1 means the child was created but crashed. −1 means the fork failed and no child exists at all.

Which is TRUE about where a newly forked child begins?

  • It starts just after the fork() call, with its own copy of the parent's variables. It was copied at the moment of the fork, so it continues from there with its own address space.
  • It starts at the top of main(), with its own copy of the parent's variables. It does not restart main(); it continues right after the fork.
  • It starts just after the fork() call, sharing the parent's variables with it. It gets its own copy: a change in one process doesn't show up in the other.
  • It starts just after the fork() call, with all variables reset to their starting values. The copy keeps the current values the parent had at the fork.
Printed to a terminal, which output is possible?
printf("A\n");
int rc = fork();
if (rc == 0) printf("B\n");
else         printf("C\n");
  • A C B: A prints once, then the parent and child print in either order. Without wait() the scheduler decides who runs first, so the parent's C may come before the child's B.
  • A B A C: A prints in both processes, then each prints its own letter. A printed before the fork, when the child didn't exist yet, so it prints once.
  • B A C: the child prints first, then the parent prints A and C. A is printed before the fork, so it must come first.
  • A B: A prints once, then only the child prints its letter. The parent also continues after the fork and prints C.

Tracing fork trees

The problem: with several forks, processes multiply fast and it's easy to lose count. How do you keep track?

You draw a tree. Each process is a node, and each fork adds a child node below the process that called it. Exam questions give you code with several forks and ask three things: how many processes, who is whose parent, and who prints what.

Try each program below. Press Step to create one process at a time, and read the line under the tree.

Node colour = generation: blue is the original process, orange its children, green its grandchildren, purple the next generation. The text under each node is what that process prints. "fork #k" means the k-th fork() call in program order (for the loop, fork #k happens when i = k−1).

The recipe

  1. Start with one node, P0, at the top of the code. Note what it prints.
  2. Each time a process reaches a fork(), draw a child below it.
  3. The child continues from just after that fork, with return value 0. The parent continues with a positive return value.
  4. Follow each process on its own through the if/else, using its own return value. A process only reaches a later fork() if its branch contains one.
  5. Count the nodes for "how many processes". Read the prints off each node.
Counting shortcuts Why a shortcut works: if every process runs a fork, the number of processes doubles. 1 → 2 → 4 → 8.
n forks in a row that every process executes (e.g. fork(); fork(); fork(); or a loop of n forks) → 2n processes, of which 2n − 1 are new. Example: 3 forks → 8 processes, 7 new.
A printf after the fork inside such a loop runs 2 + 4 + … + 2n = 2n+1 − 2 times. (During iteration i, counting from 1, there are 2i processes alive.) Example: n = 2 → 2 + 4 = 6.
A fork inside an if only doubles the processes that take that branch. So draw the tree. Don't use the formula.

wait(): the parent waits for its child

The problem: after a fork, we can't know who runs first. What if the parent needs the child to finish before it carries on?

The parent calls wait(). It's like a parent waiting at the school gate: it doesn't move on until its child comes out. Add #include <sys/wait.h> and write:

} else {                                 // parent
    int wc = wait(NULL);                 // block until a child finishes
    printf("parent of %d (wc: %d)\n", return_child, wc);
}
  • When the parent calls wait(), it blocks (pauses) until a child finishes.
  • Then wait() returns that child's PID.Bilal slides, Ch 5
  • So the output is now deterministic (the same every run): the child always prints first. Even if the parent happens to run first, it just sits in wait().OSTEP §5.2
  • To wait for one specific child, use waitpid(pid, &status, 0). It also collects that child's exit status.
This is how it's asked: "Can process A wait() for an unrelated process B?" No. wait() and waitpid() only work between a parent and its child. A process can wait only for its own children. Not even a grandchild counts. If A has no children, wait(NULL) returns −1 right away. I tested it: waitpid(1, NULL, 0) from an ordinary program fails with "No child processes".

Zombies and orphans

When a child exits, the parent may want its exit status ("did it succeed?"). So the OS can't throw the child away at once. It has to keep a record until the parent asks.

  • A zombie is a child that has exited but hasn't been waited for yet (xv6 ZOMBIE, Lesson 2). Its code and memory are gone. Only its PCB entry stays, so the parent can still read the exit status.
  • The parent's wait() reaps the zombie: it collects the status, and only then can the OS free the entry.Zafar slides, Lecture 3
  • So a long-running parent that forks children and never waits fills the process list with zombies.
  • An orphan is a child whose parent exited first. On Linux, init (PID 1) adopts it and reaps it when it ends. (This is general UNIX behaviour, not on the slides.)

In short: wait() blocks the parent until one of its own children ends, then returns that child's PID (−1 if it has no children). An exited child that nobody has waited for is a zombie; a child whose parent died first is an orphan, adopted by init.

What does a parent do when it calls wait(), and what does wait() return?

The parent blocks until one of its children finishes. wait() then returns that child's PID. If the caller has no children it returns −1 right away.

What is an orphan process, and who looks after it on Linux?

A child whose parent exited first. It is adopted by init (PID 1), which reaps it when it ends.

Which is TRUE about int wc = wait(NULL); in a parent?

  • The parent blocks until one of its children finishes, and wc is that child's PID. wait() returns the PID of the child it reaped.
  • The parent blocks until one of its children finishes, and wc is 0. 0 is what fork() returns in the child. wait() returns the child's PID.
  • The parent blocks until any process on the system finishes, and wc is that process's PID. It only waits for its own children; with none it returns −1 at once.
  • The parent blocks until all of its children finish, and wc is the number of children. One wait() returns after one child finishes, with that child's PID.

exec(): become a different program

The problem: fork() only gives you a copy of the same program. How do you run a different program, like ls or wc?

You call exec(). It loads a new program into the process that calls it.

  • exec() does not create a new process. It replaces the current program with another one (its code and static data).
  • The process's code, static data, heap and stack are all overwritten.
  • The PID stays the same, because it is still the same process.
  • If exec() succeeds, it never returns: the old program is gone, so there is nothing to return to. If it does return, something went wrong (e.g. the program wasn't found).Bilal slides, Ch 5

Bilal's p3.c child:

if (rc == 0) {                                // child
    printf("[PID: %d] - Hello, Child here.\n", (int) getpid());
    char *myargs[3];
    myargs[0] = strdup("wc");    // program: wc (word count)
    myargs[1] = strdup("p3.c");  // argument: file to count
    myargs[2] = NULL;            // marks END of array
    execvp(myargs[0], myargs);   // child becomes wc
    printf("THIS LINE SHOULDN'T PRINT\n");   // never runs
}

What happens, step by step:

  1. The child prints "Hello, Child here".
  2. The child builds the argument list. myargs[0] is the program name. The last slot must be NULL, so execvp knows where the list ends.
  3. execvp turns the child into wc. wc prints the line, word and character counts of p3.c, then the filename.
  4. The last printf never runs. That code no longer exists in the process.
  5. Meanwhile the parent sits in wait() until wc finishes.

Linux has 6 variants: execl, execlp, execle, execv, execvp, execvpe. The letters after "exec" tell you how each one takes its inputs:

  • l = the arguments as a list
  • v = the arguments as a vector (array)
  • p = search the PATH for the program
  • e = you pass the environment too

Analogy fork() is a photocopier: now there are two identical documents. exec() is erasing a document and writing a completely different text on the same sheet. It's the same sheet (same PID), but the content is new.

In short: exec() swaps the program inside the current process. Same PID, new code, data, heap and stack. On success it never returns, so any line after it runs only if it failed.

A child calls execvp() successfully, and the next line is a printf. Does the printf run? Why or why not?

No. A successful exec() never returns: the code, static data, heap and stack are all replaced by the new program, so that printf no longer exists. It only runs if exec fails.

In the exec family names (execl, execvp, execle…), what do the letters l, v, p and e mean?

l = arguments as a list, v = arguments as a vector (array), p = search the PATH for the program, e = you also pass the environment.

Which is TRUE about fork() and exec()?

  • fork() makes a process with a new PID; a successful exec() keeps the same PID and never returns. exec() replaces the program inside the existing process, so there is nothing to return to.
  • fork() makes a process with a new PID; a successful exec() also gives the process a new PID. exec() creates no process: the PID stays the same.
  • fork() makes a process with a new PID; a successful exec() keeps the same PID and returns 0. A successful exec() never returns; if it returns, it failed.
  • fork() keeps the caller's PID for the child; a successful exec() gives a new PID and never returns. Swapped: fork() gives a new PID, exec() keeps the same one.

A child calls execvp("ls", args) and it succeeds. Which is TRUE?

  • Its code, static data, heap and stack are replaced, but its PID and open file descriptors stay. Keeping the open descriptors is what lets a shell redirect output before the exec.
  • Its code and static data are replaced, but its old heap and stack are kept for the new program. The heap and stack are re-initialized too; nothing of the old program remains.
  • Its code, static data, heap and stack are replaced, and all its open file descriptors are closed. Open descriptors stay open, otherwise ls > out.txt could not work.
  • Its code, static data, heap and stack are copied into a new process, and the old program keeps running. exec() creates no new process; the old program is gone.

Why are fork and exec separate?

The problem: Windows makes a process and starts a program in one call (CreateProcess()). Why does UNIX use two calls?

Because of the gap between them. After fork() but before exec(), the child can run any code it likes. It uses that moment to set up the new program's surroundings, for example where its output goes.OSTEP §5.4

This is exactly how a shell works. The shell is just a user program that shows a prompt and runs the commands you type:

  1. The shell shows a prompt and you type a command, e.g. ls -l.
  2. The shell calls fork() to make a child.
  3. The child adjusts things (redirection, pipes…) and then calls exec() to become ls.
  4. The shell (the parent) calls wait(). When the child finishes, it prints the prompt again.

Case study: ls -l > out.txt

int rc = fork();
if (rc == 0) {                                     // child
    close(STDOUT_FILENO);                          // free fd 1 (the screen)
    open("out.txt", O_CREAT | O_WRONLY | O_TRUNC, 0644);   // takes fd 1
    char *args[] = { "ls", "-l", NULL };
    execvp(args[0], args);                         // ls now writes to out.txt
} else {
    wait(NULL);                                    // shell waits, then re-prompts
}
The file-descriptor trick A file descriptor (fd) is a small number a process uses to name an open file. fd 0 is standard input, fd 1 is standard output, fd 2 is standard error. By default they are the keyboard and the screen, but the numbers can be pointed somewhere else.
  1. open() always returns the lowest free file descriptor.
  2. So close fd 1 (stdout) first. Now 1 is the lowest free number.
  3. Then open the file. It becomes fd 1.
  4. ls is unchanged. It writes to "standard output" (fd 1) as usual, and that now goes to the file.
This only works because the child can run this code between fork and exec. And exec keeps open file descriptors, so ls inherits the new fd 1. (I compiled this and checked that out.txt contains the listing.)

Pipes (grep foo file | wc -l) use the same idea with the pipe() system call. The first process's output goes into a queue inside the kernel. The next process's input reads from that same queue.Zafar slides, Lecture 3

Beyond the big three (Zafar's slides)

  • A signal is a short message the OS delivers to a process, like a tap on the shoulder. kill() sends one.
  • Common signals: SIGINT (what Ctrl-C sends), SIGKILL (forced kill, can't be caught), SIGSTOP/SIGCONT (pause/resume).
  • A process can install a signal handler (its own function to run) for most signals.
  • Each process belongs to a user. A normal user can only signal their own processes. root (the superuser) can control any process.
  • Tools: ps (list processes), top (live view), kill -9 <pid>, killall <name>.

In short: fork and exec are separate so the child can set things up in between. A shell does fork → (child) redirect, then exec → (parent) wait. Redirection works because open() takes the lowest free fd.

List the four steps a shell takes to run a command like ls -l.

(1) Read the command at the prompt. (2) fork() a child. (3) The child sets things up (redirection, pipes) and calls exec() to become ls. (4) The shell wait()s, then prints the prompt again.

Why does close(STDOUT_FILENO) followed by open("f.txt", …) send a program's output into f.txt?

Because open() always returns the lowest free file descriptor. With fd 1 closed, the file becomes fd 1, so everything written to standard output goes to the file.

A child with fds 0, 1 and 2 open runs close(1); then open("out.txt", O_CREAT | O_WRONLY | O_TRUNC, 0644);. Which is TRUE?

  • open() returns 1, because it takes the lowest free descriptor, so standard output now goes to the file. fd 1 was just freed, so the file becomes fd 1, and anything written to stdout lands in it.
  • open() returns 3, because it takes the next unused number, so standard output still goes to the screen. open() takes the lowest free descriptor, which is 1.
  • open() returns 1, because it takes the lowest free descriptor, so standard error now goes to the file. fd 1 is standard output; standard error is fd 2.
  • open() returns 0, because it takes the lowest descriptor, so standard input now comes from the file. fd 0 is still open, so it isn't free. The lowest free one is 1.

Which sequence is right for a shell running ls -l > out.txt?

  • Shell forks → child redirects stdout to the file → child execs ls → shell waits. The redirection must happen in the child, after the fork and before the exec.
  • Shell forks → child execs ls → child redirects stdout to the file → shell waits. After a successful exec the child's own code is gone, so it must redirect before exec.
  • Shell forks → shell redirects stdout to the file → child execs ls → shell waits. The child redirects; the shell's own descriptors are separate after the fork and must stay on the screen.
  • Shell forks → child redirects stdout to the file → shell execs ls → child waits. Roles swapped: the child execs and the shell (parent) waits.

C you must be able to write

The problem: the exam may ask you to write small C programs and a Makefile on paper, with no compiler to catch mistakes.

Bilal's Quiz 1 did exactly this. Here are the three patterns with fresh examples. They're compiled and tested.

1 · Command-line arguments: argc, argv, atoi

// sumto.c   usage: ./sumto 5   →   1 + ... + 5 = 15
#include <stdio.h>
#include <stdlib.h>                      // atoi

int main(int argc, char *argv[])
{
    if (argc != 2) {                     // argv[0] is the program name
        printf("Usage: %s <n>\n", argv[0]);
        return 1;
    }
    int n = atoi(argv[1]);               // "5" (text) → 5 (int)
    int sum = 0;
    for (int i = 1; i <= n; i++)
        sum += i;
    printf("1 + ... + %d = %d\n", n, sum);
    return 0;
}

argc counts the program name too. So ./sumto 5 has argc = 2, argv[0] = "./sumto", argv[1] = "5". Every argv entry is a string (text). So you need atoi to turn "5" into the number 5.

2 · Reading a file line by line: fopen / fgets / fclose

// countlines.c   usage: ./countlines notes.txt
#include <stdio.h>

int main(int argc, char *argv[])
{
    if (argc != 2) {
        printf("Usage: %s <filename>\n", argv[0]);
        return 1;
    }
    FILE *fp = fopen(argv[1], "r");      // "r" = read
    if (fp == NULL) {                    // always check
        printf("Cannot open %s\n", argv[1]);
        return 1;
    }
    char line[256];
    int count = 0;
    while (fgets(line, sizeof(line), fp) != NULL)   // NULL = end of file
        count++;
    fclose(fp);
    printf("%s has %d lines\n", argv[1], count);
    return 0;
}

To print only the first n lines: change the loop condition to count < n && fgets(...) != NULL, and put printf("%s", line) inside the loop. fgets keeps the \n, so don't add another.

3 · A Makefile with all and run

CC = gcc
CFLAGS = -Wall

all: sumto countlines

sumto: sumto.c
	$(CC) $(CFLAGS) sumto.c -o sumto

countlines: countlines.c
	$(CC) $(CFLAGS) countlines.c -o countlines

run: all
	./sumto 5
	./countlines notes.txt

clean:
	rm -f sumto countlines
Makefile rules to remember
  • Format: target: dependencies, then the command on the next line.
  • The command must be indented with a TAB. Spaces cause a "missing separator" error.
  • A plain make builds the first target (here all).
  • run: all means "build everything first, then run". So make run compiles anything that changed, then runs each program.

In short: argc includes the program name and every argv is a string (use atoi). Always check fopen for NULL. Makefile commands start with a TAB.

You run ./area 4 7. What are argc, argv[0] and argv[2], and how do you turn argv[1] into an int?

argc = 3, argv[0] = "./area", argv[2] = "7" (a string). Use atoi(argv[1]) (from <stdlib.h>) to get the number 4.

In a Makefile, what must each command line start with, and which target does a plain make build?

A TAB (spaces give "missing separator"). Plain make builds the first target in the file (usually all).

Which is TRUE about int main(int argc, char *argv[])?

  • argc counts the program name too, and every argv entry is a string, even "5". ./sumto 5 → argc = 2, argv[1] = "5", which needs atoi to become the int 5.
  • argc doesn't count the program name, and every argv entry is a string, even "5". It does count it: argv[0] is the program name, so ./sumto 5 has argc = 2.
  • argc counts the program name too, and a number like 5 arrives in argv as an int. Every entry is a string (char *). Use atoi(argv[1]) to get the int.
  • argc counts the program name too, and the program name is stored in argv[1]. The name is argv[0]; the first real argument is argv[1].

  • It first brings all up to date, recompiling any program whose .c changed, then runs both programs. run depends on all, so make builds the dependencies first, then runs run's commands.

  • It first recompiles every .c file from scratch, changed or not, then runs both programs. make only rebuilds a target whose dependencies changed since it was last built.

Practice

Answer from memory first, then check. For tree questions, draw the tree on paper before you type.

1. Inside the newly created child, what value does fork() return?

The child gets 0. The parent gets the child's PID (positive). −1 means the fork failed and there is no child.

2. How many lines does this print in total?
for (int i = 0; i < 3; i++) { fork(); printf("x\n"); }

Each printf runs after that iteration's fork. Iteration 1 has 2 processes, iteration 2 has 4, iteration 3 has 8: 2 + 4 + 8 = 14 (= 24 − 2). Compiled and run: 14 lines.

3. How many processes in total (including the original) run this?
fork(); if (fork() == 0) fork();

After the first fork() there are 2 processes. Each one runs if (fork() == 0) fork();, which turns 1 process into 3 (itself, a child, and that child's child). 2 × 3 = 6. Verified by running it.

4. A child with PID 4210 successfully calls execvp("ls", args). What is the PID of the running ls?

exec() doesn't create a process. It replaces the program inside the same process, so the PID is still 4210. Only fork() makes a new PID.

5. Process X (PID 500) calls waitpid(812, NULL, 0). PID 812 is an editor someone started from another terminal. What happens?

You can only wait for your own children. 812 isn't X's child, so waitpid fails immediately with −1 ("No child processes").

6. Why does UNIX keep fork() and exec() as two separate calls?

The gap between them lets the child change its own setup (close stdout and open a file, set up pipes) before the new program starts. That's how shells do > and | without the program knowing.
7. Trace this program: how many processes are there, what's the hierarchy, and who prints what?
printf("1\n"); if (fork() == 0) { printf("2\n"); fork(); printf("3\n"); } else { printf("4\n"); }
3 processes. P0 (original) prints 1, 4. P1 (P0's child, fork returned 0) prints 2, 3, then forks. P2 (P1's child) starts right after that fork, so it prints only 3. Hierarchy: P0 → P1 → P2; P0 is P2's grandparent. (Compiled and run: P2's parent PID is P1's PID.)
8. What is a zombie process, and what gets rid of it?
A child that has exited but whose parent hasn't yet called wait()/waitpid() on it. Its entry stays in the process list so the parent can collect the exit status. The parent's wait() reaps it. If the parent exits first, init adopts the child and reaps it.
9. Write what the shell's child does for sort data.txt > sorted.txt, in order.
After fork() returns 0: close(STDOUT_FILENO); → open("sorted.txt", O_CREAT|O_WRONLY|O_TRUNC, 0644); (gets fd 1, the lowest free) → char *args[] = {"sort", "data.txt", NULL}; execvp(args[0], args);. The parent shell calls wait().
