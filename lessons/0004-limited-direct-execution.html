Lesson 4 · CPU virtualization: the mechanism

Limited direct execution

Let the program run straight on the CPU, so it is fast. But put two limits on it, so the OS never loses control. That is the whole chapter. OSTEP compares it to baby-proofing a room: lock the dangerous cabinets, cover the sockets, then let the baby roam freely.

The crux How can the OS virtualize the CPU efficiently (programs run at full hardware speed) while retaining control (no program can run forever or touch what it shouldn't)?OSTEP §6 Bilal slides, Ch 6, slide 4
How many times is hi printed?
fork();
fork();
printf("hi\n");
4 times. Every process runs both forks: 1 → 2 → 4 processes, and each of the 4 prints once (22 = 4).

A child process has exited but its parent never calls wait(). What state is the child stuck in, and why does the OS keep its entry?

It is a zombie. The OS keeps its process-list entry so the parent can still collect its exit status; only the parent's wait() reaps it.

Name the three parts of a process's machine state that the OS must save to pause it and resume it later.

Memory (address space), registers (PC, SP, frame pointer, general-purpose), and I/O information (open files).

The OS shares one CPU between many processes by time sharing: run one process for a bit, then another, and so on. Two challenges come with that:

  • Performance: sharing the CPU must not slow the system down.
  • Control: the OS must stay in charge. Otherwise a process could (1) run forever, or (2) access data it has no right to.

Step 1 · Direct execution: just run it

The problem: what is the fastest way to run a program?

Just run it directly on the CPU. This is called direct execution. The OS sets things up, jumps to main(), and steps aside:

OSProgram
1. Create entry for process list
2. Allocate memory for program
3. Load program into memory
4. Set up stack with argc / argv
5. Clear registers
6. Execute call main()
7. Run main()
8. Execute return from main()
9. Free memory of process
10. Remove from process list

Direct execution with no limits.Bilal slides, Ch 6, slide 6 Between steps 6 and 9, the OS is not running at all.

It is fast. But once the program is running, the OS isn't. So who stops the program from misbehaving? Nobody. That gives two problems:

ProblemExampleFix
1. Restricted operations: how do we stop the program doing things we don't want?Reading another process's memory, or any file on diskUser / kernel modes + system calls (traps)
2. Switching between processes: how do we stop it running forever?An infinite loopTimer interrupt + context switch
Analogy (OSTEP): baby-proofing a room Parents don't follow a baby around every second. Instead they baby-proof the room first: lock the cabinets with dangerous stuff and cover the electrical sockets. Then they let the baby roam freely.OSTEP §6.5
The OS "baby-proofs" the CPU the same way:
  • Lock the cabinets = run programs in a restricted user mode, so they can't do dangerous things themselves (Problem 1).
  • Set an alarm clock = start a timer at boot, so the OS gets the CPU back every few milliseconds (Problem 2).
  • Let the baby roam = the program runs directly on the CPU at full speed.

Without these limits, OSTEP says, the OS would be "just a library": code the program happens to call, with no real authority over it.

In short: direct execution is fast, but while the program runs the OS isn't running. That leaves two problems: restricted operations (fixed by modes + system calls) and running forever (fixed by the timer interrupt + context switch).

Under plain direct execution (no limits), once the OS has called main(), when does the OS run again?

Only when main() returns. Until then the program has the CPU to itself and the OS is not running at all, so it has no control.

What are the two "limits" in limited direct execution, and what problem does each solve?

(1) User/kernel mode + system calls: stop the program doing restricted operations (raw I/O, other processes' memory). (2) Timer interrupt + context switch: stop it running forever, so the OS can switch processes.

Which is TRUE about the order of steps in plain direct execution?

  • The OS sets up the stack with argc/argv before it executes call main(). Steps 1–5 (entry, memory, load, stack, clear registers) all come before step 6, call main().
  • The OS executes call main() before it loads the program into memory. The program must be in memory first: load is step 3, call main() is step 6.
  • The program frees its own memory after it executes return from main(). Wrong actor: the OS frees the process's memory (step 9) and removes it from the process list (step 10).
  • The OS creates the process-list entry after main() returns. Creating the entry is step 1, the very first thing. After the return, the OS removes the entry.

Direct execution has two problems. Which is TRUE about how limited direct execution fixes them?

  • Restricted operations: user/kernel modes plus system calls. Running forever: the timer interrupt. Modes stop a program doing raw I/O itself (it must trap to the OS); the timer lets the OS take the CPU back.
  • Restricted operations: the timer interrupt. Running forever: user/kernel modes plus system calls. Swapped. Modes handle restricted operations; the timer handles a program that never gives up the CPU.
  • Restricted operations: user/kernel modes plus system calls. Running forever: the yield() system call. yield() is the cooperative approach, which trusts the process. An infinite loop never yields: the timer interrupt is needed.
  • Restricted operations: the OS checks every instruction in software. Running forever: the timer interrupt. That would throw away direct execution's speed. The hardware enforces it with user/kernel modes.

Problem 1 · Restricted operations

The problem: a program needs to do I/O (like reading a file), but we can't give it full control of the machine. How do we allow one without the other?

Why not just let every program do raw I/O? Because then any program could read or overwrite the entire disk, including other people's files. So the hardware helps with two modes of execution:Bilal slides, Ch 6, slide 9

User modeKernel mode
Who runs hereApplicationsThe OS (kernel)
Can doOrdinary instructions only. No I/O, no privileged instructionsAnything, including all restricted operations
If it tries something privilegedThe CPU raises an exception; the OS will likely kill the programAllowed

The mode bit is a single bit inside the CPU that says which mode it is in: user or kernel.

System calls: asking the OS nicely

So how does a user program read a file, if user mode can't do I/O? It asks the kernel to do it. That request is a system call: the kernel does a privileged job on the program's behalf. Most operating systems have hundreds of them.Bilal slides, Ch 6, slide 11

Making a system call needs two special instructions. A trap jumps into the kernel and raises the privilege to kernel mode. A return-from-trap goes back to the program and lowers the privilege to user mode.

A system call, step by step (following Dr. Bilal's slide):Bilal slides, Ch 6, slide 12

First, one new term. The kernel stack is a small stack in kernel memory, one per process. The hardware uses it to save the program's registers, so the program can be resumed later.

  1. The program puts a system-call number and the arguments in agreed places (registers or the stack). The number says which service it wants, e.g. "open a file".
  2. The program executes the trap instruction. The hardware then:
    • saves the program's registers (PC, flags, a few others) onto its kernel stack,
    • switches to kernel mode,
    • jumps into the kernel, to a handler the OS chose in advance (the trap table, below).
  3. The OS does the requested work, in kernel mode.
  4. The OS executes return-from-trap. The hardware then:
    • restores the saved registers from the kernel stack,
    • switches back to user mode,
    • continues the program right after the trap.

You never write the trap yourself. When you call open(), you call a small C-library function (a wrapper). It is hand-written in assembly to do steps 1–2 for you.OSTEP §6.2 That's why open() looks like a normal function call to your program.

The trap table: where may a trap jump to?

Why does this matter? If the program could pick where the trap jumps, it could jump into the middle of the kernel, past the permission checks. Think of a building with a reception desk: visitors can ask for room 3, but they can't walk in through any door they like.

  • At boot time, the machine starts in kernel mode. The OS then tells the hardware which code to run for each event: system call, timer interrupt, keyboard interrupt, divide-by-zero, and so on.
  • That list is the trap table. Each entry points to a trap handler: the OS code for that event.
  • Installing the trap table is itself a privileged instruction. Only the kernel can do it.
  • The hardware remembers these addresses until the next reboot.
  • A user program can only give a system-call number. The OS decided in advance where each number leads.
#System callHandler (chosen by OS at boot)
0read()read_handler()
1write()write_handler()
2open()open_handler()

Simplified trap table.Zafar slides, Ch 6, slide 10 Point to ponder from OSTEP: if you could install your own trap table, you could take over the machine.

In short: programs run in user mode and must ask the kernel for I/O with a system call. A trap saves registers to the kernel stack, switches to kernel mode and jumps to a handler from the trap table (set by the OS at boot). Return-from-trap undoes all three.

A program running in user mode tries to execute a privileged instruction (e.g. raw disk I/O). What happens?

The CPU raises an exception, which traps into the OS; the OS will likely kill the program. Only kernel mode may run privileged instructions (tracked by the mode bit).

List the three things the hardware does when a program executes the trap instruction.

(1) Save the program's registers (PC, flags…) onto its kernel stack. (2) Switch to kernel mode. (3) Jump to the trap handler the OS registered in the trap table.

Why isn't a user program allowed to choose the kernel address that its trap jumps to?

It could jump into the middle of the kernel and skip the permission checks. Instead the OS installs a trap table at boot (a privileged instruction), and the program only supplies a system-call number.

Which is TRUE about user mode and kernel mode?

  • User mode runs ordinary instructions only; kernel mode can run anything, including I/O and privileged instructions. Applications run in user mode and the OS runs in kernel mode with full access.
  • User mode can run ordinary instructions and I/O; kernel mode can run anything, including privileged instructions. User mode can't do I/O either: that's why programs need system calls.
  • User mode runs ordinary instructions only; kernel mode can run privileged instructions only. Kernel mode can run anything, ordinary instructions included.
  • User mode runs ordinary instructions only; a program enters kernel mode by setting the mode bit itself. Changing the mode is privileged. A program can only get there through a trap.

A program in user mode executes a privileged instruction. Which is TRUE?

  • The CPU raises an exception, control passes to the OS, and the OS will likely kill the program. The hardware refuses and hands control to the OS, which decides what to do (usually terminate).
  • The CPU quietly skips the instruction, and the program carries on with the next one. The CPU raises an exception; it doesn't silently ignore it.
  • The CPU switches to kernel mode and runs the instruction for the program, then returns. That would defeat the protection. The CPU raises an exception and the OS handles it.
  • The CPU raises an exception, and the hardware itself kills the program without the OS. The hardware passes control to the OS, and the OS decides to kill it.

Which is TRUE about the mode bit?

  • The CPU holds the current mode in a mode bit; a trap sets it to kernel and return-from-trap sets it to user. It flips up on the trap and back down on the return-from-trap.
  • The OS holds the current mode in the PCB; a trap sets it to kernel and return-from-trap sets it to user. The mode is kept by the CPU (hardware), in the mode bit.
  • The CPU holds the current mode in a mode bit; a trap sets it to user and return-from-trap sets it to kernel. Swapped: a trap raises privilege to kernel; return-from-trap lowers it to user.
  • The CPU holds the current mode in a mode bit; a user program can set it to kernel with an ordinary instruction. Only a trap can raise the privilege level; otherwise protection would be meaningless.

Which is TRUE about what happens when a program executes a trap?

  • The hardware saves the registers onto the kernel stack, switches to kernel mode, and jumps to the handler in the trap table. Save, raise privilege, jump: all three are done by the hardware, using addresses the OS set at boot.
  • The hardware saves the registers onto the user stack, switches to kernel mode, and jumps to the handler in the trap table. They go onto the process's kernel stack.
  • The OS saves the registers onto the kernel stack, switches to kernel mode, and jumps to the handler in the trap table. The OS isn't running yet at that moment: the hardware does all three.
  • The hardware saves the registers onto the kernel stack, stays in user mode, and jumps to the handler in the trap table. A trap raises the privilege to kernel mode; the handler runs as the kernel.

Which is TRUE about the trap table?

  • The OS installs it at boot with a privileged instruction; a user program only supplies a system-call number. The OS decides in advance where each event and system-call number leads.
  • Each program installs its own at startup with a system call; a user program only supplies a system-call number. Only the OS, at boot, installs it. A program that could install one could take over the machine.
  • The OS installs it at boot with an ordinary instruction; a user program only supplies a system-call number. Installing the trap table is a privileged instruction.
  • The OS installs it at boot with a privileged instruction; a user program supplies the handler's address. The program gives only a number; letting it choose an address would let it skip permission checks.

The LDE protocol, as a timeline

The problem: we have modes, traps and a trap table. In what order do they happen, from switching on the machine to a program exiting?

The full sequence is the limited direct execution (LDE) protocol. It has two phases:

  1. At boot: the kernel sets up the trap table.
  2. Running a process: the kernel sets up the process. Then it uses return-from-trap to start it.

Why return-from-trap to start a program? Because that one instruction already does what's needed: switch to user mode and jump into the program. The OS just pretends the process is coming back from a system call.

In short: boot = OS installs the trap table. Run = OS sets up the process and starts it with return-from-trap. Every trap and return-from-trap goes through the hardware's three steps.

In the LDE protocol, how does the OS start a user process for the very first time?

It sets up the process (process-list entry, memory, load the program, stack with argc/argv, fill the kernel stack with registers/PC) and then executes return-from-trap, as if the process were returning from a system call.

List the three things the hardware does on return-from-trap.

(1) Restore the registers from the process's kernel stack. (2) Switch to user mode. (3) Jump to the program's PC (just after the trap).

In the LDE protocol, what does the OS do in the boot phase, before any program runs?

In kernel mode, it initialises the trap table (tells the hardware the address of each handler: system calls, timer, etc.). With the timer approach it also starts the interrupt timer. Both are privileged.

Which is TRUE about return-from-trap?

  • The hardware restores the registers from the kernel stack, switches to user mode, and jumps to the program's PC. It is the mirror image of the trap: restore, lower privilege, jump back.
  • The hardware restores the registers from proc_t, switches to user mode, and jumps to the program's PC. It restores from the kernel stack. proc_t is used by the OS's switch().
  • The hardware restores the registers from the kernel stack, switches to kernel mode, and jumps to the program's PC. Return-from-trap lowers privilege to user mode.
  • The hardware restores the registers from the kernel stack, switches to user mode, and jumps to main() again. It jumps to the saved PC, just after the trap. Only the very first start lands on main().

In the LDE protocol, how does the OS start a user process for the very first time?

  • It fills the kernel stack with registers and PC, then executes return-from-trap, as if returning from a system call. Reusing return-from-trap gets the switch to user mode and the jump to main() in one step.
  • It fills the kernel stack with registers and PC, then executes a trap, as if the process made a system call. A trap goes into the kernel. To leave it and start the program, the OS uses return-from-trap.
  • It fills the user stack with registers and PC, then executes return-from-trap, as if returning from a system call. Return-from-trap restores from the kernel stack; the user stack gets argc/argv.

Problem 2 · Getting control back

The problem: how can the OS get the CPU back from a running process, so it can switch to another one?

Here is the subtle part. If a process is running on the CPU, the OS is, by definition, not running. And something that isn't running can't decide anything. OSTEP calls this the crux: "How can the operating system regain control of the CPU?" There are two approaches.Bilal slides, Ch 6, slide 14OSTEP §6.3

Approach A · Cooperative: trust the process

In the cooperative approach, the OS trusts each process to give the CPU back now and then. Older systems worked this way (early Macintosh OS, the Xerox Alto). The OS gets control back only when a process:

  • makes a system call (e.g. for I/O),
  • or calls yield(), a special system call that does nothing except hand control to the OS,
  • or does something illegal (divides by zero, touches bad memory). That causes a trap into the OS.

The catch: what if a buggy or malicious process enters an infinite loop? It never makes a system call and never makes an error. Then the OS never runs again. The only fix is to reboot the machine.

Approach B · Non-cooperative: the timer interrupt

In the non-cooperative approach, the OS doesn't trust the process at all. It uses hardware instead.

An interrupt is an event raised by a hardware device (not by the program) that makes the CPU stop and run OS code. A timer interrupt is a hardware interrupt every few milliseconds, raised by a timer device. It stops the running process, whatever it is doing. Then the OS's interrupt handler (code the OS chose in advance) runs. So the OS has control again.Bilal slides, Ch 6, slides 16–17

Setup happens at boot, just like the trap table:

  • The OS tells the hardware which code to run when the timer interrupt occurs.
  • The OS starts the timer. This is privileged too. Otherwise a program could simply switch it off.
  • When the interrupt fires, the hardware saves the running process's registers onto its kernel stack, exactly as for a trap. That way the OS can resume the process later.
Analogy Cooperative scheduling is a meeting with no chairperson: it only moves on when the speaker chooses to stop. The timer interrupt is a chairperson with a buzzer who cuts you off every 2 minutes, however interesting you think you are. In baby-proofing terms, it's the alarm clock that makes the parent check on the baby, whatever the baby is doing.

Worked example: the OS vs. while(1);

int main() {
    while (1)
        ;   // no system call, no yield(), no error, ever
}

Under the cooperative approach, this freezes the machine. Here is how the timer saves the day, step by step:

  1. At boot (kernel mode), the OS installs the trap table. It includes the address of the timer interrupt handler.
  2. Still at boot, the OS starts the hardware timer: "interrupt me every X ms". This and step 1 are privileged instructions.
  3. The OS starts the looping process with return-from-trap. It now runs in user mode, spinning forever.
  4. After X ms the timer interrupt fires. The process didn't ask for it and can't block it.
  5. The hardware saves the process's registers (PC etc.) onto its kernel stack. It switches to kernel mode and jumps to the timer handler from the trap table.
  6. The OS is running again. The scheduler (the part of the OS that picks who runs next) decides: keep running this process, or switch to another one?
  7. If it switches, the OS does a context switch (next section). Then it does a return-from-trap into a different process. The looping process is preempted: taken off the CPU without its consent. It will get another turn later, or the OS can kill it.
This is how it's asked "A process runs while(1) and never makes a system call. Explain step by step how the OS gets the CPU back." Hit these four keywords in order: timer set at boot → timer interrupt fires (user → kernel mode, jump to handler) → state saved (registers / PC onto the kernel stack) → scheduler may context switch to another process. Also mention why the cooperative approach fails here (no system call means no trap; you'd have to reboot).

In short: cooperative = the OS waits for a system call, yield() or an error, so an infinite loop means reboot. Non-cooperative = a timer interrupt, started at boot (privileged), forces control back to the OS every few ms.

Under the cooperative approach, in which ways does the OS get the CPU back from a running process?

Only when the process (1) makes a system call (including yield()), or (2) does something illegal (divide by zero, bad memory access) that traps into the OS. If it does neither, the OS never runs again.

Why must starting (and stopping) the hardware timer be a privileged operation?

Otherwise a user program could simply switch the timer off and then run forever, and the OS would never get control back.

Which is TRUE about the cooperative approach?

  • The OS regains the CPU only on a system call (including yield()) or an illegal operation; a loop with no system calls means a reboot. With no timer, a process that never traps never gives the OS a chance to run.
  • The OS regains the CPU on a system call, an illegal operation or a timer interrupt; a loop with no system calls gets preempted. The timer interrupt is the non-cooperative approach; cooperative has no timer.
  • The OS regains the CPU only on a system call (including yield()); an illegal operation is simply ignored. An illegal operation (divide by zero, bad memory) traps into the OS, which also gives it control.
  • The OS regains the CPU only on a system call or an illegal operation; a loop with no system calls is killed by the OS after a while. The OS never runs again, so it can't kill anything: the only fix is to reboot.

Which is TRUE about the timer interrupt?

  • The OS starts the timer at boot with a privileged instruction; when it fires, the OS's handler runs and the scheduler may keep the same process. The timer only guarantees the OS gets control back; whether to switch is the scheduler's choice.
  • The OS starts the timer at boot with an ordinary instruction; when it fires, the OS's handler runs and the scheduler may keep the same process. Starting the timer is privileged, otherwise a program could switch it off.
  • The OS starts the timer at boot with a privileged instruction; when it fires, the OS's handler runs and must switch to another process. The scheduler may keep running the same process; a switch isn't required.
  • The OS starts the timer at boot with a privileged instruction; when it fires, a busy process can ignore it and keep running. The interrupt can't be ignored by the process; it halts it and runs the OS's handler.

The context switch

The problem: the OS has the CPU back, and the scheduler wants to run B instead of A. How does it stop A and resume B exactly where B left off?

Think of a bookmark. Before you put down book A, you mark your page. To pick up book B, you open it at B's bookmark.

A context switch does the same with registers. It is a small piece of low-level OS code. It saves the state (the context) of the old process and restores the new one's.Bilal slides, Ch 6, slide 18 It runs only if the scheduler decides to switch. Three steps:

  1. Save the current process's registers: general-purpose registers, PC, and the kernel stack pointer.
  2. Restore the new process's saved register values.
  3. Crucially, switch the kernel stack pointer to the new process's kernel stack.

Step 3 is the clever trick. Remember: return-from-trap restores registers from whatever kernel stack is current. After step 3, that is B's stack. So when the OS executes return-from-trap, the CPU "returns" into B, not A. We entered the kernel as A and leave it as B.

Two different kinds of register save

Why are there two saves? A trap or interrupt always needs to save the program's registers, even if no switch follows. So the hardware does that one automatically. The second save only happens when the OS decides to switch.

① Implicit save (trap / interrupt)② Explicit save (context switch)
WhenEvery trap or interrupt, alwaysOnly when the scheduler decides to switch
WhatUser registers of the running processKernel registers of the process
WhoThe hardware, automaticallyThe OS, in the switch() routine
Where toThat process's kernel stackThat process's process structure (proc_t, the PCB)

OSTEP §6.3 What ② achieves: before it, the system looks "as if it just trapped into the kernel from A". After it, the system looks "as if it just trapped into the kernel from B".

What switch() looks like (xv6)

The real code is about 20 lines of x86 assembly.Bilal slides, Ch 6, slide 20 You don't need to memorise it. Just recognise its two halves: save the old registers, then load the new ones.

# void swtch(struct context **old, struct context *new);
swtch:
    # Save old registers
    movl 4(%esp), %eax    # put old ptr into eax
    popl 0(%eax)          # save the old IP
    movl %esp, 4(%eax)    # and stack
    movl %ebx, 8(%eax)    # ...and ebx, ecx, edx, esi, edi, ebp
    # Load new registers
    movl 4(%esp), %eax    # put new ptr into eax
    movl 8(%eax), %ebx    # ...restore ebp, edi, esi, edx, ecx, ebx
    movl 4(%eax), %esp    # stack is switched here  <-- the key line
    pushl 0(%eax)         # return addr put in place
    ret                   # finally return into new ctxt

In short: two saves. On every trap/interrupt, the hardware saves user registers to the kernel stack. Only on a switch, the OS's switch() saves kernel registers to proc_t, restores the new process's, and switches to its kernel stack, so return-from-trap lands in the new process.

Compare the two register saves in a context switch: who does each, which registers, and where do they go?

Implicit (every trap/interrupt): the hardware saves the user registers onto the process's kernel stack. Explicit (only when switching): the OS's switch() saves the kernel registers into the process structure (proc_t, the PCB).

A timer interrupt fires while process X runs, and the OS switches to process Y. List the four save/restore steps in order.

(1) Hardware saves X's user registers onto X's kernel stack and enters kernel mode. (2) The OS saves X's kernel registers into proc_t(X). (3) The OS restores Y's kernel registers from proc_t(Y) and switches to Y's kernel stack. (4) Return-from-trap: hardware restores Y's user registers from Y's kernel stack, goes to user mode, and jumps to Y's PC.

Which is TRUE about the context switch?

  • The OS saves the old process's registers, restores the new one's, and switches to the new process's kernel stack. Switching kernel stacks makes the next return-from-trap land in the new process.
  • The hardware saves the old process's registers, restores the new one's, and switches to the new process's kernel stack. The context switch is OS code (switch()), run after the scheduler decides to switch.
  • The OS saves the old process's registers, restores the new one's, and keeps using the old process's kernel stack. It must switch kernel stacks, or return-from-trap would resume the old process.
  • The OS saves the old process's registers, restores the new one's, and does this on every timer interrupt, even if the scheduler keeps the same process. The context switch runs only when the scheduler picks a different process; otherwise return-from-trap simply resumes the same one.

A timer interrupt leads to a switch from A to B. Which correctly describes the two register saves for A?

  • The hardware saves A's user registers onto A's kernel stack; the OS saves A's kernel registers into proc_t(A). Implicit save by hardware on the interrupt, then explicit save by switch().
  • The hardware saves A's user registers into proc_t(A); the OS saves A's kernel registers onto A's kernel stack. Places swapped: hardware uses the kernel stack, the OS uses proc_t.
  • The OS saves A's user registers onto A's kernel stack; the hardware saves A's kernel registers into proc_t(A). Actors swapped: the hardware does the first save, the OS the second.
  • The hardware saves A's user registers onto A's user stack; the OS saves A's kernel registers into proc_t(A). The hardware saves them onto A's kernel stack.

Which is TRUE about the kernel stack?

  • Each process has its own kernel stack, where the hardware saves its user registers on every trap or interrupt. One per process, which is why switching to B's kernel stack makes the CPU return into B.
  • All processes share one kernel stack, where the hardware saves their user registers on every trap or interrupt. Each process has its own kernel stack.
  • Each process has its own kernel stack, kept in user memory, where the hardware saves its user registers on every trap or interrupt. The kernel stack lives in kernel memory; if the program could reach it, it could forge its saved registers before return-from-trap.
  • Each process has its own kernel stack, where the hardware saves its user registers only during a context switch. The hardware saves them there on every trap or interrupt, switch or not.

Interrupts during interrupts

The problem: what if a timer interrupt arrives while the OS is already handling a system call or another interrupt?Bilal slides, Ch 6, slide 21

  • Simple approach: the OS disables interrupts while it handles one. Then no second interrupt is delivered in the middle.
  • The risk: disable them for too long and interrupts get lost.
  • The OS also uses locks. A lock lets only one activity at a time touch a piece of kernel data. This matters when several things happen in the kernel at once, especially on multi-core CPUs. (That's the concurrency part of the course.)

In short: disable interrupts while handling one (but not for too long, or interrupts get lost), and use locks to protect kernel data, especially on multi-core CPUs.

What can the OS do when a timer interrupt arrives while it is already handling another interrupt? Name the two techniques and one risk.

(1) Disable interrupts while handling one; risk: disable them too long and interrupts get lost. (2) Use locks to protect the kernel's internal data structures (especially on multi-core CPUs).

A timer interrupt arrives while the OS is already handling another interrupt. Which is TRUE?

  • The OS can disable interrupts while it handles one, but if it keeps them off too long, interrupts can be lost. OSTEP: disabling interrupts during interrupt processing means no other one is delivered, but doing it for too long "could lead to lost interrupts".
  • The OS can disable interrupts while it handles one, and it can keep them off as long as it likes at no cost. Not free: keep them off too long and interrupts get lost.
  • The user program can disable interrupts while the OS handles one, but if it keeps them off too long, interrupts can be lost. Wrong actor: turning interrupts off is privileged, so only the OS (in kernel mode) can do it.
  • The OS can disable interrupts while it handles one, and on multi-core CPUs that alone protects all kernel data. Multi-core is exactly where the OS also needs locks to protect its internal data structures.

Which is TRUE about the locks the OS uses inside the kernel?

  • They protect the kernel's internal data structures when several things run in the kernel at once, especially on multi-core CPUs. Several activities can be in the kernel at the same time; locks stop them corrupting shared kernel data.
  • They protect each user program's private variables when several things run in the kernel at once, especially on multi-core CPUs. They protect the kernel's internal data structures, not a program's own variables.
  • They protect the kernel's internal data structures when several things run in the kernel at once, especially on single-core CPUs. The slides and OSTEP single out multi-core CPUs (multiprocessors), where kernel code really runs in parallel.
  • They protect the kernel's internal data structures when several things run in the kernel at once, and are simple and bug-free. OSTEP warns the opposite: locking "can be complicated and lead to a variety of interesting and hard-to-find bugs".

Practice

Answer from memory first, then check.

1. What does the trap instruction do, in hardware?

A trap does two things at once: jumps into the kernel (to a handler registered in the trap table) and raises the privilege level to kernel mode. It also saves registers to the kernel stack. The program never chooses the address.

2. Who installs the trap table, and when?

At boot, in kernel mode, the OS tells the hardware where its handlers are. Doing so is privileged; if a user program could install a trap table, it could take over the machine.

3. Under a purely cooperative scheduler, a process enters an infinite loop with no system calls. What can the OS do?

With no system call, no illegal operation and no timer, the OS never runs again, so it can't do anything. Reboot is the only option. That is exactly why the timer interrupt was invented.

4. When the timer interrupt fires while process A runs, where are A's user registers saved, and by whom?

The implicit save: hardware pushes A's user registers onto A's kernel stack. Only if the scheduler then decides to switch does the OS explicitly save A's kernel registers into proc_t(A).

5. During a context switch from A to B, which step makes the final return-from-trap land in B instead of A?

Return-from-trap restores registers from the current kernel stack. Once switch() points the stack pointer at k-stack(B), the hardware restores B's registers and jumps to B's PC.

6. A program calls read() once, and no interrupt happens meanwhile. How many times does the CPU's mode bit change?

Twice: user → kernel on the trap, then kernel → user on return-from-trap.
7. A process runs for(;;) { x = x * 2; } forever and never makes a system call. Explain step by step how the OS still gets the CPU back.
(1) At boot, the OS registered a timer-interrupt handler in the trap table and started the hardware timer (privileged operations). (2) The process runs in user mode. (3) After X ms the timer raises an interrupt that the process can't ignore. (4) Hardware saves the process's registers/PC to its kernel stack, switches to kernel mode and jumps to the OS's timer handler. (5) The OS scheduler decides whether to continue this process or switch. (6) If switching, the OS context-switches (saves its kernel registers into its proc struct, restores another process's, switches kernel stack) and return-from-trap runs the other process. A cooperative OS would have to be rebooted here.
8. Name the two problems with plain direct execution and the mechanism that fixes each.
Restricted operations (a program could do I/O or touch other memory): fixed by user/kernel mode plus system calls via trap / return-from-trap and a trap table. Switching between processes (a program could run forever): fixed by the timer interrupt plus the context switch.
