Lesson 5 · CPU virtualization: the policy

Scheduling basics: FIFO, SJF, STCF, RR

Lesson 4 showed how the OS gets the CPU back. Now: once it has the CPU, who should run next? Four simple policies, two metrics, and one trade-off you can't escape.

The plan of the chapter Start with an unrealistic, simplified workload. Invent the best policy for it. Then relax one assumption at a time and watch that policy break, which motivates the next one.OSTEP §7

A process runs while(1); and never makes a system call. Step by step, how does the OS get the CPU back? (Lesson 4)

Timer interrupt. (1) At boot the OS installs the trap table and starts the timer (both privileged). (2) After X ms the timer fires. (3) The hardware saves the process's registers onto its kernel stack, switches to kernel mode and jumps to the OS's timer handler. (4) The scheduler may now do a context switch and return-from-trap into another process. With only the cooperative approach (system calls / yield()) you would have to reboot.

What three things does the hardware do on a trap, and what three on return-from-trap? (Lesson 4)

Trap: save regs → kernel stack · move to kernel mode · jump to the trap handler.
Return-from-trap: restore regs ← kernel stack · move to user mode · jump to the program's PC (just after the trap).

A process is Blocked waiting for a disk read. The read finishes. Which state does it move to, and why not straight to Running? (Lesson 2)

It moves to Ready. There is no Blocked → Running arrow: the I/O-done event only makes it able to run, and it must wait until the scheduler picks it.

In the scheduling chapter, which new policy is invented when we relax (a) "all jobs have the same length", (b) "all jobs arrive together", (c) "run-times are known"?

(a) FIFO suffers the convoy effect → SJF. (b) SJF can't stop a long job that started first → STCF (add preemption). (c) SJF/STCF need an oracle → MLFQ.

Which is TRUE about relaxing the workload assumptions (in words, so the numbering doesn't matter)?

  • Relaxing "all jobs arrive at the same time" breaks SJF, so we invent STCF. A long job that arrives first can't be stopped by non-preemptive SJF, so STCF adds preemption.
  • Relaxing "all jobs arrive at the same time" breaks FIFO, so we invent SJF. That is the "same length" assumption: FIFO's convoy effect led to SJF.
  • Relaxing "the run-time is known" breaks SJF, so we invent STCF. STCF needs run-times too. Unknown run-times lead to MLFQ.
  • Relaxing "all jobs arrive at the same time" breaks STCF, so we invent Round Robin. RR came from a new metric (response time), not from a relaxed assumption. Late arrivals broke SJF, fixed by STCF.

Which is TRUE about the assumption "the run-time of each job is known"?

  • SJF and STCF both depend on it; a real OS doesn't know run-times, which is why MLFQ learns from the past. Both must compare job lengths (SJF by burst, STCF by time left), so both need an oracle.
  • SJF and RR both depend on it; a real OS doesn't know run-times, which is why MLFQ learns from the past. RR just cycles with a fixed slice and needs no run-times. The two that need them are SJF and STCF.
  • SJF depends on it but STCF doesn't; a real OS doesn't know run-times, which is why MLFQ learns from the past. STCF compares remaining times, so it needs the run-times as well.
  • SJF and STCF both depend on it; a real OS reads run-times from the program file, so MLFQ isn't needed. No such field exists: the OS has no oracle, so MLFQ predicts from past behaviour.

Two metrics

MetricFormulaMeasures
Turnaround timeTturnaround = Tcompletion − TarrivalPerformance: how long from arriving to being completely done
Response timeTresponse = Tfirst run − TarrivalInteractivity: how long until the job first gets the CPU

A third goal, fairness, is often at odds with performance.Bilal slides, Ch 7, slide 4 If all jobs arrive at 0, turnaround is simply the completion time.

The recipe: averages from any Gantt chart

  1. Make a table with one row per job and columns: arrival · first run · completion · T · R.
  2. Arrival: copy from the question (or the ↓ marks above the chart). Don't assume 0.
  3. First run: the left edge of the job's first block.
  4. Completion: the right edge of the job's last block. With preemption a job has several blocks, so make sure you take the last one.
  5. T = completion − arrival, R = first run − arrival, row by row.
  6. Add each column and divide by the number of jobs. Leave the answer as a fraction too (e.g. 14/3 = 4.67).
Three classic slips (1) Using the job's length instead of its completion time. (2) Forgetting to subtract the arrival time for late jobs. (3) Off-by-one on quiz charts: Dr. Bilal's quiz charts label the time slots 1, 2, 3, …, so a job filling slots 1–3 runs from 0 to 3 and completes at 3. Read the boundaries, not the slot numbers.

Tturnaround = Tcompletion − Tarrival

Which is TRUE about turnaround time?

  • Turnaround time = completion time − arrival time. It measures the whole stay, from arriving to being completely done: Tturnaround = Tcompletion − Tarrival.
  • Turnaround time = first-run time − arrival time. That is response time. Turnaround ends at completion, not at the first run.
  • Turnaround time = completion time − first-run time. It starts counting at arrival, not at the first run: time spent waiting before the first run counts too.
  • Turnaround time = completion time − burst time. You subtract the arrival time, not the job's length (burst).

A job arrives at t = 4, first gets the CPU at t = 9, and completes at t = 17. Which is TRUE?

  • Its response time is 5. Response = first run − arrival = 9 − 4 = 5.
  • Its response time is 9. You forgot to subtract the arrival: 9 − 4 = 5.
  • Its response time is 13. 17 − 4 = 13 is its turnaround time. Response uses the first run: 9 − 4 = 5.
  • Its response time is 8. 17 − 9 = 8 is the time from first run to completion, which is neither metric. Response = 9 − 4 = 5.

FIFO (First In, First Out)

Also called FCFS (First Come, First Served). Run jobs in arrival order, each to completion. Very simple and easy to implement.

Three jobs A, B, C, each 4 s long, arrive at 0 (A just before B, just before C):

Average turnaround = (4 + 8 + 12) / 3 = 8 s. Fine.

The convoy effect

Now relax assumption 1: A needs 12 s, B and C need 3 s each.

Average turnaround = (12 + 15 + 18) / 3 = 15 s. Two short jobs are stuck behind one long one. That is the convoy effect.Bilal slides, Ch 7, slide 6

Analogy One supermarket checkout. The person in front of you has three full trolleys; you have a bottle of water. That feeling is the convoy effect.

What is the convoy effect, and which scheduling policy suffers from it most?

Short jobs get stuck waiting behind one long job, so average turnaround is terrible. It is the weakness of FIFO (and it comes back in SJF when a long job arrives first).

FIFO. Jobs A (10 s), B (2 s), C (4 s) all arrive at t = 0, in that order. Average turnaround? Average response?

Timeline: A 0–10 | B 10–12 | C 12–16.
Turnaround: (10 + 12 + 16)/3 = 38/3 ≈ 12.67.
Response: (0 + 10 + 12)/3 = 22/3 ≈ 7.33.

Which is TRUE about the convoy effect?

  • Under FIFO, short jobs queue behind one long job, so average turnaround is poor. Same total work, but the long job in front pushes every short job's completion time late. That is the convoy.
  • Under SJF, long jobs queue behind many short jobs, so average turnaround is poor. Reversed. Running short jobs first is how SJF cures the convoy. The victims are short jobs stuck behind a long one under FIFO.
  • Under RR, short jobs queue behind one long job, so average turnaround is poor. RR gives every job a slice in turn, so no job waits for a long one to finish. The convoy is a FIFO problem.
  • Under FIFO, the CPU idles while one job waits for I/O, so turnaround is poor. That is the I/O overlap problem. The convoy effect is short jobs stuck behind a long job.

FIFO. A arrives at t = 0 (burst 5), B at t = 2 (burst 3), C at t = 4 (burst 2). Which is TRUE?

  • Average turnaround is 17/3 ≈ 5.67. A 0–5, B 5–8, C 8–10. Turnaround: (5 − 0) + (8 − 2) + (10 − 4) = 5 + 6 + 6 = 17, so 17/3 ≈ 5.67.
  • Average turnaround is 23/3 ≈ 7.67. That averages the completion times (5 + 8 + 10) and forgets to subtract the arrivals: (5 + 6 + 6)/3 = 17/3 ≈ 5.67.
  • Average turnaround is 10/3 ≈ 3.33. That averages the bursts (5 + 3 + 2). Turnaround = completion − arrival: (5 + 6 + 6)/3 = 17/3 ≈ 5.67.
  • Average turnaround is 7/3 ≈ 2.33. That is the average response time, (0 + 3 + 4)/3. Turnaround = (5 + 6 + 6)/3 = 17/3 ≈ 5.67.

SJF (Shortest Job First)

Run the shortest job first, then the next shortest, and so on. SJF is non-preemptive: once a job starts, it runs to completion. Same three jobs:

Average turnaround = (3 + 6 + 18) / 3 = 9 s, down from 15, with exactly the same total work. When all jobs arrive together, SJF is provably optimal for average turnaround.OSTEP §7.4

SJF breaks when jobs arrive late

Relax assumption 2. A (12 s) arrives at t = 0; B and C (3 s each) arrive at t = 2. At t = 0 only A exists, so SJF starts it, and, being non-preemptive, can't stop it:

Average turnaround = ((12 − 0) + (15 − 2) + (18 − 2)) / 3 = (12 + 13 + 16) / 3 = 41/3 ≈ 13.67 s. The convoy is back.

SJF. Jobs A (10 s), B (2 s), C (4 s) all arrive at t = 0. Give the timeline and the average turnaround.

Shortest first: B 0–2 | C 2–6 | A 6–16.
Turnaround: (2 + 6 + 16)/3 = 24/3 = 8 (FIFO gave 12.67 for the same jobs).

Why does SJF stop being optimal once jobs can arrive at different times?

SJF is non-preemptive. If a long job arrives first, SJF starts it (it's the only job) and can't stop it, so short jobs that arrive a moment later wait behind it. The convoy is back.

Which is TRUE about SJF?

  • SJF is non-preemptive: once a job starts, it runs to completion even if a shorter job arrives. SJF only makes a decision when the running job finishes. Adding preemption turns it into STCF.
  • SJF is preemptive: when a shorter job arrives, it takes the CPU from the running job. That is STCF (preemptive SJF). Plain SJF is non-preemptive.
  • SJF is non-preemptive: once a job starts it runs to completion, and no run-times need to be known. SJF must know every run-time to find the shortest job (an oracle). That is why MLFQ was invented.
  • SJF re-decides at every arrival, comparing the remaining time of every job. That is STCF. SJF decides only when the running job finishes.

Which is TRUE about SJF and average turnaround?

  • When all jobs arrive together, SJF gives the lowest possible average turnaround. OSTEP: SJF is provably optimal for average turnaround if all jobs arrive at the same time.
  • When all jobs arrive together, SJF gives the lowest possible average response time. RR beats it on response (three 5-s jobs: SJF 5 s, RR with a 1-s slice 1 s). SJF's guarantee is about turnaround.
  • Even when jobs arrive at different times, SJF gives the lowest possible average turnaround. A long job that arrives first blocks later short ones and the convoy returns. With staggered arrivals, STCF is the optimal one.
  • When all jobs arrive together, SJF and FIFO always give the same average turnaround. Only if FIFO's order happens to be shortest-first. A 12, B 3, C 3 in that order: FIFO gives 15 s, SJF gives 9 s.

STCF (Shortest Time-to-Completion First)

Add preemption to SJF. Also called Preemptive SJF (PSJF). Whenever a new job enters the system, compare the remaining times of all jobs (including the one running) and run the one with the least time left.Bilal slides, Ch 7, slide 9

At t = 2, A has 10 s left but B needs only 3, so A is preempted. Average turnaround = ((18 − 0) + (5 − 2) + (8 − 2)) / 3 = (18 + 3 + 6) / 3 = 9 s. With jobs arriving at different times, STCF is optimal for average turnaround.

What are the decision points for SJF, and for STCF?

SJF: only when a job finishes. STCF: when a job finishes or a new job arrives (then compare remaining times of all jobs, including the running one).

STCF. A arrives at t = 0 (burst 6). B arrives at t = 3 (burst 4). Which is TRUE at t = 3?

  • A keeps running, because its 3 remaining units are less than B's 4. STCF compares remaining times: A has 6 − 3 = 3 left and B needs 4, so A finishes at 6 and B runs 6–10.
  • B preempts A, because B's burst of 4 is less than A's burst of 6. STCF compares remaining time, not original bursts. A has only 6 − 3 = 3 left, so it keeps the CPU.
  • B preempts A, because under STCF a newly arrived job always runs first. A newcomer runs only if it needs less time than the running job has left. Here 4 > 3, so A continues.
  • A keeps running, because STCF never preempts a job once it has started. Right outcome, wrong reason. STCF does preempt (that is what it adds to SJF); here it doesn't need to, since 3 < 4.

  2. FIFO test: each time the CPU picks a job, is it the one that arrived earliest among those waiting?
  3. SJF test: each time the CPU picks a job, is it the shortest among those waiting?
  4. STCF test: passes the SJF test, and at every arrival the newcomer is not shorter than the running job's remaining time (otherwise STCF would have preempted).
Write down every policy that passes. If two jobs arrive at the same time, FIFO's order between them is their listed order.

Contrast: with A(0, 6), B(1, 4), C(2, 2) from the worked example, FIFO gives A B C, SJF gives A C B and STCF splits A and B, so each chart identifies exactly one policy.

A (burst 3) arrives at 0, B (burst 6) at 1, C (burst 2) at 2. The CPU ran A 0–3, C 3–5, B 5–11. Which of FIFO, SJF and STCF could have produced this chart?

SJF and STCF, not FIFO. FIFO would pick B at t = 3 (it arrived before C). SJF picks C (2 < 6). STCF: at t = 1, B (6) is not shorter than A's 2 left; at t = 2, C (2) is not shorter than A's 1 left, so no preemption, and the rest matches SJF.

  • FIFO and SJF only. SJF picks the shortest waiting job at t = 4: C (3), not B (6).
  • FIFO, SJF and STCF. SJF and STCF both pick C at t = 4 (3 < 6), so the chart would show C 4–7, B 7–13.
  • SJF and STCF only. Running B before C is arrival order, which is FIFO; shortest-first would run C first.

A (burst 4) arrives at 0, B (burst 5) at 1, C (burst 1) at 2. The CPU ran A 0–4 | C 4–5 | B 5–10. Of FIFO, SJF and STCF, which could have produced this chart?

  • SJF only. At t = 4 SJF picks C (1) over B (5). STCF would have preempted A at t = 2 (C's 1 < A's 2 left), and FIFO would run B before C.
  • SJF and STCF only. At t = 2, C needs 1 and A has 4 − 2 = 2 left, so STCF preempts: A 0–2, C 2–3, A 3–5, B 5–10.
  • FIFO and SJF only. FIFO runs in arrival order: B (arrived at 1) before C (arrived at 2). Here C ran first.
  • FIFO, SJF and STCF. An unsplit chart can still rule STCF out: at t = 2, C (1) < A's 2 left, so STCF would have preempted. FIFO is out too (C ran before B).

A new metric: response time

Time-shared machines have users sitting at terminals, and they care about how quickly the system responds, not when it finishes.Bilal slides, Ch 7, slide 12 STCF and its relatives are bad at this. Three jobs A, B, C of 4 s each, all arriving at 0, under SJF:

Average response = (0 + 4 + 8) / 3 = 4 s. C waits 8 s before running a single instruction. Imagine typing and waiting 8 s for a letter to appear.

Why is SJF bad for response time? Use three 5-second jobs that all arrive at t = 0.

SJF runs them back to back: first runs at 0, 5, 10 → average response = 15/3 = 5 s. The last job waits 10 s before running anything. (RR with a 1-s slice gives (0 + 1 + 2)/3 = 1 s.)

Four jobs of 3 s each all arrive at t = 0 and run under SJF. Which is TRUE?

  • The average response time is 4.5 s. They start at 0, 3, 6, 9 → (0 + 3 + 6 + 9)/4 = 18/4 = 4.5.
  • The average response time is 7.5 s. That is the average turnaround, (3 + 6 + 9 + 12)/4. Response uses the first-run times: 18/4 = 4.5.
  • The average response time is 9 s. 9 s is only the last job's response. Average: (0 + 3 + 6 + 9)/4 = 4.5.
  • The average response time is 1.5 s. That is RR with a 1-s slice: (0 + 1 + 2 + 3)/4. SJF runs them back to back: 4.5.

Which is TRUE about response time?

  • It is first-run time − arrival time, and STCF is not particularly good at it. STCF runs short jobs to completion first, so jobs that arrive together wait a long time for their first turn.
  • It is completion time − arrival time, and STCF is not particularly good at it. Completion − arrival is turnaround. Response ends at the first run.
  • It is first-run time − arrival time, and STCF is the optimal policy for it. STCF is optimal for turnaround. For response it is poor; RR is the response-time policy.
  • It is first-run time − arrival time, and it matters most on batch systems with no users waiting. It arose with time-shared machines, where users sit at terminals waiting for the system to respond.

Round Robin (RR)

RR is time slicing: run a job for one time slice (also called a scheduling quantum), then switch to the next job in the run queue, and keep cycling until all jobs are done. The time slice must be a multiple of the timer-interrupt period (Lesson 4's timer is what makes RR possible).Bilal slides, Ch 7, slide 13

Same three 4-s jobsAvg responseAvg turnaround
SJF (= FIFO = STCF here)(0+4+8)/3 = 4(4+8+12)/3 = 8
RR, quantum 2(0+2+4)/3 = 2(8+10+12)/3 = 10
RR, quantum 1(0+1+2)/3 = 1(10+11+12)/3 = 11

RR is great for response time and terrible for turnaround: it stretches every job out as long as possible. OSTEP's general point: any fair policy (one that divides the CPU evenly over short timescales) performs poorly on turnaround. You can be fair or fast, not both.

The fundamental trade-off SJF / STCF optimise turnaround but hurt response. RR optimises response (and fairness) but hurts turnaround. Neither wins on both.

How long should the time slice be?

Every switch costs time: saving and restoring registers (Lesson 4), and also flushing CPU caches, TLBs and branch predictors, which then have to warm up again for the new job.

Amortization means paying a fixed cost less often. OSTEP's numbers: with a 10 ms slice and a 1 ms switch, roughly 10% of the time is wasted on switching. Raise the slice to 100 ms and the waste drops below 1%.OSTEP §7.7 Choosing the slice is a trade-off for the system designer: long enough to amortize switching, short enough to stay responsive.

Round Robin, time slice 2. A (3), B (5), C (2) all arrive at t = 0, in that order. Give the timeline, the average response and the average turnaround.

A 0–2 | B 2–4 | C 4–6 (done) | A 6–7 (done) | B 7–9 | B 9–10 (done).
Response: (0 + 2 + 4)/3 = 2.
Turnaround: A 7, B 10, C 6 → 23/3 ≈ 7.67.

Round Robin: what goes wrong with a very short time slice, and with a very long one?

Too short: context-switch cost dominates (saving/restoring registers, cold caches/TLB). Too long: response time gets worse and RR drifts towards FIFO. A longer slice amortizes the switch cost (pays it less often).

RR uses a 19 ms time slice and each context switch costs 1 ms. What percentage of CPU time is wasted on switching?

Each cycle = 19 + 1 = 20 ms, of which 1 ms is switching: 1/20 = 5%.

Which is TRUE about the Round Robin time slice?

  • The time slice must be a multiple of the timer-interrupt period. The OS only gets control back when the timer fires, so a slice can only end on a timer tick (10 ms timer → 10, 20, 30 ms, …).
  • The timer-interrupt period must be a multiple of the time slice. Swapped. The slice is a multiple of the timer period.
  • The time slice must be shorter than the timer-interrupt period. The OS can only switch when the timer fires, so the slice can't end between ticks. It is a whole multiple of the period.
  • The time slice can be any length, because RR doesn't rely on the timer interrupt. RR depends on the timer to take the CPU back (Lesson 4), so the slice must be a multiple of the timer period.

Which is TRUE about the trade-off between the policies?

  • RR optimises response time but hurts turnaround; SJF/STCF optimise turnaround but hurt response. That is the fundamental trade-off: neither kind of policy wins on both metrics.
  • RR optimises turnaround but hurts response; SJF/STCF optimise response but hurt turnaround. Swapped. RR is the response-time policy; SJF/STCF are the turnaround policies.
  • RR optimises both response and turnaround; only its context-switch cost holds it back. RR stretches every job out, so its turnaround is among the worst (three 4-s jobs: RR(1) 11 s vs SJF 8 s).
  • STCF optimises both turnaround and response, because it always runs the shortest job. Jobs that arrive together still wait their turn: three 4-s jobs → STCF response (0 + 4 + 8)/3 = 4 s vs RR's 1 s.

Three jobs of 6 s each arrive at t = 0. Round Robin with a 2-s slice. Which is TRUE?

  • Average response is 2 s and average turnaround is 16 s. First runs at 0, 2, 4 → 6/3 = 2. The third round ends A at 14, B at 16, C at 18 → 48/3 = 16.
  • Average response is 2 s and average turnaround is 12 s. 12 is SJF's turnaround, (6 + 12 + 18)/3. Under RR the jobs finish at 14, 16, 18 → 16.
  • Average response is 6 s and average turnaround is 16 s. 6 is SJF's response, (0 + 6 + 12)/3. Under RR they first run at 0, 2, 4 → 2.
  • Average response is 2 s and average turnaround is 18 s. 18 is when the last job finishes. The average is (14 + 16 + 18)/3 = 16.

Which is TRUE about amortizing the context-switch cost in RR?

  • A longer slice amortizes the switch cost: the same fixed cost is paid less often. With a 1 ms switch, a 10 ms slice wastes about 10% and a 100 ms slice under 1%. The price is worse response time.
  • A shorter slice amortizes the switch cost: each switch becomes cheaper. The cost of one switch doesn't depend on the slice. Amortizing means paying it less often, which needs a longer slice.
  • A longer slice amortizes the switch cost, and it also improves response time. A longer slice makes response time worse (RR drifts towards FIFO). That is the trade-off.
  • A longer slice amortizes the switch cost by making each switch faster. Each switch costs the same; it just happens less often.

Incorporating I/O

Relax the "no I/O" assumption. When a job starts an I/O request, it is blocked waiting for it to finish, so the scheduler should run another job on the CPU. When the I/O completes, an interrupt is raised and the OS moves the job from blocked back to ready.Bilal slides, Ch 7, slide 18

Example: A needs 30 ms of CPU and B needs 40 ms. A runs 10 ms, then does a 10 ms I/O, then repeats (three CPU bursts, two I/Os). B is pure CPU, no I/O. If the scheduler treats A as one indivisible job, the CPU sits idle during A's I/O:

Poor use of resources: everything done at 90 ms, with the CPU idle for 20 ms.

The fix: treat each 10 ms CPU burst of A as its own small job. With STCF, each time a 10 ms burst of A becomes ready it is shorter than what B has left, so it preempts B; while A waits for the disk, B runs:

Overlap allows better use of resources: everything done at 70 ms instead of 90, and the CPU is never idle. Interactive (I/O-heavy) jobs run often; CPU-heavy jobs soak up the gaps.

The last assumption: we don't know the run-time

SJF and STCF need to know how long each job will run, and a real OS has no oracle. The next lesson's scheduler, MLFQ, uses the recent past to predict the future.

A job starts an I/O request. Which state does it enter, what should the scheduler do, and what happens when the I/O completes?

It becomes Blocked, so the scheduler should run another job instead of idling. When the I/O finishes, an interrupt fires and the OS moves the job from Blocked back to Ready.

Interactive job A alternates 10 ms of CPU with 10 ms of I/O; job B is pure CPU. How does STCF overlap them?

Treat each 10 ms CPU burst of A as its own job. When a burst is ready it is shorter than B's remaining time, so it runs first; while A waits for the disk, B runs. The CPU never idles.

A running job issues an I/O request. Which is TRUE?

  • It becomes blocked, the scheduler runs another job, and when the I/O completes an interrupt moves it back to ready. Bilal's slide: blocked while waiting, another job gets the CPU, then interrupt → blocked to ready.
  • It becomes blocked, the scheduler runs another job, and when the I/O completes an interrupt moves it straight back to running. There is no Blocked → Running arrow. It goes to ready and waits for the scheduler.
  • It becomes ready, the scheduler runs another job, and when the I/O completes an interrupt moves it back to running. A job waiting for I/O can't use the CPU, so it is blocked, not ready.
  • It becomes blocked, the CPU waits idle until the I/O completes, and then an interrupt moves it back to ready. Idling wastes the CPU. The scheduler should run another job during the I/O.

A needs 15 ms of CPU: it runs 5 ms, does a 5 ms I/O, and repeats (three CPU bursts, two I/Os). B needs 20 ms of CPU and does no I/O. Compare running A completely first and then B, with overlapping (STCF treating each 5 ms burst of A as a job). Which is TRUE?

  • Without overlap all work is done at 45 ms; with overlap, at 35 ms. No overlap: 15 CPU + 10 idle + 20 = 45. Overlap: A 0–5, B 5–10, A 10–15, B 15–20, A 20–25, B 25–35. The CPU never idles, so 15 + 20 = 35.
  • Without overlap all work is done at 45 ms; with overlap, at 25 ms. 25 ms is when A finishes. B still has 10 ms left: it runs 25–35, so everything is done at 35.
  • Without overlap all work is done at 35 ms; with overlap, at 25 ms. Without overlap the CPU idles during A's two I/Os: 15 + 10 + 20 = 45. With overlap: 35.
  • Without overlap all work is done at 50 ms; with overlap, at 35 ms. A does only two I/Os (between its three bursts): 15 + 2 × 5 + 20 = 45.

SJF in pseudocode

If every job arrives at time 0, SJF is just "sort, then run in order":

SJF(jobs):                          # all jobs arrive at time 0
    sort jobs by burst, ascending   # ties: earlier arrival first
    time = 0
    for each job in jobs:
        job.start  = time
        time       = time + job.burst      # runs to completion
        job.finish = time
        job.turnaround = job.finish - job.arrival
        job.response   = job.start  - job.arrival

With different arrival times you can't sort once up front; pick the shortest job that has already arrived each time the CPU becomes free:

SJF(jobs):                          # general arrivals, non-preemptive
    time = 0
    while some job is unfinished:
        ready = unfinished jobs with arrival <= time
        if ready is empty:
            time = earliest arrival among unfinished jobs   # CPU idle
            continue
        job = job in ready with the smallest burst
        job.start  = time
        time       = time + job.burst      # no preemption
        job.finish = time

For STCF, change two things: choose by remaining time, and only run the chosen job until it finishes or the next job arrives, whichever comes first.

This is how it's asked "Write short pseudocode for SJF. Focus on sorting jobs by burst time and executing them in order." The first version above earns full marks. Must-haves: sort by burst ascending, a running clock, finish = clock after the burst, then turnaround and response.

SJF with different arrival times: why can't you just sort once at the start, and what do you do instead?

A short job may not have arrived yet. Each time the CPU becomes free, pick the shortest job that has already arrived; if none has arrived, jump the clock to the next arrival (the CPU idles).

All jobs arrive at t = 0. Which is the correct core of the SJF pseudocode?

  • Sort by burst ascending; then for each job: start = time, time += burst, finish = time. Record the start before the clock moves, run the whole burst (no preemption), then record the finish.
  • Sort by burst descending; then for each job: start = time, time += burst, finish = time. Shortest first means ascending. Descending runs the longest job first, the worst order.
  • Sort by burst ascending; then for each job: time += burst, start = time, finish = time. Wrong order: start must be recorded before adding the burst, or every job's start equals its finish.
  • Sort by arrival ascending; then for each job: start = time, time += burst, finish = time. Sorting by arrival is FIFO. SJF sorts by burst.

SJF with different arrival times. Which is TRUE about the general loop?

  • Each time the CPU is free, pick the shortest job that has already arrived; if none has, jump the clock to the next arrival. Only arrived jobs can run; if none is waiting, the CPU idles until the next arrival.
  • Each time the CPU is free, pick the shortest unfinished job, even if it hasn't arrived yet. A job can't run before it arrives. Pick from jobs with arrival ≤ time.
  • Each time a new job arrives, pick the shortest job that has already arrived, preempting the running job if needed. Deciding at every arrival with preemption is STCF. SJF decides only when the CPU is free.
  • Each time the CPU is free, pick the shortest job that has already arrived; if none has, end the loop. Jobs may still be on their way. Jump the clock to the earliest unfinished arrival and continue.

Matching questions Past papers ask you to match algorithms to one-line characteristics. Memorise the "Rule" row word for word: FCFS → first job to arrive is first to run; SJF → shortest burst time; STCF → preemption, least time left; RR → time slice / quantum; MLFQ (next lesson) → multiple priority queues with different time slices.

Of FIFO, SJF, STCF and Round Robin: which are preemptive, and which need to know run-times in advance?

Preemptive: STCF and RR. Need run-times: SJF and STCF. (FIFO is neither; RR is preemptive but needs no run-times.)

Give the one-line rule for each: FCFS, SJF, STCF, RR.

FCFS: first job to arrive runs first. SJF: shortest burst first, run to completion. STCF: preemption, least time left runs. RR: fixed time slice (quantum), cycle through the queue.

Which is TRUE about preemption?

  • STCF and RR are preemptive; FIFO and SJF run each job to completion. STCF preempts when a shorter job arrives; RR preempts when the slice ends. FIFO and SJF never take the CPU away.
  • SJF and RR are preemptive; FIFO and STCF run each job to completion. SJF and STCF are swapped: STCF is preemptive SJF, and plain SJF is non-preemptive.
  • Only RR is preemptive; FIFO, SJF and STCF run each job to completion. STCF is preemptive too: it switches whenever a newcomer needs less than the running job has left.
  • SJF, STCF and RR are preemptive; only FIFO runs each job to completion. SJF is non-preemptive: once a job starts, it runs to completion.
