Lesson 8 · CPU scheduling

Linux CFS: fair by the clock

Linux's Completely Fair Scheduler (CFS) drops tickets and lotteries. Each task keeps one number: its virtual runtime. The task that is furthest behind always runs next. Priorities only change how fast that number grows.

The one-sentence version CFS gives every runnable task a vruntime that grows while it runs. It always runs the task with the smallest vruntime. It finds that task fast: it is the leftmost node of a red-black tree. High-priority tasks (bigger weight) gain vruntime more slowly, so they get picked more often.Bilal slides, Ch 9BOSTEP §9.7

Stride, large number 10,000. J has 40 tickets and pass 500; K has 25 tickets and pass 400. Who runs next, what is its pass afterwards, and who runs after that? (Lesson 7)

Lowest pass is K (400). K's stride = 10,000/25 = 400, so its pass becomes 800. Next pick: J (500 < 800).

Lottery, tickets numbered from 0, list order R (30), S (20), T (50). The winning ticket is 49. Who runs? (Lesson 7)

Ranges: R 0–29, S 30–49, T 50–99 → S. (Counter walk: R 30 > 49? no; S 50 > 49? yes.)

MLFQ with slices 3 / 6 / FCFS. A long CPU-bound job is in the bottom queue when the priority boost (Rule 5) fires. What does it do next? (Lesson 6)

It moves to the top queue, runs one top slice of 3, drops and runs one middle slice of 6, then drops back to the bottom (until the next boost).

Why not just lottery or stride?

The problem: lottery and stride already share the CPU by tickets. Why did Linux build something else?

Dr. Bilal's recap gives three reasons to move on:Bilal slides, Ch 9B

  • Lottery is probabilistic. It's fair in the long run. In the short term, unlucky jobs suffer jitter (short-term unfairness).
  • Stride fixes the jitter, because it is deterministic. But it must manage global state (total tickets, pass values), and that gets complex.
  • Pass/stride values can overflow (grow too big for the variable) when tasks keep entering and leaving the system.

What we want instead:

  • short-term fairness, with no luck involved;
  • smooth handling of tasks that sleep, wake up and get created;
  • a plain time-based measure, instead of abstract tickets.

The ideal: a perfectly divisible CPU

Imagine a CPU that could run all N tasks at once, each at exactly 1/N speed. That is perfect fairness. Example: 4 tasks, each running at 1/4 speed, so in 40 ms each one gets 10 ms of work done.

A real core runs one task at a time. So CFS fakes the ideal with quick time slices. Its goal: the time each task actually gets should match what it would have got on the ideal CPU.

In short: lottery is unfair in the short term, stride's global state is complex and can overflow. CFS aims for the "ideal CPU" where N tasks each get 1/N, measured in real time, not tickets.

Give the three reasons (from Dr. Bilal's recap) for moving from lottery/stride scheduling to CFS.

(1) Lottery is probabilistic: unfair (jitter) in the short term. (2) Stride's global state (total tickets, pass values) is complex to manage. (3) Pass/stride values can overflow as tasks keep entering and leaving.

Dr. Bilal's recap explains why we move past lottery scheduling. Which is TRUE?

  • Lottery is probabilistic, so it is fair over a long run; over a short time, unlucky jobs suffer jitter (unfairness). Random draws even out only over many draws. In the short term some jobs lose more than their share: that is the jitter.
  • Lottery is probabilistic, so it is fair over a short run; over a long time, unlucky jobs suffer jitter (unfairness). Reversed. Luck evens out over many draws, so lottery is fair in the long run and unfair in the short term.
  • Stride is probabilistic, so it is fair over a long run; over a short time, unlucky jobs suffer jitter (unfairness). Wrong scheduler. Stride is deterministic (lowest pass runs), so it has no jitter; lottery is the probabilistic one.
  • Lottery is deterministic, so it is fair over a long run; over a short time, unlucky jobs suffer jitter (unfairness). A deterministic scheduler has no "unlucky" jobs. Lottery picks a random winning ticket: it is probabilistic.

CFS tries to imitate an "ideal fair CPU". Which is TRUE?

  • With N runnable tasks, all N run at once, each at exactly 1/N of the CPU's speed; CFS fakes this with quick time slices. That is the ideal (perfectly divisible) CPU. A real core runs one task at a time, so CFS switches quickly so each task's real time matches its ideal share.
  • With N runnable tasks, all N run at once, each at the CPU's full speed; CFS fakes this with quick time slices. The N tasks share one CPU, so each gets 1/N of its speed, not full speed.
  • With N runnable tasks, all N run at once, each at exactly 1/N of the CPU's speed; CFS fakes this with random ticket draws. Random draws are lottery, which CFS replaces. CFS is deterministic and uses time slices and vruntime, not tickets.
  • With N runnable tasks, all N run at once, each at exactly 1/N of the CPU's speed; CFS fakes this by running each task to completion. Running each task to the end is FIFO-like and unfair in the short term. CFS switches quickly between tasks with small time slices.

vruntime: the one rule

The problem: how does CFS know which task is "behind" and should run next?

It keeps a running clock for each task. Virtual runtime (vruntime) is how much CPU time a task has used so far (scaled by its priority, as the next section shows). It is measured in nanoseconds. It grows only while the task runs. Waiting doesn't add anything.

The golden rule Always pick the process with the smallest vruntime to run next.

So whoever has had the least CPU so far is always next in line.

Tiny example (all nice 0, so vruntime = real time): A = 6 ms, B = 4 ms. B is smaller, so B runs. B runs 3 ms, so B = 7. Now A (6) is smaller, so A runs next.

Analogy A group sharing one games console. Everyone has a timer that only ticks while they're holding the controller. Whoever's timer shows the least time gets the controller next. Nobody needs to draw lots or keep a rota. The timers sort it out.

In short: vruntime grows only while a task runs. CFS always runs the task with the smallest vruntime.

State CFS's golden rule. When does a task's vruntime grow, and in what unit?

Always run the task with the smallest vruntime. vruntime grows only while the task runs (not while it waits), measured in nanoseconds.

CFS tree holds tasks with vruntimes 12.0, 7.0, 19.5 and 7.5 ms. Which runs next, and where is it in the red-black tree?

The task with 7.0: the smallest vruntime, which is the leftmost node.

Which is TRUE about CFS's vruntime?

  • The task with the smallest vruntime runs next; vruntime grows as the task runs. Whoever has had the least (weighted) CPU time so far is next in line. Waiting in the run queue adds nothing.
  • The task with the largest vruntime runs next; vruntime grows as the task runs. The smallest vruntime runs: the task furthest behind goes next.
  • The task with the smallest vruntime runs next; vruntime also grows while it waits in the run queue. Waiting for the CPU adds no vruntime; only running does. That is how a waiting task falls behind and gets picked.
  • The task with the largest weight runs next; vruntime grows as the task runs. The pick is always the smallest vruntime. Weight only changes how fast vruntime grows.

Priorities: nice values become weights

The problem: some tasks matter more than others. How do we give them more CPU when the rule is always "smallest vruntime runs"?

Linux sets priority with a nice value, from −20 (highest priority, VIP) to +19 (lowest priority, background). The default is 0. The name makes sense if you think "a nicer process gives way to others". As the book puts it, when you're too nice, you just don't get as much attention.

CFS turns each nice value into a weight: a number that says how big the task's share is. Nice 0 has weight 1024. Each step of nice changes the weight by about 1.25×. Example: nice 0 → 1024, nice +1 → 820 (1024 ÷ 1.25 ≈ 820).Bilal slides, Ch 9BOSTEP §9.7

The bold three are the ones on the slides (−5 → 3121, 0 → 1024, +5 → 335). The others come from the full Linux table in OSTEP (Dr. Zafar's L4 quiz also used +10 → 110). Lower nice means bigger weight, which means more CPU.

Formula 1 · How fast vruntime grows

Here is the trick. CFS keeps the pick rule the same. Instead, it makes each task's clock tick at a different speed. A big weight makes the clock tick slowly, so the task stays "behind" and gets picked more.

vruntime update vruntime increase = actual runtime × (weight0 / weighti), where weight0 = 1024 (nice 0).
Big weight: the fraction is < 1, so vruntime grows slower than real time and the task stays left in the tree.
Small weight: the fraction is > 1, so vruntime grows faster and the task moves right quickly.

Tiny example first: a task with weight 2048 (twice the default) runs 10 ms. Increase = 10 × 1024/2048 = 5 ms. Its clock runs at half speed.

Now with real weights: three tasks each run for exactly 8 ms of real time.

TaskniceweightCalculationvruntime increase
Normal010248 × 1024/1024+8.00 ms
Important−1095488 × 1024/9548+0.86 ms
Background+101108 × 1024/110+74.47 ms

Same 8 ms on the CPU, three very different vruntime increases. The important task's vruntime is still small, so it gets picked again soon. The selection rule never changed. Only the speed of each task's clock did.

In short: lower nice → bigger weight (nice 0 = 1024). vruntime increase = runtime × 1024 / weight. Big weight → slow clock → picked more often.

CFS nice values: what is the range, which end is highest priority, and what is the weight of nice 0?

Write the CFS vruntime update formula. Then: a nice −5 task (weight 3121) runs 12 ms, and a nice +10 task (weight 110) runs 3 ms. How much does each vruntime grow?

Which is TRUE about Linux nice values?

  • They range from −20 to +19, and −20 is the highest priority. Lower nice = "less nice to others" = bigger weight = more CPU.
  • They range from −20 to +19, and +19 is the highest priority. +19 is the lowest priority (a "nice" process gives way). −20 is the highest.
  • They range from −20 to +19, and a higher nice value means a bigger weight. Reversed: lower nice → bigger weight (−5 → 3121, 0 → 1024, +5 → 335).
  • They range from −20 to +19, and a nice −20 task's vruntime grows fastest. Biggest weight → smallest 1024/weight → vruntime grows slowest.

  • Nice 0 has weight 1024, and each nice step changes the weight by about 2×. About 1.25× per step: 1024 → 820 (nice +1), 1024 → 1277 (nice −1).
  • Nice 0 has weight 0, so its vruntime grows at the same rate as real time. Its weight is 1024 (= weight0); that's why its vruntime matches real time: runtime × 1024/1024.
  • Nice 0 has weight 1024, and a nice +5 task has a bigger weight than that. Higher nice → smaller weight: nice +5 → 335.

Which is TRUE about a high-priority (big-weight) task in CFS?

  • Its vruntime grows more slowly than real time, so it stays left in the tree and is picked more often. Big weight → 1024/weight < 1 → slow clock → small vruntime → leftmost → runs again soon.
  • Its vruntime grows faster than real time, so it is picked more often. Big weight → 1024/weight < 1 → slower. A fast-growing vruntime would make it picked less.
  • Its vruntime grows more slowly than real time, so it drifts right in the tree. Small vruntimes stay on the left, which is where CFS picks from.
  • Its vruntime grows at real-time speed, but CFS picks big weights first. The pick rule never changes (smallest vruntime). Weight only changes the speed of the task's clock.

Formula 2 · How long each turn lasts

The problem: CFS knows who runs next. But how long should each task run before CFS checks again?

There is a trade-off. Switch very often, and things are fairer, but you waste time on context switches. Switch rarely, and you waste less time, but short-term fairness suffers. CFS controls this with two knobs:Zafar slides, CFS Deep Dive p.8–9

sched_latency (typically 48 ms)The window in which every runnable process should get to run once. It is shared out in proportion to weight.
min_granularity (typically 6 ms)The floor: no slice is shorter than this, however many processes there are. Every switch costs time, so tiny slices would be mostly overhead.

Start simple: if every task has the same weight, CFS just splits sched_latency evenly. With 4 tasks and sched_latency = 48 ms, each slice is 48 / 4 = 12 ms (OSTEP's example).OSTEP §9.7 With different weights, each task gets a piece in proportion to its weight:

Time slice time_slicei = (weighti / Σ weights) × sched_latency
If the result is below min_granularity, use min_granularity instead. Check each task's slice on its own.

Tiny example: sched_latency = 10 ms, min_granularity = 2 ms. A has weight 3072, B has 1024 (sum 4096). A = 3072/4096 × 10 = 7.5 ms. B = 1024/4096 × 10 = 2.5 ms, which is above 2, so B keeps 2.5 ms.

Worked example

sched_latency = 20 ms, min_granularity = 2 ms. Tasks: W (nice 0, weight 1024), X (nice −5, weight 3121), Y (nice +5, weight 335). All start at vruntime 0.

  1. Sum the weights: 1024 + 3121 + 335 = 4480.
  2. Slices: W = 1024/4480 × 20 = 4.57 ms. X = 3121/4480 × 20 = 13.93 ms. Y = 335/4480 × 20 = 1.50 ms, which is below the 2 ms floor, so Y gets 2 ms.
  3. vruntime after one round: W = 4.57 × 1024/1024 = 4.57. X = 13.93 × 1024/3121 = 4.57. Y = 2 × 1024/335 = 6.11.

One round in real time: X gets about 70% of the CPU because it holds about 70% of the weight. Because Y was raised to 2 ms, the round takes 20.5 ms instead of 20.

The pattern to notice W and X gained exactly the same vruntime (4.57 = 20 × 1024 / 4480), even though X ran three times longer. That is CFS in one line: fair in virtual time = proportional in real time. Only a task whose slice was raised to min_granularity gets ahead in vruntime (Y: 6.11), because it got more than its strict share.

When there are too many tasks

Why is there a floor at all? Each switch costs time. With many tasks, slices would get tiny and most of the CPU would go on switching.

Example: 10 equal tasks, sched_latency 48 ms. The formula gives 48/10 = 4.8 ms each. That is below 6 ms, so each task gets 6 ms. A full round stretches to 10 × 6 = 60 ms. CFS gives up a little responsiveness to save a lot of switching overhead.Zafar slides, CFS Deep Dive p.14–16

This is how it's asked Dr. Bilal: "Task P has weight 1024 and Q has weight W, both run X ms: calculate the vruntime increase for both, then explain using the red-black tree why Q gets more CPU in the long run." Dr. Zafar: "Given nice values and weights, sched_latency and min_granularity: (a) each time slice, (b) vruntime after one round, (c) the vruntime of a newly arrived process."
  • For (a), always check each slice against min_granularity.
  • For (b), use the raised slice for any task that was clamped.
  • For (c), the answer is min_vruntime (see below).

In short: slice = weight ÷ (sum of weights) × sched_latency, raised to min_granularity if smaller (each slice checked on its own). Unclamped tasks all gain the same vruntime per round; a clamped one gains more.

The red-black tree

The problem: CFS must find the smallest vruntime many times a second, among maybe thousands of tasks. How does it do that fast?

It keeps every runnable task in a red-black tree. That is a binary search tree that keeps itself balanced. The tree is sorted by vruntime: smaller values go left, bigger values go right. So the leftmost node is always the next task to run.Bilal slides, Ch 9B

OperationCostWhy
Pick the next taskO(1)The kernel caches a pointer to the leftmost node (Dr. Bilal's slide)
Insert a waking or preempted task, or remove a blocking oneO(log n)A balanced binary search tree has height about log₂ n
Same job with a plain sorted listO(n)Insertion has to scan the list, which doesn't scale to thousands of tasks (OSTEP)

Why not a min-heap? Two reasons. First, heaps are usually arrays, which need contiguous memory in the kernel. Second, a task can block on I/O at any moment, and then it must be removed. Removing an arbitrary task from a heap means an O(n) search. In a red-black tree it is O(log n).Bilal slides, Ch 9B

How to say the complexity OSTEP and Dr. Zafar say "red-black tree, O(log n)" to find or insert. Dr. Bilal adds that picking is O(1) thanks to the cached leftmost pointer, while insert and remove are O(log n). Writing both earns full marks with either examiner.

In short: runnable tasks sit in a red-black tree keyed by vruntime. The leftmost node runs next. Pick is O(1) with a cached pointer; insert and remove are O(log n).

What data structure does CFS keep runnable tasks in, keyed by what? Which node runs next, and what do pick and insert cost?

A red-black tree (self-balancing BST) keyed by vruntime. The leftmost node runs next. Pick: O(1) with a cached leftmost pointer (O(log n) to find without it). Insert / remove: O(log n).

Why does CFS use a red-black tree instead of a sorted list or a min-heap?

A sorted list needs an O(n) scan to insert, which doesn't scale to thousands of tasks. A heap is usually an array (needs contiguous kernel memory), and removing an arbitrary task (one that just blocked) is an O(n) search; in a red-black tree it is O(log n).

Which is TRUE about CFS's red-black tree?

  • It is keyed by vruntime, and the leftmost node is the next task to run. Smaller keys sit on the left, so the leftmost node holds the smallest vruntime.
  • It is keyed by vruntime, and the rightmost node is the next task to run. The rightmost node has the largest vruntime. CFS runs the leftmost.
  • It is keyed by weight, and the leftmost node is the next task to run. The key is vruntime. Weight only sets how fast a task's vruntime grows.
  • It is keyed by vruntime, and the root node is the next task to run. The root is just a middle value. The smallest is the leftmost node.

Which is TRUE about inserting a waking task into CFS's red-black tree of n runnable tasks?

  • It costs O(log n), because a balanced tree has height about log₂ n. Insertion walks one root-to-leaf path and rebalances; OSTEP: insertion and deletion are logarithmic.
  • It costs O(n), because the tree must be walked in order to find the spot. That is the cost for a sorted list. A balanced search tree follows one path: O(log n).
  • It costs O(1), because the kernel caches a pointer to the leftmost node. The cached pointer makes picking fast. Inserting still descends the tree: O(log n).
  • It costs O(n log n), because the whole tree is re-sorted after each insert. Nothing is re-sorted: one insert plus a local rebalance, O(log n).

New tasks and I/O sleepers: min_vruntime

The problem: a task that slept, or a brand-new task, has a much smaller vruntime than everyone else. Won't it hog the CPU?

Only runnable tasks live in the tree. A task that blocks for I/O (or sleeps) is taken out. Its vruntime stops growing, while the others keep running.OSTEP §9.7

That creates a problem. Say A runs all the time, and B goes to sleep for 10 seconds. When B wakes up, its vruntime is 10 seconds behind A's. Under the golden rule, B would monopolize the CPU for the next 10 seconds while it catches up. A would starve. A brand-new task has the same problem, because vruntime 0 is the lowest possible value.

The fix When a task is created or wakes up, CFS sets its vruntime to the minimum vruntime currently in the tree (min_vruntime). It competes fairly from now on: it isn't allowed to hog the CPU, and it doesn't wait behind everyone else either.

Using the worked example: after one round, W = 4.57, X = 4.57 and Y = 6.11. A new task Z (nice 0) arrives. CFS sets Z's vruntime = min_vruntime = 4.57.

The cost (OSTEP): a task that sleeps for short periods very often may never get its full fair share, because it keeps being reset to the minimum. Compare stride scheduling, where a new job at pass 0 monopolizes the CPU (previous lesson). CFS's fix is the one suggested there: start at the current minimum.

In short: a new or waking task gets min_vruntime, the smallest vruntime in the tree. Not 0 (it would hog the CPU) and not the maximum (it would be punished).

A CFS task wakes up after sleeping on I/O for 5 seconds. What vruntime does it get, and why not keep its old one?

It gets min_vruntime, the smallest vruntime currently in the tree. Its old value is 5 s behind everyone, so it would monopolise the CPU while catching up and starve the others.

The CFS tree holds vruntimes 31.2, 28.5 and 40.0 ms. A brand-new task is created. What vruntime does it start with? What is the downside of this policy?

28.5 (min_vruntime). Downside (OSTEP): a task that sleeps for short periods very often keeps being reset to the minimum and may not get its full fair share.

The CFS tree holds tasks with vruntimes 14.2, 9.6 and 22.0 ms. A brand-new task is created. Which is TRUE?

  • It starts at 9.6, the current min_vruntime. New and waking tasks get the smallest vruntime in the tree, so they compete fairly from now on.
  • It starts at 0, the lowest possible vruntime. At 0 it would be far behind everyone and monopolize the CPU while catching up. CFS uses min_vruntime: 9.6.
  • It starts at about 15.27, the average vruntime in the tree. CFS uses the minimum, not the average: 9.6.
  • It starts at 22.0, the largest vruntime, so it waits its turn. That would put it behind everyone. CFS uses the minimum: 9.6.

Which is TRUE about how each scheduler chooses the next job?

  • Lottery draws a random winning ticket, stride runs the job with the lowest pass, and CFS runs the task with the lowest vruntime. Matches the table: random ticket / lowest pass / lowest vruntime (the leftmost node of the red-black tree).
  • Lottery draws a random winning ticket, stride runs the job with the lowest stride, and CFS runs the task with the lowest vruntime. The stride is a fixed step (BIG / tickets). Stride picks the lowest pass, the running total of strides.
  • Lottery draws a random winning ticket, stride runs the job with the highest pass, and CFS runs the task with the lowest vruntime. Reversed. The job that has run least (relative to its tickets) has the lowest pass, and that one runs.
  • Lottery runs the job holding the most tickets, stride runs the job with the lowest pass, and CFS runs the task with the lowest vruntime. That would let the biggest ticket-holder run every time. Lottery draws a random ticket; more tickets only raise the chance of winning.

Which is TRUE about what each scheduler updates after a job runs?

  • Lottery updates nothing; stride adds BIG / tickets to the job's pass; CFS adds runtime × 1024 / weight to its vruntime. Matches the table. Lottery just draws again; stride's step shrinks with more tickets; CFS's vruntime grows more slowly for bigger weights.
  • Lottery updates nothing; stride adds BIG × tickets to the job's pass; CFS adds runtime × 1024 / weight to its vruntime. The stride is BIG ÷ tickets. More tickets must mean a smaller step, so the job is picked more often.
  • Lottery updates nothing; stride adds BIG / tickets to the job's pass; CFS adds runtime × weight / 1024 to its vruntime. Inverted. It is runtime × 1024 / weight, so a big-weight (high-priority) task's vruntime grows more slowly.
  • Lottery removes the winning ticket; stride adds BIG / tickets to the job's pass; CFS adds runtime × 1024 / weight to its vruntime. Lottery keeps every ticket in play; the next draw is from the same tickets. It has nothing to update.

From your lab: stride.c is half of CFS

You didn't write CFS in a lab. But the pick loop in Lab 4's stride.c already has the shape of CFS's golden rule. Rename a few things and it is the same idea.

stride.cCFS
passvruntime
stride = NUMERATOR / tickets (line 28)1024 / weight per unit of runtime: more weight → slower growth
pass += stride, one fixed step per slice (line 65)vruntime += runtime × 1024 / weight: grows by how long it actually ran

So the row "Picks: lowest pass / lowest vruntime" in the table above is literally the same loop. CFS adds three things around it:

  • A time-based charge: a task that runs half a slice is charged half.
  • Slices sized by weight, from sched_latency and min_granularity (Formula 2). stride.c gives every pick the same fixed slice.
  • A tree, so the pick doesn't scan every task.
Exam angle: if asked how CFS relates to stride, say this. Both run the task with the lowest counter and add a weighted amount after it runs. CFS charges by actual runtime, sizes each slice by weight (sched_latency, min_granularity), and keeps tasks in a red-black tree.

Rewrite stride.c's line 65 as the CFS update, for a task with weight w that just ran for ran ms.

jobs[k].vruntime += ran * 1024.0 / w;
Same shape as pass += stride, but the step depends on how long it actually ran, and it uses 1024 / weight instead of NUMERATOR / tickets.

stride.c finds the lowest pass by scanning all jobs (lines 49–55). Why doesn't Linux CFS do that, and what does it do instead?

A scan is O(n) every pick, which is too slow with thousands of tasks. CFS keeps runnable tasks in a red-black tree keyed by vruntime: the next task is the leftmost node (O(1) with a cached pointer), and insert/remove are O(log n).

If stride.c were turned into CFS, which line would become vruntime += runtime × 1024 / weight?

  • Line 65, pass += stride. It is the update after the job runs: the counter grows by a weighted amount.
  • Line 28, stride = NUMERATOR / tickets. That runs once, at the start, to set the step size. The per-slice update is line 65.
  • Line 51, the pass < comparison. That is the pick rule (lowest counter wins), not the update.
  • Line 64, remaining_time--. That tracks how much work is left. CFS's vruntime update corresponds to the pass update, line 65.

stride.c starts every job at pass 0 (line 29). Which is TRUE about doing that for a task that joins later?

  • In stride it would monopolize the CPU until it caught up; CFS avoids this by starting it at min_vruntime. Everyone else's counter is already large, so 0 is the lowest by far. CFS starts newcomers at the smallest vruntime in the tree.
  • In stride it would starve until it caught up; CFS avoids this by starting it at min_vruntime. The lowest counter runs, so a pass-0 newcomer runs every time. It hogs the CPU; it doesn't starve.
  • In stride it would monopolize the CPU until it caught up; CFS also starts it at 0. CFS sets a new task's vruntime to min_vruntime, not 0, for exactly this reason.
  • In stride it would monopolize the CPU until it caught up; CFS starts it at the largest vruntime. That would make it wait behind everyone. CFS uses the minimum.

Practice

Answer from memory first, then check. Struggling a little is what makes it stick.

1. A task with nice +5 (weight 335) runs for 6 ms. By how much does its vruntime increase (in ms)?

6 × (1024 / 335) = 6 × 3.057 = 18.34 ms. Its clock runs about 3× faster than real time because its weight is about 1/3 of the default.

2. sched_latency = 36 ms, min_granularity = 4 ms. Tasks: P (nice 0, 1024), Q (nice −5, 3121), R (nice +10, 110). What is Q's time slice (in ms)?

Σ = 1024 + 3121 + 110 = 4255. Q = 3121 / 4255 × 36 = 26.41 ms. That is above 4 ms, so it isn't clamped.

3. Same setup as Q2. All start at vruntime 0. What is R's vruntime after one round?

R's formula slice = 110 / 4255 × 36 = 0.93 ms, which is below the 4 ms floor, so R runs 4 ms. vruntime = 4 × 1024 / 110 = 37.24. (P and Q both end at 8.66, the "fair" amount, and R is ahead because it was given extra time.)

4. Same setup, after that first round. A new task S (nice 0) is created. What vruntime does CFS give it?

New tasks get min_vruntime, the smallest vruntime in the tree. After one round P = 8.66, Q = 26.41 × 1024/3121 = 8.66, and R = 37.24. Minimum = 8.66. Starting at 0 would let S monopolize the CPU.

5. 16 runnable tasks, all nice 0, with sched_latency = 48 ms and min_granularity = 6 ms. How long (in ms) is one full round in which every task runs once?

48 / 16 = 3 ms, which is below the 6 ms floor, so each task gets 6 ms. The round = 16 × 6 = 96 ms, not 48.

6. Tasks H (weight 4096) and L (weight 1024) each run 10 ms. Why does H end up with more CPU time over many rounds?

H gains 10 × 1024/4096 = 2.5 ms of vruntime and L gains 10 ms. H's smaller vruntime keeps it at the left of the red-black tree, and CFS always runs the leftmost (smallest vruntime) node, so H is picked more often.

7. A task has been blocked on disk I/O for a long time and now wakes up. What does CFS do with its vruntime?

If it kept its old, much smaller value, it would monopolize the CPU while catching up. Zero is even worse. The maximum would punish it for sleeping. CFS uses min_vruntime.
8. Write the two CFS formulas and the selection rule, and say what data structure CFS uses and its cost.
time_slicei = (weighti / Σ weight) × sched_latency, but at least min_granularity.
vruntimei += runtime × (1024 / weighti) (1024 = weight of nice 0).
Rule: always run the task with the smallest vruntime. The runnable tasks are kept in a red-black tree keyed by vruntime, and the leftmost node is the next to run. Picking is O(1) with a cached leftmost pointer, and insert/remove is O(log n). New and waking tasks get min_vruntime.
