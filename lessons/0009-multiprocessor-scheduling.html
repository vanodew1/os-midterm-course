Lesson 9 · CPU virtualization, the last piece

Scheduling on many CPUs

Every policy so far assumed one CPU. Put two or more cores on a chip and three new problems show up: caches that disagree, shared queues that need locks, and jobs that run faster if they stay where they were.

The one-sentence version A multiprocessor scheduler must pick between one shared queue (SQMS: simple, but needs a lock and moves jobs around) and one queue per CPU (MQMS: scalable and cache-friendly, but the queues can become unbalanced, so jobs have to be migrated).OSTEP §10

CFS: a nice 0 task (weight 1024) and a nice +5 task (weight 335) each run for 4 ms, starting from the same vruntime. How much does each vruntime grow, and who is picked next? (Lesson 8)

nice 0: 4 × 1024/1024 = 4.00 ms. nice +5: 4 × 1024/335 = 4096/335 ≈ 12.23 ms. The nice 0 task now has the smaller vruntime, so it runs next.

CFS: a brand-new task is created. What vruntime does it get, and why not 0? (Lesson 8)

It gets min_vruntime (the smallest vruntime in the tree). At 0 it would be far behind everyone and monopolise the CPU until it caught up.

Stride, large number 6,000. X has 30 tickets, Y has 20 (X listed first, ties to X). Give the first 5 picks. (Lesson 7)

Strides: X 200, Y 300. (0,0) X → (200,0) Y → (200,300) X → (400,300) Y → (400,600) X.
Picks: X Y X Y X, i.e. 3 : 2 = 30 : 20.

Why bother? A multicore chip packs several CPU cores onto one chip. But adding CPUs does not make a single ordinary program faster. To use more cores, a program has to be rewritten to run in parallel, using threads. The OS's job is to place all those runnable jobs onto the cores well.Bilal slides, Ch 10 p.2

Background · caches

A cache is a small, fast memory that holds copies of popular data from the big, slow main memory. If the data is already in the cache (a hit), the CPU gets it quickly. Caches work because programs have locality:

Temporal localityData used once is likely to be used again soon (e.g. a loop counter).
Spatial localityData near something just used is likely to be used next (e.g. walking through an array).

By keeping data in the cache, the system makes slow memory look fast. On one CPU this is simple. With several CPUs, each CPU has its own private cache, but they all share one main memory. That's where the trouble starts.

Problem 1 · Cache coherence

Follow address 1, which holds value D:Bilal slides, Ch 10 pp.6–7

Cache coherence means keeping the copies of shared data in several caches consistent. The hardware fixes it with bus snooping: every cache watches ("snoops on") the shared bus. When it sees another CPU write to an address it holds, it either invalidates its copy (throws it away) or updates it.Bilal slides, Ch 10 p.8 This all happens in hardware, invisible to the OS and to your code.

Problem 2 · Synchronization

Coherence keeps single values consistent, but it does not make multi-step updates safe. When code on several CPUs touches a shared data structure, you still need locks (mutual exclusion). Here's the slides' list-pop routine:Bilal slides, Ch 10 pp.9–10

int List_Pop() {
    lock(&m);
    Node_t *tmp = head;        // remember old head
    int value = head->value;   // ... and its value
    head = head->next;         // advance head
    free(tmp);                 // free old head
    unlock(&m);
    return value;
}

Without the lock, thread 1 on CPU 0 and thread 2 on CPU 1 can both run tmp = head at the same instant. Both grab the same node, both return the same value, and both call free(tmp) on it, which is a double free (Lesson 11 shows why that crashes). On one CPU this race needed an unlucky interrupt; on many CPUs it's real parallelism, so it happens far more easily.

The catch: locks cost time. As the number of CPUs grows, they spend more and more time waiting for the same lock. Keep that in mind; it's SQMS's first weakness.

Problem 3 · Cache affinity

While a process runs on a CPU, it fills that CPU's cache (and TLB) with its data. If it runs on the same CPU next time, much of that state is still there ("warm"), so it runs faster. If it moves to a different CPU, it starts "cold" and must reload everything.Bilal slides, Ch 10 p.12

Rule Cache affinity: keep a process on the same CPU whenever possible. A multiprocessor scheduler should take cache affinity into account when it decides where to run a job.
Analogy A cook who always works at the same station knows where every pan and spice is (warm cache). Move them to a new station each hour and they waste time hunting for things (cold cache), even though they're just as skilled.

So the three challenges the slides list are: synchronization (protect shared structures with locks), cache affinity (reuse warm caches), and load balancing (keep all CPUs evenly busy).Bilal slides, Ch 10 p.4 Now let's build schedulers.

Define temporal locality and spatial locality, with an example of each.

Temporal: data used once is likely to be used again soon (a loop counter). Spatial: data near something just used is likely to be used next (walking through an array).

On a multiprocessor, what is the cache coherence problem, and how does the hardware solve it?

Each CPU has a private cache but memory is shared. CPU 0 updates a value only in its own cache; CPU 1 then reads the old (stale) value. Fix: bus snooping: each cache watches the shared bus and invalidates or updates its copy when another CPU writes that address. Done in hardware.

What is cache affinity, and why should a multiprocessor scheduler care about it?

A process runs faster on the same CPU it ran on last time, because that CPU's cache (and TLB) still holds its data ("warm"). Moving it to another CPU means starting cold. So the scheduler should keep a process on the same CPU whenever possible.

Which is TRUE about temporal locality?

  • Data used once is likely to be used again soon, like a loop counter. Temporal = the same data again, soon. Caches keep it, so the second use is a hit.
  • Data near something just used is likely to be used next, like an array walk. That is spatial locality. Temporal is about the same data used again soon.
  • Data used once is unlikely to be needed again soon, so caches evict it. Reversed. Caches work because recently used data is likely to be used again.
  • A process that ran on a CPU is likely to run on that same CPU again soon. That describes cache affinity, a scheduling goal. Temporal locality is about a program reusing data.

A loop adds a[0], a[1], a[2], … into a variable sum. Which is TRUE?

  • Reading a[i+1] just after a[i] is spatial locality; reusing sum every pass is temporal. Neighbouring addresses = spatial; the same variable again soon = temporal.
  • Reading a[i+1] just after a[i] is temporal locality; reusing sum every pass is spatial. Swapped. Neighbours = spatial; same data again = temporal.
  • Both are spatial locality, because all the data sits next to each other in memory. sum is not a neighbour being read; it is the same variable reused: temporal.
  • Both are temporal locality, because the loop repeats the same steps. Each array element is read only once; what helps is that it is next to the previous one: spatial.

Which is TRUE about cache coherence on a multiprocessor?

  • Bus snooping, done in hardware, makes caches invalidate or update their copy when another CPU writes it. Each cache watches the shared bus; on seeing a write to an address it holds, it invalidates or updates its copy.
  • Bus snooping, done by the OS scheduler, makes caches invalidate or update their copy when another CPU writes it. Snooping is done by the hardware, invisible to the OS and to your code.
  • Bus snooping, done in hardware, also makes multi-step updates like List_Pop() safe without locks. Coherence keeps single values consistent. A multi-step update still needs a lock, or two CPUs can pop and free the same node.
  • Coherence is not an issue, because all the CPUs share one cache. Each CPU has its own private cache over a shared memory; that is exactly why stale copies appear.

Which is TRUE about cache affinity?

  • A process runs faster if it runs again on the same CPU, whose cache still holds its state. Its data is still warm in that CPU's cache (and TLB), so keep a process on the same CPU whenever possible.
  • A process runs faster if it moves to a different CPU, whose cache has free room. A different CPU's cache is cold for it, so it must reload everything. Stay on the same CPU.
  • A process should go to whichever CPU has the fewest jobs; that is what affinity means. That is load balancing. Affinity = keep a process on the same CPU when possible.
  • A process runs faster on the same CPU because only that CPU can reach its memory. All CPUs share main memory. The gain comes from the warm cache (and TLB).

Approach 1 · Single-queue (SQMS)

Single-Queue Multiprocessor Scheduling (SQMS) reuses whatever single-CPU policy you already have (RR, MLFQ…). It's very simple. But it has two problems:Bilal slides, Ch 10 p.13

  1. Lack of scalability (lock contention). Every CPU must take the same lock to touch the queue. With more CPUs, more of them sit waiting for that one lock, and the scheduler itself becomes the bottleneck.
  2. Poor cache affinity. Each CPU just grabs the next job, so jobs bounce from CPU to CPU, starting cold every time.

Here's what problem 2 looks like with five jobs on four CPUs. Each time slice, every CPU takes the next job from the shared queue:

Follow job A (blue): CPU 0 → CPU 1 → CPU 2 → CPU 3 → CPU 0… It never runs on the same CPU twice in a row, so it never benefits from a warm cache. Every job does the same.

The fix: an affinity mechanism

Most SQMS schedulers add an affinity mechanism: try to keep each job on the same CPU, and move only a few jobs to balance the load.Bilal slides, Ch 10 p.14

A, B, C and D now stay on their own CPUs (warm caches). Only E (pink) migrates from CPU to CPU, filling in the gaps. You could pick a different job to migrate next time, to be fair. Downside: implementing this is complex, and it still doesn't fix the lock problem.

What are the two problems of single-queue multiprocessor scheduling (SQMS)?

(1) Lack of scalability: every CPU needs the same queue lock, so lock contention grows with the number of CPUs. (2) Poor cache affinity: jobs bounce from CPU to CPU and start cold.

What does an affinity mechanism add to SQMS, and what are its drawbacks?

It tries to keep most jobs on the same CPU and migrates only a few to balance load (e.g. one job moves around filling gaps). Drawbacks: it is complex to implement and still has the single lock.

Why does single-queue multiprocessor scheduling (SQMS) scale poorly? Which is TRUE?

  • Every CPU must take the same queue lock, so lock contention grows as CPUs are added. More CPUs means more of them waiting for the one lock, until the scheduler itself is the bottleneck.
  • Each CPU's queue can become unbalanced, so some CPUs sit idle. That is MQMS's problem. SQMS has one queue, so load balances naturally; its problem is the shared lock.
  • Jobs never move between CPUs, so busy CPUs can't share their work. Opposite: in SQMS jobs move constantly (poor affinity). Scalability suffers from lock contention.
  • Every CPU must take the same queue lock, so cache coherence breaks as CPUs are added. Coherence is kept by hardware snooping. The cost is CPUs waiting for the lock.

SQMS with five jobs A–E on four CPUs: every time slice, each CPU takes the next job from the shared queue. Which is TRUE about job A?

  • A lands on a different CPU every time, so it keeps starting with a cold cache. A goes CPU 0 → 1 → 2 → 3 → … and never reuses a warm cache. That is SQMS's poor cache affinity.
  • A stays on CPU 0, because SQMS keeps each job on the CPU it started on. Plain SQMS has no such rule; A bounces CPU 0 → 1 → 2 → 3. Keeping jobs in place needs an extra affinity mechanism.
  • A lands on a different CPU every time, which keeps its cache warm on all four. Other jobs fill each cache in between, so A starts cold each time.
  • A lands on a different CPU every time, but that costs only lock time, not cache warmth. Moving costs cache warmth (affinity). Lock contention is SQMS's other, separate problem.

Approach 2 · Multi-queue (MQMS)

Multi-Queue Multiprocessor Scheduling (MQMS) gives every CPU its own queue.Bilal slides, Ch 10 p.15

  • Each queue follows its own scheduling discipline (e.g. round robin).
  • When a job enters the system, it's placed on exactly one queue (randomly, or on the one with the fewest jobs), and stays there.
  • Each CPU schedules its own queue independently, so there's no shared information and no global lock to fight over.

Example: two CPUs, Q0 holds A and C, Q1 holds B and D, each running RR:

A and C never leave CPU 0; B and D never leave CPU 1. Caches stay warm.

This is how it's asked: "How does MQMS fix SQMS's two problems?"

Lock contention / scalability: each CPU has its own queue with its own lock, so CPUs don't compete for one global lock. Adding CPUs adds queues, and the design scales.

Cache affinity: a job stays on the same queue, so it keeps running on the same CPU and reuses its warm cache, for free.

Then add the catch: MQMS introduces a new problem, load imbalance.

The catch · load imbalance

Suppose job C finishes. Q0 now holds only A, while Q1 still holds B and D:Bilal slides, Ch 10 p.18

A gets a whole CPU; B and D each get half a CPU. A gets twice as much CPU as B and D. Unfair.

Worse, suppose A finishes too:

CPU 0 sits idle while two jobs wait on CPU 1. Half the machine is wasted.

The fix · migration

The answer is to move jobs between CPUs, called migration. In the idle case it's easy: move B (or D) to CPU 0.

After migrating D to Q0, each CPU has one job. Balanced.

The trickier case is A alone on CPU 0 and B, D on CPU 1. Moving one job only flips the imbalance (now CPU 1 has one job and CPU 0 has two). The fix is continuous migration: keep switching which job moves.Bilal slides, Ch 10 p.21

At t=4, B migrates to CPU 0 (now A shares with B; D has CPU 1 alone). At t=8, A migrates to CPU 1. Over a long time, A, B and D each get about the same share. (This is the slides' pattern; it's one of many valid ones.)

How to decide when to migrate · work stealing

Work stealing is one common way to do the migration:Bilal slides, Ch 10 p.23

  1. A source queue that is low on jobs…
  2. …occasionally peeks at another target queue to see how full it is.
  3. If the target is (notably) more full than the source, the source steals one or more jobs from the target.
Trade-off Peek too often and you pay high overhead and trouble scaling, which is exactly the problem MQMS was built to avoid. Peek too rarely and load stays unbalanced. Real systems tune how often to look.
This is how it's asked: "Draw it with and without load balancing" You get N CPU-bound jobs placed unevenly on two queues (RR). Without balancing: each CPU round-robins only through its own queue, so the CPU with fewer jobs gives each one more time (or sits idle). With balancing: migrate jobs until the queues have as equal counts as possible, then draw each CPU round-robining its new queue. Label the lanes CPU 0 / CPU 1, use one box per time slice, and end with "…". If counts can't be equal, say "continuous migration" and show jobs swapping.

MQMS, two CPUs, round robin. Q0 holds A and B; Q1 holds C, D, E and F. Without load balancing, what fraction of a CPU does each job get? What about after balancing?

Without: A and B get 1/2 each; C, D, E, F get 1/4 each (A gets twice as much as C).
With balancing: migrate one job from Q1 to Q0 → 3 + 3, so every job gets 1/3.

Describe work stealing in three steps, and the trade-off in how often to do it.

(1) A source queue low on jobs (2) occasionally peeks at a target queue; (3) if the target is notably fuller, it steals one or more jobs. Peek too often → high overhead, trouble scaling. Too rarely → load stays imbalanced.

MQMS: CPU 0 has only job A, CPU 1 has B and D. Why doesn't migrating one job once fix this, and what does?

Moving one job just flips the imbalance (now one CPU has two jobs, the other one). The fix is continuous migration: keep switching which job moves, so over time A, B and D each get about the same share.

Which is TRUE about multi-queue multiprocessor scheduling (MQMS)?

  • It fixes SQMS's lock contention and poor cache affinity, but it can suffer load imbalance. One queue per CPU: no global lock, and jobs stay put. But one queue can end up with more jobs than another.
  • It fixes SQMS's load imbalance and poor cache affinity, but it suffers lock contention. Swapped. SQMS balances load naturally; MQMS has no global lock but can become imbalanced.
  • It fixes SQMS's lock contention, but it makes cache affinity worse. Jobs stay on their own queue, so they keep running on the same CPU: better affinity.
  • It fixes lock contention, cache affinity and load imbalance with no extra mechanism. Load imbalance is MQMS's new problem; it needs migration (e.g. work stealing).

MQMS, two CPUs, round robin, no load balancing. Q0 holds only A; Q1 holds B, C, D and E. Over a long run, which is TRUE?

  • A gets 4 times as much CPU as B. A has CPU 0 to itself (1 CPU). B shares CPU 1 with C, D and E (1/4 CPU). 1 ÷ 1/4 = 4.
  • A gets 3 times as much CPU as B. B shares CPU 1 with three others, so 4 jobs split it: B gets 1/4 and 1 ÷ 1/4 = 4.
  • Every job gets 2/5 of a CPU, because two CPUs are shared by five jobs. That would need load balancing. Without it, each CPU only round-robins its own queue: A gets 1, the others 1/4.

MQMS: CPU 0 runs only A; CPU 1 runs B and D. Which is TRUE?

  • Migrating one job once just flips the imbalance; continuous migration keeps switching which job moves. Over time A, B and D then each get about the same share of the two CPUs.
  • Migrating B to CPU 0 once fixes it, since both CPUs then have work. Then CPU 0 has A and B while D is alone on CPU 1: the same imbalance, flipped. Keep switching which job moves.
  • Nothing can help, because three jobs can't share two CPUs fairly. Over time they can: continuous migration gives A, B and D about the same share.
  • A should be pinned to CPU 0 for good, to protect its cache affinity. Then A keeps getting twice the CPU of B and D. The fix is continuous migration.

Which is TRUE about work stealing?

  • A queue that is low on jobs peeks at a fuller queue now and then, and steals jobs from it. The source (low) queue occasionally peeks at a target queue; if the target is notably fuller, it takes one or more jobs.
  • A queue that is full peeks at an emptier queue now and then, and pushes jobs onto it. In work stealing the source is the queue that is low on jobs, and it takes work from the fuller target.
  • A queue that is low on jobs peeks at the others constantly, which costs almost nothing. Peeking too often brings back the overhead and scaling trouble MQMS was built to avoid. Too rarely, and load stays unbalanced.
  • A queue that is low on jobs steals from a fuller queue, and the stolen job keeps its warm cache. The stolen job moves to a new CPU and starts cold. Stealing trades a little affinity for balance.

What Linux did

Linux never settled on one answer. Three schedulers have been used:Bilal slides, Ch 10 p.24

Both are right; write "single queue, proportional share" and mention deadlines if you have room. The key fact to remember: O(1) and CFS are multi-queue, BFS is single-queue.

Linux has used three multiprocessor schedulers. Name them and say whether each is single-queue or multi-queue.

O(1): multi-queue, priority-based (MLFQ-like). CFS: multi-queue, deterministic proportional share. BFS: single-queue, proportional share (deadline-based).

SQMS vs MQMS: which balances load naturally, and which has better scalability and cache affinity?

SQMS balances load naturally (any free CPU takes the next job). MQMS wins on scalability (no global lock) and cache affinity (jobs stay put), but can become imbalanced and needs migration.

Which is TRUE about Linux's multiprocessor schedulers?

  • O(1) and CFS use multiple queues; BFS uses a single queue. OSTEP: both O(1) and CFS use multiple queues, whereas BFS uses a single queue, showing both approaches can work.
  • O(1) and BFS use multiple queues; CFS uses a single queue. CFS is multi-queue. BFS is the single-queue one.
  • CFS and BFS use multiple queues; O(1) uses a single queue. O(1) is multi-queue. BFS is the single-queue one.
  • All three use one queue per CPU, as in MQMS. BFS is the exception: a single queue.

Practice

Answer from memory first, then check. Struggling a little is what makes it stick.

1. CPU 1 reads a stale value because CPU 0 changed it only in CPU 0's cache. What hardware technique prevents this?

This is the cache coherence problem. Each cache snoops on the shared bus; when it sees a write to an address it holds, it invalidates or updates its copy. It's done in hardware.

2. Which pair of problems does a single shared queue (SQMS) suffer from?

One shared queue needs one lock, so CPUs contend for it (not scalable), and jobs bounce between CPUs (poor affinity). Load imbalance is MQMS's problem; SQMS balances naturally.

3. A dual-core MQMS system: Q0 is empty (CPU 0 is idle) while Q1 holds three jobs. What should happen?

Q0 (the source, low on jobs) peeks at Q1 (the target), sees it's fuller, and steals a job. Losing a little cache warmth is far better than leaving a whole CPU idle.

4. MQMS, two CPUs, round robin. Q0 holds only job A. Q1 holds jobs B, C and D. With no load balancing, over a long run, how many times more CPU time does A get than B?

A gets all of CPU 0. B shares CPU 1 with C and D, so B gets 1/3 of a CPU. Ratio = 1 ÷ (1/3) = 3. That unfairness is what load imbalance means.

5. Which Linux scheduler uses a single queue rather than multiple queues?

BFS is single-queue. O(1) and CFS are both multi-queue.
6. Two CPUs, MQMS with round robin. Five CPU-bound jobs A, B, C, D, E are placed on Q0 (CPU 0) and job F on Q1 (CPU 1). Draw how they run (a) without load balancing, (b) with load balancing.

(a) Without balancing: CPU 0 cycles through five jobs, while F has CPU 1 all to itself (F gets 5× the CPU of any other job).

(b) With balancing: CPU 0's queue is fuller, so CPU 1 steals two jobs (say D and E). Now each CPU has three jobs:

Every job now gets 1/3 of a CPU. Any split of 3 + 3 is correct.

7. Explain how MQMS solves the two problems of SQMS, and name the new problem it creates.
(1) Scalability: each CPU has its own queue, so there's no single global lock for all CPUs to fight over. (2) Cache affinity: a job stays in one queue, so it keeps running on the same CPU with a warm cache. New problem: load imbalance, where one queue has more jobs than another (unfair shares, or an idle CPU). Fixed by migration, e.g. work stealing.
8. Why does List_Pop() need a lock on a multiprocessor even though the hardware keeps caches coherent?
Coherence only keeps each single memory value consistent. List_Pop does several steps (read head, read value, update head, free). Two CPUs can run those steps at the same time, both take the same node, return the same value, and free it twice. A lock makes the whole sequence mutually exclusive.
