Lesson 10 · Memory virtualization begins

The address space

We tricked every process into thinking it owns the CPU. Now we pull the same trick with memory: each process gets its own private memory that starts at 0, even though they all share one physical RAM.

The one-sentence version The address space is the running program's view of memory: its code, heap and stack laid out in a private range starting at 0. Every address the program sees is virtual; the OS and hardware translate it to a real physical address on every access.OSTEP §13

Lesson 9: Multi-queue multiprocessor scheduling (MQMS, one queue per CPU) scales well and keeps cache affinity. What problem does it create, and how is it fixed?

Load imbalance: one CPU's queue can run empty (or hold fewer jobs) while another CPU is overloaded. Fix: migration, moving jobs between queues, e.g. by work stealing (an idle-ish CPU peeks at a busier queue and takes a job).

Lesson 5: Round Robin with a time slice of 2. Jobs A, B and C all arrive at time 0 and each needs 4 units of CPU. Give the average response time and the average turnaround time.

Schedule: A 0–2, B 2–4, C 4–6, A 6–8, B 8–10, C 10–12.
Response = first run − arrival: A 0, B 2, C 4, so average 2.
Turnaround = finish − arrival: A 8, B 10, C 12, so average 10. RR is great for response time, poor for turnaround.

A short history

Early systems: one program

Early machines barely needed an abstraction. The OS was just a set of routines (a library) sitting in memory starting at address 0, and one running program used all the rest.Bilal slides, Ch 13 p.3 No sharing, so no protection was needed.

Multiprogramming and time sharing

Computers were expensive, so people wanted to share them:

  • Multiprogramming: keep several processes ready to run, and switch to another when one waits (e.g. for I/O). Goal: better CPU utilization and efficiency.
  • Time sharing: many users at terminals, each wanting a quick, interactive response. It made computing more accessible.

One crude way to time-share: run a program with all of memory, then save its entire memory to disk and load the next one. That's far too slow (disk is slow). Instead, the OS leaves several processes in memory at once and switches between them quickly:OSTEP Fig 13.2

The new problem With several programs in memory at once, nothing stops Process A from reading or overwriting Process B's data, or even the OS itself. Protection becomes essential.Bilal slides, Ch 13 p.6

Why don't we time-share memory by saving a program's whole memory to disk and loading the next one on every switch? What does the OS do instead, and what new problem does that create?

Disk is far too slow for that. Instead the OS leaves several processes in memory at once and switches between them quickly. New problem: one process could read or overwrite another's memory (or the OS's), so protection becomes essential.

In one line each: what is the goal of multiprogramming, and what is the goal of time sharing?

Multiprogramming: keep several processes ready so the CPU switches to another when one waits for I/O, for better CPU utilization.
Time sharing: many users at once, each getting a quick interactive response.

Which statement about memory in early systems (before multiprogramming) is TRUE?

  • The OS was a library of routines in memory, one running program used the rest, and the program saw physical memory directly. OSTEP 13.1: early machines gave users little abstraction. With only one program and no sharing, there was nothing to protect it from.
  • The OS was a library of routines in memory, several programs shared the rest, and each program saw physical memory directly. Wrong era. Several programs in memory at once is multiprogramming, which came later. Early systems ran one program.
  • The OS was a library of routines in memory, one running program used the rest, and the program saw a virtual address space starting at 0. The virtual address space is the later abstraction. Early machines had no such illusion: the program used physical memory directly.
  • The OS was a library of routines in memory, one running program used the rest, and its memory was saved to disk on every switch. Saving all of memory to disk on each switch was the crude time-sharing idea, which came later (and was too slow). Early systems ran one program with no switching.

Which statement about multiprogramming is TRUE?

  • Several processes are ready at once, and the OS switches when one does I/O, to raise CPU utilization; it came before time sharing. OSTEP 13.2: machines were expensive, so keeping the CPU busy during I/O mattered. Time sharing (interactivity) came after.
  • Several processes are ready at once, and the OS switches when one does I/O, to give users an interactive response; it came before time sharing. Wrong goal. Quick interactive response is the goal of time sharing; multiprogramming's goal is better CPU utilization.
  • Several processes are ready at once, and the OS switches only when one finishes, to raise CPU utilization; it came before time sharing. Wrong trigger. The OS switches when a process waits (e.g. for I/O), so the CPU isn't left idle.
  • Several processes are ready at once, and the OS switches when one does I/O, to raise CPU utilization; it came after time sharing. Wrong order. Multiprogramming came first; people then demanded more, and time sharing followed.

The abstraction: the address space

To make shared memory easy and safe, the OS creates an abstraction called the address space: the running program's view of memory. The OS virtualizes memory so that every program believes it has its own private memory, starting at address 0.Bilal slides, Ch 13 p.11

An address space holds everything about the running program's memory, in three main pieces:

RegionHoldsSize over timePlaced
Code (text segment)The program's instructionsStatic: fixed, doesn't change while runningAt the start (address 0), since it never needs to grow
HeapDynamically-allocated, user-managed memory (malloc() in C, new in C++/Java)Grows and shrinks as you allocate and freeJust after the code, growing toward higher addresses
StackLocal variables, function parameters, return addressesGrows on every call, shrinks on every returnAt the far end, growing toward lower addresses

Because the two growing regions start at opposite ends and grow toward each other, they share the free space in the middle, and neither runs out until the whole gap is used. (This is a convention; with several threads, for example, there are several stacks.)OSTEP §13.3

Drawing convention: Bilal vs Zafar Dr. Bilal's slides (and OSTEP) draw 0KB at the top: code, then heap growing down the page, stack at the bottom growing up the page. Dr. Zafar's slides draw the same thing upside down: 0KB at the bottom, "stack grows down, heap grows up". The addresses are identical in both: heap grows toward higher addresses (positively), stack toward lower addresses (negatively). In the exam, label the addresses on your diagram and you can't be marked wrong.

"Starts at 0" is a lie

In the multiprogramming figure, Process A really lives at physical 320KB. But Process A believes its address space starts at 0. So when A runs load from address 0, the OS together with the hardware must make that load actually go to physical address 320KB, not to 0 (which is where the OS lives). That conversion is address translation, and it's the subject of Lesson 12.

Analogy A hotel guest says "room 0 of my suite". The front desk knows that suite starts on the 32nd floor and silently sends them there. The guest never learns the real floor number, and can't wander into another guest's suite.

Name the three regions of an address space, say what each holds, and which way each one grows.

Code: the instructions; static, fixed size, at address 0.
Heap: malloc'd (user-managed) data; grows toward higher addresses.
Stack: locals, parameters, return addresses; grows toward lower addresses.
Heap and stack start at opposite ends and grow toward each other, sharing the free gap.

The OS places Process D in physical memory starting at 128KB. D runs load from address 0. Which physical byte address must actually be read, and what is this conversion called?

Physical = 128 × 1024 + 0 = 131,072 (128KB), not 0 (where the OS lives). Turning a virtual address into a physical one is address translation.

Which statement about the address space is TRUE?

  • It is the running program's view of memory: a private range of addresses starting at 0, holding its code, heap and stack. This is the abstraction the OS provides (OSTEP §13.2): every process gets its own, and every address in it is virtual.
  • It is the running program's view of memory: a private range of addresses starting where the OS loaded it in physical RAM. It starts at 0. Where the process really sits (e.g. 320KB) is hidden from it; that's what translation is for.
  • It is the slice of physical RAM the OS reserves for a process, holding its code, heap and stack at their real addresses. That's the physical memory behind it. The address space is the program's view of memory, made of virtual addresses.
  • It is the running program's view of memory: one range of addresses starting at 0 that all running processes share. Each process gets its own private address space; sharing one would destroy protection.

In the 16KB example address space (OSTEP / Dr. Bilal), which statement about the code segment is TRUE?

  • It is static (its size is fixed while the program runs), so it is placed at the start of the address space, at address 0. OSTEP §13.3: the code is static and easy to place, so it goes at the top (address 0); it never needs room to grow.
  • It grows on every function call, so it is placed at the start of the address space, at address 0. That's the stack. The code is static: the instructions don't change size while running.
  • It is static (its size is fixed while the program runs), so it is placed at the far end of the address space, at 16KB. The stack sits at the far end. Code sits at the start, address 0.
  • It is static (its size is fixed while the program runs), so it is placed in the free gap between the heap and the stack. The free gap is left empty so the heap and stack can grow into it. Code sits at address 0.

Which statement about how the heap and the stack grow is TRUE?

  • The heap grows toward higher addresses and the stack toward lower addresses, so the two grow toward each other. Heap starts just after the code and grows positively; stack starts at the far end and grows negatively. They share the free gap.
  • The heap grows toward lower addresses and the stack toward higher addresses, so the two grow toward each other. Swapped. Heap grows toward higher addresses, stack toward lower. (Zafar's "stack grows down" drawing means the same thing.)
  • The heap grows toward higher addresses and the stack toward lower addresses, so the two grow away from each other. They start at opposite ends, so growing that way brings them toward each other, into the shared gap.
  • The heap and the stack both grow toward higher addresses, and the stack starts just after the end of the heap. The stack starts at the far end and grows toward lower addresses.

Process C sits in physical memory at 128KB–192KB, but believes its address space starts at 0. C executes load from address 1000. Which is TRUE?

  • 1000 is a virtual address; the load really reads physical 131,072 + 1,000 = 132,072. 128KB = 128 × 1024 = 131,072. The OS and hardware add C's real starting point to every address it uses.
  • 1000 is a physical address; the load really reads physical 1,000, which belongs to the OS. Every address a program uses is virtual. Reading the OS's memory is exactly what translation prevents.
  • 1000 is a virtual address; the load really reads physical 128,000 + 1,000 = 129,000. KB means 1024 here: 128KB = 131,072, so the answer is 132,072.
  • 1000 is a virtual address; the load really reads physical 196,608 + 1,000 = 197,608. 196,608 is 192KB, C's end. Virtual 0 maps to C's start, 128KB, so the answer is 132,072.

Every address you see is virtual

If you print a pointer in C, you are seeing a virtual address. Only the OS and hardware know where it really is in physical RAM.OSTEP §13.4 aside You saw this in Lab 5 with your own va_explorer.c, which prints one address from each region:

Two runs of it on a 64-bit Linux machine:

$ ./va_explorer
Code segment (main function) : 0x63a4d845d1c9
Heap segment (2 Mib malloc) : 0x7b168abff010
Stack segment (local variable): 0x7fff4ff44be4
$ ./va_explorer
Code segment (main function) : 0x5d0e68f721c9
Heap segment (2 Mib malloc) : 0x76190d3ff010
Stack segment (local variable): 0x7fff516ebe84

Three things to notice:

  1. The order matches the picture: code is lowest, then the heap block, then the stack near the very top of the (huge, 64-bit) address space.
  2. The numbers change between runs. That's ASLR (Address Space Layout Randomization): Linux shifts each region randomly every run, so an attacker can't predict where things are. With ASLR turned off, the addresses repeat exactly, which proves they're not physical: two runs can't both own the same physical RAM.
  3. None of these are physical addresses. The machine may not even have that much RAM (0x7fff… is about 128 TB). They're positions in the process's own address space.

Side note: the 2 MiB block is far from the code because big malloc() requests are served by mmap() rather than by growing the classic heap. Lesson 11 explains.

Run mem.c twice (Lab 5, Task 2, and Lesson 1) with ASLR off and both copies print the same heap address, yet each counts independently. Same virtual address, different physical memory.

With ASLR turned off, two copies of the same program print the same heap address, yet each one counts up independently. What does that prove? And what is ASLR for?

The printed addresses are virtual, not physical: two processes can't own the same physical RAM, so the same virtual address must map to different physical memory. ASLR (Address Space Layout Randomization) shifts the code, heap and stack to random places each run so attackers can't predict addresses.

Which statement about ASLR is TRUE?

  • Address Space Layout Randomization: code, heap and stack get different random virtual addresses each run, so attackers can't predict them. That's why va_explorer prints different code, heap and stack addresses on every run. It is a security feature.
  • Address Space Layout Randomization: code, heap and stack get different random virtual addresses each run, so processes never clash in RAM. Keeping processes apart in RAM is the job of address translation. ASLR exists for security: unpredictable addresses.
  • Address Space Layout Randomization: only the heap gets a different random virtual address each run; code and stack stay fixed. All three move: in the lesson's two runs the code (0x63a4… vs 0x5d0e…) and the stack changed too.
  • Address Space Layout Randomization: the process is put at a different random physical address each run, and the program prints it. Printed pointers are always virtual. ASLR randomises the virtual layout of the address space.

With ASLR off, two copies of the same program both print the heap address 0x5555555592a0, yet each one counts up independently. Which conclusion is TRUE?

  • The printed address is virtual: the same virtual address maps to different physical memory in each process. Two processes can't own the same physical RAM, so each one's 0x…92a0 is translated to its own physical location.
  • The printed address is virtual: the same virtual address maps to the same physical memory in both processes. Then one process's writes would show up in the other's counter. They count independently, so the physical memory is different.
  • The printed address is physical: the OS gives both processes the same physical block and saves it on every switch. Pointers you print are virtual. Swapping memory to disk on every switch is the slow approach the OS avoids.
  • The printed address is physical, and the two values only match because ASLR is turned off. ASLR changes the virtual layout. Printed pointers are never physical; matching values prove they're virtual.

p, &p and *p

A pointer variable connects two regions of the address space, and this is a favourite exam question. Take:

int main(void) {
    int *p = malloc(sizeof(int));   // p is a local variable
    *p = 42;
    printf("%p\n", p);    // 0x633613e58010
    printf("%p\n", &p);   // 0x7ffc46627770
    printf("%d\n", *p);   // 42
}
This is how it's asked "Which statement correctly describes p, &p and *p?" The answer always has this shape: p = the heap address (what malloc returned), &p = the address of the pointer variable (on the stack, because p is a local), *p = the value stored in the heap. Distractors swap these around. If the pointer were a global variable, &p would be in the data region instead of the stack.

Inside main(): int *q = malloc(2 * sizeof(int)); q[0] = 9;
Say what each of q, &q and *q is, and which region it refers to.

q = the heap address malloc returned (where the 2 ints are).
&q = the address of the pointer variable q itself, on the stack (q is a local).
*q = 9, the value stored in the heap block (same as q[0]).

Now the pointer is a global: int *g; at file scope, and main() does g = malloc(sizeof(int));. Where is &g? Where does g point?

&g is in the data (globals) region, not the stack, because g is a global. g still holds a heap address, since that's what malloc returns.

Inside main(): double *d = malloc(sizeof(double)); *d = 2.5;
Which statement is TRUE?

  • d holds a heap address, &d is a stack address, and *d is 2.5, stored in the heap. d holds what malloc returned (heap). d itself is a local, so its own address &d is on the stack. *d follows d to the heap value.
  • d holds a stack address, &d is a heap address, and *d is 2.5, stored in the heap. Swapped: d holds what malloc returned, a heap address; &d is where d itself lives, on the stack.
  • d holds a heap address, &d is a stack address, and *d is 2.5, stored on the stack. *d is the value at the address d holds, so it is stored in the heap.
  • d holds a heap address, &d is that same heap address, and *d is 2.5, stored in the heap. &d is the address of the pointer variable d itself, a stack address, different from the heap address inside it.

At file scope: int *g; Then main() runs g = malloc(4 * sizeof(int)); g[0] = 7;
Which statement is TRUE?

  • &g is in the data (globals) region, g holds a heap address, and *g is 7. g is a global, so g itself lives in the data region (strictly .bss, the zero-filled part for uninitialised globals). Its value is what malloc returned (heap). *g is g[0] = 7.
  • &g is on the stack, g holds a heap address, and *g is 7. Only local variables live on the stack. g is a global, so &g is in the data region.
  • &g is in the data (globals) region, g holds a data-region address, and *g is 7. Where g lives doesn't change what it holds: it holds malloc's return value, a heap address.
  • &g is in the data (globals) region, g holds a heap address, and *g is the address of g[0]. The address of g[0] is g itself. *g is the value g[0], which is 7.

You run ./mem 41. What are the first three "value of p" numbers it prints, and roughly when does the first one appear?

42, 43, 44. Line 19 stores 41, then each loop pass does sleep(1) (line 21), adds 1 (line 22), and only then prints (line 23). So the first line appears after about 1 second and already shows 42.

Someone changes line 17 to print (void *)&p. What kind of address appears now? And what would go wrong if they printed *p with %d on line 17 instead?

&p is the address of the pointer variable itself, a stack address (0x7ff… on Linux), because p is a local. Printing *p on line 17 reads the heap int before line 19 has stored anything in it: an uninitialized read, so it prints whatever was there (malloc doesn't clear memory).

From memory: write the lines that malloc one int, check the result, store 5 in it, print the heap address and the value, then free it.

int *p = malloc(sizeof(int));
if (p == NULL) { fprintf(stderr, "malloc failed\n"); exit(1); }
*p = 5;
printf("%p %d\n", (void *)p, *p);
free(p);
The heap address is p and the value is *p. Writing &p would print the stack address of the pointer.

In mem.c, which line stores a value into the heap block?

  • Line 19, *p = atoi(argv[1]);: it follows p to the heap and writes the int there. The * means "the thing p points at", which is the heap int.
  • Line 13, p = malloc(sizeof(int));: it follows p to the heap and writes the int there. Line 13 writes into p itself (on the stack): it stores the heap address, not a value in the block.
  • Line 17, printf(..., (void *)p);: it follows p to the heap and writes the int there. Line 17 only reads p (the address) to print it. Nothing is written.
  • Line 12, int *p;: it follows p to the heap and writes the int there. Line 12 just declares the pointer on the stack. It doesn't point anywhere yet.

Goals of virtual memory

The OS doesn't just want the illusion to exist; it wants a good one. Three goals:Bilal slides, Ch 13 p.19

GoalMeans
TransparencyThe program shouldn't be able to tell memory is virtualized. It behaves as if it has its own private physical memory; the OS and hardware do the work invisibly.
EfficiencyVirtualization must not make programs noticeably slower (time), nor waste lots of memory on bookkeeping (space). This needs hardware support (e.g. TLBs, later).
Protection (isolation)A process must not be able to read or write another process's memory, or the OS's. Each process is isolated, so one crash or bug can't spread.
Memory hook T·E·P: Transparency, Efficiency, Protection. Dr. Bilal lists them in the order Protection, Efficiency, Transparency; OSTEP and Dr. Zafar use T, E, P. The order doesn't matter, but the one-line meaning of each does.
Summary The VM system gives each program the illusion of a large, sparse, private address space. The OS (with hardware help) maps every virtual reference to physical memory. That's what makes protection between processes and efficient sharing of RAM possible.

Name the three goals of virtual memory and give a one-line meaning for each.

Transparency: the program can't tell memory is virtualized; it acts as if it owns private memory.
Efficiency: little slowdown (time) and little wasted memory (space); needs hardware support such as TLBs.
Protection (isolation): no process can touch another process's memory or the OS's.

A proposed VM design works perfectly and safely, but every memory access now takes 50 times longer. Which goal does it fail?

Efficiency (time). This is why translation must be done by hardware, not by the OS in software on each access.

Which description of the three goals of virtual memory is TRUE?

  • Transparency: the program can't tell memory is virtualized. Efficiency: little time or space overhead. Protection: no process can touch another's memory or the OS's. These are the T·E·P goals (OSTEP §13.5, Bilal Ch 13 p.19). Bilal lists them in the order P, E, T; the meanings are the same.
  • Transparency: the program can see which physical addresses it uses. Efficiency: little time or space overhead. Protection: no process can touch another's memory or the OS's. Transparent means invisible: the program should not be able to tell memory is virtualized.
  • Transparency: the program can't tell memory is virtualized. Efficiency: little time overhead; space overhead doesn't matter. Protection: no process can touch another's memory or the OS's. Efficiency covers both time (speed) and space (little memory spent on bookkeeping).
  • Transparency: the program can't tell memory is virtualized. Efficiency: little time or space overhead. Protection: no process can touch another's memory, though it may read the OS's. Protection isolates processes from each other and from the OS.

A proposed VM design is safe and invisible to programs, but the OS checks and translates every memory access in software, so each access is 30× slower. Which is TRUE?

  • It fails the efficiency goal (time); translation has to be done by hardware so it costs almost nothing per access. Every fetch, load and store is translated, so it must be fast: that's why it needs hardware support.
  • It fails the efficiency goal (space); the OS's bookkeeping for the checks wastes too much memory. The problem described is speed: it fails efficiency in time.
  • It fails the protection goal; a check done in software lets a process reach another process's memory. The design is stated to be safe. What it loses is efficiency (time).
  • It fails the efficiency goal (time); the fix is to translate addresses only at context switches, not on every access. Every access must be translated. The fix is to do it in hardware.

Practice

Answer from memory first, then check. Struggling a little is what makes it stick.

1. A buggy game tries to overwrite the memory of your browser, and the OS stops it. Which goal of virtual memory is that?

Protection (isolation): no process may touch another process's memory, or the OS's.

2. In void f(int n) { int k = n * 2; char *s = malloc(k); }, where do k and the block s points to live?

Local variables (k, and s itself) are on the stack. Anything returned by malloc() is on the heap.

3. double *d = malloc(sizeof(double)); *d = 2.5; runs inside main(). What does printf("%p", (void *)&d) print?

&d is the address of the pointer variable, which is a local, so it's on the stack. d (no &) would print the heap block's address, and *d is 2.5.

4. In the slides' 16KB address space, which way does each region grow?

Heap starts after the code (1KB) and grows positively; stack starts at the top end (16KB) and grows negatively. They meet in the free space. Only the code is fixed.

5. In that 16KB address space the stack occupies 15KB–16KB. A deep function call pushes another 512 bytes. What is the lowest stack address now, in bytes? (1KB = 1024 bytes)

The stack grows negatively, toward lower addresses. Its low end moves from 15KB = 15360 down by 512: 15360 − 512 = 14848 (14.5KB).

6. Process B believes its address space starts at 0, but the OS placed it at physical 192KB. B loads from virtual address 1000. Which physical byte address must the hardware actually access?

Physical = where B really starts + virtual address = 192 × 1024 + 1000 = 196608 + 1000 = 197608. This simple "add an offset" translation is exactly base-and-bounds, next lesson but one.
7. Why did multiprogramming and time sharing make memory protection necessary, when early systems didn't need it?
Early systems ran one program with all of memory, so there was nobody else to harm. Multiprogramming and time sharing keep several processes in memory at once (swapping whole memories to disk was too slow). Now one program could read or overwrite another's memory, or the OS's, so the OS must isolate them. The address space abstraction provides that.
8. Your program prints a pointer: 0x7ffd1a2b3c40. Is that where the data is in RAM? Explain in two sentences.
No. It's a virtual address in the process's own address space (here, on the stack); the OS and hardware translate it to some unrelated physical address on every access. Proof: with ASLR off, two processes print the same address yet hold different values.
