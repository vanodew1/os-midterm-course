Lesson 11 · Memory virtualization

malloc, free, and how they go wrong

The stack cleans up after itself. The heap is yours to manage, and C will happily let you get it wrong. This lesson covers the API, the seven classic bugs, and why some of them "seem to work".

The problem: OSTEP's crux for this chapter: "How to allocate and manage memory? What interfaces are commonly used? What mistakes should be avoided?"OSTEP §14

The one-sentence version malloc(size) hands you size bytes on the heap and returns a pointer (or NULL); free(ptr) gives them back. You must allocate enough, initialize it, free it exactly once, and never touch it after freeing. The compiler checks none of this; these are run-time bugs.OSTEP §14

Lesson 10: void f(void) { char *s = malloc(6); }
Where does the variable s live, where do the 6 bytes live, and what would &s give you?

s is a local, so it lives on the stack. The 6 bytes from malloc live on the heap; s holds their address. &s is the address of the pointer variable s, a stack address.

Lesson 6: MLFQ Rule 5 says: after some time period S, move all jobs to the topmost queue. Which two problems does this priority boost fix?

(1) Starvation: long-running jobs stuck at the bottom while interactive jobs hog the top queues finally get CPU time.
(2) Changing behaviour: a job that was CPU-bound but has become interactive gets moved back up, instead of staying sunk forever.

Two kinds of memory

The problem: local variables vanish when a function returns. Where do you put data that must live longer?

A C program uses two kinds of memory:

  • Stack memory is handled for you by the compiler. It is also called automatic memory. Space appears when a function is called and disappears when it returns.
  • Heap memory is handled by you, by hand. You ask for it with malloc() and give it back with free(). OSTEP calls this "a heavy responsibility" and "the cause of many bugs".
Stack memoryHeap memory
Managed byThe compiler, automatically ("automatic memory")You, the programmer, explicitly
AllocatedWhen the function is calledWhen you call malloc()
FreedWhen the function returnsWhen you call free(), and only then
Use it forShort-lived localsData that must outlive the function, or whose size is known only at run time
void func() {
    int x = 5;                          // stack: gone when func returns
    int *p = malloc(sizeof(int));       // p is on the stack; *p is on the heap
    ...
}                                       // x and p vanish; the heap int does NOT

Notice that the int *p = malloc(...) line uses both kinds of memory at once. This is the same p / &p / *p picture as Lesson 10:

WriteWhat it isWhere it livesAfter func returns
&pthe address of the variable p itselfstack (p is a local)gone
pthe value inside p: a heap addressstored on the stack, points into the heapgone (with p)
*pthe int at that heap addressheapstill there, until free()

That last column is the root of most heap bugs. The pointer variable dies with the function. The heap block lives on until someone calls free(). If nobody kept a copy of its address, nobody can ever free it.

In short: stack = automatic, freed on return. Heap = manual, freed only by free(). Use the heap for data that must outlive the function or whose size is known only at run time.

Stack memory vs heap memory: who manages each, and when is each one freed?

Stack: managed automatically by the compiler; allocated when a function is called, freed when it returns.
Heap: managed by you; allocated by malloc(), freed only when you call free().
What's wrong with this function?
char *make_name(void) {
    char buf[16];
    strcpy(buf, "eve");
    return buf;
}
buf is on the stack, and the stack frame is freed when the function returns. The caller gets a dangling pointer to dead stack memory; the next function call will overwrite it. Fix: char *buf = malloc(16); (and the caller frees it).
With 4-byte ints:
void f(void) {
    int n = 4;
    int *q = malloc(n * sizeof(int));
    q[0] = 1;
}
Right after f returns, which is TRUE?
  • n and q are gone with the stack frame, but the 16-byte block q pointed to is still allocated on the heap. Locals live on the stack and die at return; heap memory lasts until free(). 4 × 4 = 16 bytes, now leaked.
  • n and q are gone with the stack frame, but the 4-byte block q pointed to is still allocated on the heap. The block holds n ints: 4 × sizeof(int) = 4 × 4 = 16 bytes, not 4.
  • n and q are gone with the stack frame, and the 16-byte block q pointed to is freed along with them. C has no garbage collector. A heap block is freed only by free(); here it is leaked.
  • n is gone with the stack frame, but q and the 16-byte block it points to are still allocated on the heap. q is a local variable, so q itself is on the stack and dies at return. Only *q (the block) is on the heap.

A function reads n from the user, then builds an array of n ints that its caller will keep using. Which is TRUE?

  • Use malloc(n * sizeof(int)): the heap block outlives the function, and the caller must free() it later. The data must outlive the function and its size is known only at run time: both are reasons to use the heap.
  • Use a local array int a[n]: the stack block outlives the function, and the caller must free() it later. A local array is on the stack and is freed when the function returns; returning it gives a dangling pointer (and you never free stack memory).
  • Use malloc(n * sizeof(int)): the heap block outlives the function, and it is freed when the caller returns. Heap memory is never freed automatically; the caller (or someone) must call free().
  • Use malloc(n): the heap block outlives the function, and the caller must free() it later. malloc takes bytes. n ints need n × sizeof(int) bytes (4n with 4-byte ints), not n.

malloc()

The problem: how do you ask for heap memory, and how much should you ask for?

You call malloc(). You tell it a size. It either gives you a pointer to fresh heap space, or fails.

#include <stdlib.h>
void *malloc(size_t size);
  • Argument: how many bytes you want. (size_t is just an unsigned integer type.)
  • Returns: on success, a void * pointer to the new block. On failure, NULL. So always check for NULL.Bilal slides, Ch 14 p.2

Use sizeof, never a hard-coded number

malloc counts bytes, not ints or doubles. So let the compiler tell you how many bytes a type takes:

double *d = malloc(sizeof(double));       // one double
int *arr   = malloc(n * sizeof(int));      // n ints (as in your dynamic_array.c)

sizeof is worked out by the compiler, not at run time. So it's fast and always right for the machine you compile on. Example: with 4-byte ints, 10 * sizeof(int) = 40 bytes.

One trap. sizeof on a pointer gives the size of the pointer, not of the block it points to:Bilal slides, Ch 14 p.3

int *x = malloc(10 * sizeof(int));
printf("%zu\n", sizeof(x));    // 8: the size of the POINTER, not of the 40-byte block
int y[10];
printf("%zu\n", sizeof(y));    // 40: a real array, size known at compile time

The slides print 4 for the pointer. That's right on a 32-bit machine. On today's 64-bit machines a pointer is 8 bytes. Either way: sizeof(pointer) is never the size of what it points to.

Strings need +1

C strings end with an invisible '\0' byte that marks the end. strlen does not count it. So strlen("hello") is 5, but storing "hello" takes 6 bytes:

char *dst = malloc(strlen(src) + 1);   // +1 for the '\0' terminator

Casting

You'll see (int *) malloc(...) in the slides. In C the cast is optional, because void * converts to any pointer type automatically. OSTEP says the cast only tells the reader "yeah, I know what I'm doing". It doesn't change what happens.OSTEP §14.2

In short: malloc(bytes) returns a void * or NULL (check it). Ask for n * sizeof(type), add +1 for strings, and remember sizeof(pointer) is 8 on 64-bit, not the block size.

How many bytes must you malloc to copy the string "operating", and what's the safe general way to write it?

strlen("operating") = 9, plus 1 for the '\0' terminator = 10. Write malloc(strlen(s) + 1). Forgetting the +1 is the "not allocating enough" (buffer overflow) bug.

On a 64-bit machine: int *a = malloc(25 * sizeof(int)); int b[25];
What do sizeof(a) and sizeof(b) give?

sizeof(a) = 8: a is a pointer, so you get the pointer's size, not the block's.
sizeof(b) = 100: b is a real array of 25 four-byte ints, known at compile time.

What does malloc() take as its argument, and what does it return on success and on failure?

It takes the number of bytes wanted (a size_t). It returns a void * to the new heap block on success, and NULL on failure, so always check for NULL.

What does malloc(n) return?

  • On success, a void * to a block of n bytes on the heap; on failure, NULL, so you should check the result. Bilal Ch 14 p.2: success → void pointer to the block; fail → a null pointer.
  • On success, a void * to a block of n bytes on the heap; on failure, nothing: the program is terminated. malloc returns NULL on failure and the program carries on, which is why you must check.
  • On success, a void * to a block of n bytes on the heap, all set to zero; on failure, NULL. malloc does not clear the block (that's the "forgot to initialize" bug). calloc zeroes.
  • On success, an int * to a block of n ints on the heap; on failure, NULL. The argument is a number of bytes, and the return type is void *. For n ints, ask for n * sizeof(int).

char *src = "kernel"; You want a heap copy made with strcpy. How many bytes must you malloc?

  • 7: strlen("kernel") is 6, and the '\0' terminator needs one more byte. C strings end with an invisible '\0' that strlen doesn't count, so malloc(strlen(src) + 1) = 7.
  • 6: strlen("kernel") is 6, and that count already includes the '\0' terminator. strlen does not count the '\0'. You need 6 + 1 = 7.
  • 6: strlen("kernel") is 6, and strcpy puts the '\0' just past the block, which is allowed. Writing that byte past the block is a buffer overflow (it may seem to work, then corrupt something). Allocate 7.
  • 8: sizeof(src) is 8 on a 64-bit machine, and that is the number of bytes the string takes. sizeof(src) is the size of the pointer, not of the string. Use strlen(src) + 1 = 7.

On a 64-bit machine with 4-byte ints: int *a = malloc(20 * sizeof(int)); int b[20];
Which is TRUE?

  • sizeof(a) is 8 and sizeof(b) is 80. a is a pointer, so you get the pointer's size (8). b is a real array, so you get 20 × 4 = 80.
  • sizeof(a) is 80 and sizeof(b) is 80. a is a pointer: sizeof gives the pointer's size, 8, never the size of the block it points to.
  • sizeof(a) is 8 and sizeof(b) is 8. b is a real array whose size is known at compile time: sizeof(b) = 20 × 4 = 80.
  • sizeof(a) is 4 and sizeof(b) is 80. 4 is a pointer on a 32-bit machine (as on the slides). On a 64-bit machine a pointer is 8 bytes.

Why does line 43 set arr = NULL when the program is about to exit anyway? What would it protect against in a longer program?

free() doesn't change arr; it still holds the old address (a dangling pointer). Setting it to NULL means any later use crashes at once instead of quietly reading or writing reused memory, and a second free(arr) becomes free(NULL), which is safe.

You need a heap block for exactly n ints, no more and no less. Which line is TRUE (correct)?

  • int *arr = malloc(n * sizeof(int)); malloc counts bytes: n ints need n × 4 bytes on a machine with 4-byte ints.
  • int *arr = malloc(n); That's n bytes, a quarter of what n ints need: a buffer overflow waiting to happen.
  • int *arr = malloc(n * sizeof(arr)); sizeof(arr) is the size of the pointer (8 on 64-bit), not of an int, so it asks for twice the bytes. Use sizeof(int) (or sizeof *arr).
  • int *arr = malloc(sizeof(int)); That's room for just one int. Multiply by n.

Line 29 passes &arr[i] to scanf. Which expression gives the same address?

  • arr + i Pointer arithmetic already scales by sizeof(int), so arr + i is the address of element i in the heap.
  • arr + i * sizeof(int) That scales twice: it lands at element 4i, far past where you meant.
  • &arr + i &arr is the address of the pointer variable on the stack, not of the heap block.
  • arr[i] That's the value of element i, not its address. scanf needs an address.

free()

The problem: how do you give heap memory back, and what exactly happens when you do?

OSTEP puts it well: allocating is the easy part; knowing when, how, and even if to free is the hard part. The call itself is simple:

void free(void *ptr);

Pass back exactly the pointer malloc() gave you. Notice you don't say how big the block was. How does free() know? The allocator stored the size itself, in a small hidden header just before your block. (Your my_malloc.c did exactly this with its MemBlock header, and found it again with (MemBlock *)ptr - 1.)

What free() does NOT do
  • It doesn't erase your data.
  • It doesn't set your pointer to NULL.
  • It usually doesn't give the memory back to the OS.
It just marks the block as free inside the allocator, so a later malloc() can reuse it. Hold on to that. It explains three of the bugs below.
Analogy free() is like checking out of a hotel room. The hotel can now give the room to someone else. But you still have the room number written down (the pointer keeps the address), and the old furniture is still inside (the data isn't erased). If you go back in, nothing stops you at first, but you may be walking into the next guest's room.

In short: free(ptr) takes only the pointer malloc returned; the size comes from a hidden header. It marks the block reusable, and that's all: the pointer still holds the old address.

Why don't you tell free() how big the block is? And name three things free() does NOT do.

The allocator stored the size in a small hidden header just before your block, and free() finds it there.
free() does not: erase your data, set your pointer to NULL, or (usually) give the memory back to the OS. It just marks the block free for a later malloc to reuse.

Right after free(p); which statement is TRUE?

  • The block is marked free so a later malloc can reuse it, and p still holds the same address. free() only updates the allocator's bookkeeping. It can't change p (p is passed by value), so p now dangles.
  • The block is marked free so a later malloc can reuse it, and p is set to NULL automatically. free() does not touch your pointer. Set p = NULL; yourself.
  • The block's bytes are erased and handed back to the OS, and p still holds the same address. free() does not erase the data and usually keeps the memory in the library's free list, not the OS.
  • The block is unmapped from the process, so any later use of *p is guaranteed to crash. The memory usually stays mapped, so using *p often seems to work. That's why use-after-free is so sneaky.

calloc() and realloc()

The problem: malloc gives you uncleared memory of a fixed size. What if you want it zeroed, or need it bigger later?

CallDoes
calloc(num, size)Allocates num × size bytes and zeroes them. Returns a pointer or NULL. Prevents uninitialized reads. Example: calloc(10, sizeof(int)) = 40 zeroed bytes.
realloc(ptr, size)Changes the block's size to size bytes, keeping the old contents. The pointer it returns may be the same as ptr or a new one. Returns NULL on failure.Bilal slides, Ch 14 p.14

The program you should be able to write from memory

Allocate one int, grow it with realloc(), then free it. The pattern is: malloc → check → realloc into a temporary pointer → check → switch over → use → free once.

#include <stdio.h>
#include <stdlib.h>

int main(void) {
    int *ptr = malloc(sizeof(int));           // room for 1 int
    if (ptr == NULL) return 1;
    ptr[0] = 7;

    int *tmp = realloc(ptr, 5 * sizeof(int)); // grow to 5 ints
    if (tmp == NULL) {                        // failed: ptr is STILL valid
        free(ptr);
        return 1;
    }
    ptr = tmp;                                // success: now switch over
    for (int i = 1; i < 5; i++) ptr[i] = 7 * (i + 1);

    printf("%d %d\n", ptr[0], ptr[4]);        // prints: 7 35
    free(ptr);                                // free the NEW block, once
    ptr = NULL;
    return 0;
}
Why the temp pointer? Suppose you write ptr = realloc(ptr, ...) and realloc fails:
  1. realloc returns NULL. The old block is still allocated and untouched.
  2. But the = overwrites ptr, your only copy of the old block's address, with NULL.
  3. Now nobody can free the old block. That's a memory leak.
So assign to tmp, check it, then copy into ptr. (Checked with valgrind: 0 errors, 0 bytes in use at exit.)

In short: calloc = malloc + zeroing. realloc keeps the contents but may move the block, so always use the pointer it returns, and catch it in a temp pointer so a failure doesn't leak the old block.

How is calloc(num, size) different from malloc(num * size)?

Same amount of memory, but calloc() also zeroes every byte. That prevents the "forgot to initialize" bug (reading leftover garbage).

Spot the bug: list = realloc(list, 200 * sizeof(int));

If realloc fails it returns NULL and leaves the old block alone, but this line overwrites list (the only pointer to that block) with NULL: a memory leak. Fix: int *tmp = realloc(list, ...); if (tmp == NULL) { /* handle, list still valid */ } else list = tmp;

realloc() succeeds but has to move the block to a new address. What is the old pointer now, and which pointer must you eventually free?

The old pointer is dangling: realloc already freed the old block after copying. Use and later free() only the pointer realloc returned.

With 4-byte ints: int *a = malloc(10 * sizeof(int)); int *b = calloc(10, sizeof(int));
Which is TRUE?

  • Both blocks are 40 bytes; only the bytes of b's block are guaranteed to be zero. calloc(num, size) allocates num × size = 40 bytes and zeroes them; malloc leaves whatever was there.
  • Both blocks are 40 bytes; the bytes of both blocks are guaranteed to be zero. malloc does not initialize: reading a's block before writing it gives leftover garbage.
  • Both blocks are 40 bytes; only the bytes of a's block are guaranteed to be zero. Swapped: calloc zeroes, malloc doesn't.
  • a's block is 40 bytes and b's is 10 bytes; only b's bytes are guaranteed to be zero. calloc takes a count and a size: 10 × sizeof(int) = 40 bytes, the same as a.

int *t = realloc(p, 100 * sizeof(int)); succeeds. Which is TRUE?

  • t may equal p or be a new address; the old contents are kept, and from now on you use and free only t. Bilal Ch 14 p.15: the pointer returned may be the same as ptr or a new one. If it moved, realloc copied the data and freed the old block.
  • t always equals p, because realloc grows the block in place; the old contents are kept. If something is in the way, realloc allocates a new block, copies, and frees the old one, so t can differ from p.
  • t may equal p or be a new address; the new block starts zeroed, so you copy the old data over yourself. realloc keeps the old contents (it copies them for you if it moves the block).
  • t may equal p or be a new address; the old contents are kept, and you must free both p and t. If it moved, realloc already freed the old block; if not, p and t are the same block. Either way freeing both is a double free: free only t.

The common errors

The problem: the compiler doesn't check how you use the heap. Which mistakes do people make, and how does each one show up?

C gives you full control and full responsibility. OSTEP notes that all of these bugs "compile and run with nary a peep from the compiler". Many fail silently, long after the real mistake. Its warning tip: "it compiled" or "it ran" does not mean "it is correct".OSTEP §14.4 Each bug below is a tiny program plus what actually happened when it ran on Linux.

1 · Forgetting to allocate

char *dst;                  // uninitialized pointer: points nowhere valid
strcpy(dst, "hello");       // writes to a random address

Result: Segmentation fault (core dumped). Fix: char *dst = malloc(strlen(src) + 1);

2 · Not allocating enough (buffer overflow)

char *src = "hello";
char *dst = malloc(strlen(src));   // 5 bytes, but "hello\0" needs 6
strcpy(dst, src);                  // writes 1 byte past the end

Result: often seems to work (prints "hello"). Why? The extra byte lands on heap memory nobody is using yet. Later it may corrupt another variable or the allocator's headers, and crash. Overflows like this are a classic security hole. Fix: strlen(src) + 1.

3 · Forgetting to initialize

int *x = malloc(sizeof(int));
printf("%d\n", *x);         // uninitialized read

Result: prints whatever was there before: 0 one time, garbage another. malloc() doesn't clear memory. Fix: assign a value first, or use calloc().

4 · Forgetting to free (memory leak)

A memory leak is heap memory that is allocated and never freed. This is your memory_leak.c. It leaks twice:

  • main mallocs 10 ints and never frees them.
  • leaky_function() mallocs 50 ints into a local pointer. The pointer disappears on return, so that block becomes unreachable: no pointer to it is left anywhere.
$ valgrind --leak-check=full ./memory_leak
==53903== 40 bytes in 1 blocks are definitely lost ...
==53903== 200 bytes in 1 blocks are definitely lost ...
==53903==    definitely lost: 240 bytes in 2 blocks

Result: no crash. The program just holds memory it can never use. 40 + 200 = 240 bytes here. In a long-running program (a server, the OS itself), usage keeps growing until it runs out of memory and dies.Bilal slides, Ch 14 p.10 In a short program the OS reclaims everything at exit, but it's still a bug. Fix: every malloc() gets exactly one free().

5 · Dangling pointer / use-after-free

A dangling pointer is a pointer that still holds the address of memory that has been freed. Reading or writing through it is use-after-free. It is undefined behaviour (C makes no promise about what happens). The scary part: it often seems to work. Here's why, with a login-style example:

char *name = malloc(16);
strcpy(name, "alice");
free(name);                       // name is now dangling (still holds the address)

char *pass = malloc(16);          // same size: the allocator REUSES the freed block
strcpy(pass, "s3cret");

printf("name=%p pass=%p\n", (void *)name, (void *)pass);
strcpy(name, "bob");              // write through the dangling pointer...
printf("pass now: %s\n", pass);   // ...and pass has changed!
name=0x589ad9320010 pass=0x589ad9320010
pass now: bob

Why does this "work" instead of crashing?

  1. free() doesn't invalidate the address. It doesn't erase the data or set the pointer to NULL. The memory usually stays part of the process's heap, still mapped and writable. So the hardware has no reason to fault on *name.
  2. The allocator recycles. The freed 16-byte block sits on a free list. The very next malloc(16) grabs the most convenient fit, which is often that same block. Now name and pass hold the same address (see the printout: both 0x589ad9320010).
  3. So the old pointer silently edits the new data. Nothing crashes. You just get wrong values, far from the real bug. Attackers love this pattern.

Think back to the hotel analogy: you kept the old room number, and the hotel gave the room to the next guest. Writing "bob" through name is walking in and rearranging their things.

Reading a freed block can also show garbage instead of the old value. When your use_after_free.c printed *p after free(p), it got 85158778, not 42. The allocator had written its own free-list pointer into the freed block. Either way it's undefined behaviour: the outcome depends on the allocator, the compiler and the run.

Fix: set the pointer to NULL right after freeing (free(name); name = NULL;). Then a later use crashes immediately and obviously. AddressSanitizer reports this exact bug as heap-use-after-free.

6 · Double free

int *p = malloc(sizeof(int));
free(p);
free(p);                    // freeing the same block twice

Your double_free.c did this. Output:

Allocated and set *p = 7
Freed p once.
free(): double free detected in tcache 2
Aborted (core dumped)
This is how it's asked: "Compile-time or run-time error?" Run-time (undefined behaviour). Here's why, step by step:
  1. The compiler checks only syntax and types. p is a valid int *, so free(p) twice is perfectly legal C to it. It doesn't track which blocks are allocated while the program runs.
  2. The allocator does track that. It keeps metadata (bookkeeping) saying which blocks are free.
  3. The first free marks the block free. On the second, glibc notices it's already free and calls abort().
  4. But that check isn't guaranteed. Other allocators may silently corrupt their free list and crash somewhere unrelated, later. That's why it's "undefined".

7 · Invalid free

int x = 5;
free(&x);                   // x is on the stack, not from malloc
int *a = malloc(4 * sizeof(int));
free(a + 1);                // not the pointer malloc returned

Result: free(): invalid pointer · Aborted. free() looks for its hidden header just before the address you pass. There isn't one, so it reads nonsense. Only pass a pointer that came straight from malloc/calloc/realloc, or NULL (which is safe and does nothing).

Tools that catch them

AddressSanitizerA compiler flag: gcc -fsanitize=address -g. It adds checks at run time. It stops at the first overflow or use-after-free and names the line.

On the name/pass program above, ASan stops immediately:

In short: seven bugs, all run-time, none caught by the compiler. Overflow and use-after-free often "seem to work"; double free and invalid free usually abort; leaks only hurt long-running programs. Every malloc gets exactly one free of the exact pointer it returned.

free(a);
free(b);
Double free: b holds the same address as a, so the same block is freed twice. It's a run-time error (undefined behaviour); the compiler only sees two legal calls on valid pointers. glibc usually notices via its metadata and aborts ("double free detected"), but that isn't guaranteed.
Which bug does this program have?
char *read_name(void) {
    char *n = malloc(32);
    strcpy(n, "zafar");
    return n;
}
int main(void) {
    read_name();
    return 0;
}
  • A memory leak: main throws away the returned address, so the 32-byte block becomes unreachable and the program can never free() it. The block outlives read_name (good), but nobody keeps its address, so it can never be freed.
  • A dangling pointer: n is a local, so the 32-byte block it points to is freed when read_name returns. Only the pointer variable n (on the stack) dies on return. The heap block lives until free(); returning n is fine.
  • A double free: the 32-byte block is freed once when read_name returns and again when main exits. There is no free() at all. Returning from a function never frees heap memory, so this is a leak.
  • A use-after-free: main uses the 32-byte block after read_name's stack frame has been freed. main never uses the block, and a heap block isn't part of any stack frame. The bug is a leak.

Which definition of a dangling pointer is TRUE?

  • A pointer that still holds the address of memory that has already been freed. free() leaves the address in the pointer; using it afterwards is use-after-free (undefined behaviour).
  • A pointer that was set to NULL right after the memory it pointed to was freed. Setting it to NULL is the fix: a NULL pointer no longer points at freed memory.
  • A heap block that is still allocated, but that no pointer refers to any more. That's a leaked (unreachable) block: memory with no pointer, the opposite of a pointer with no memory.
  • A pointer that was declared but never given a valid address to point to. That's forgetting to allocate (an uninitialized pointer), which usually segfaults straight away.
Which bug does this code have?
int *a = malloc(4 * sizeof(int));
int *b = a + 1;
free(a);
b[0] = 9;
  • Use-after-free: b points into the block that free(a) released, so b[0] = 9 writes to freed memory. a and b point into the same block. Freeing it through a makes b dangle too.
  • Memory leak: b still points into the block, so free(a) can't release it and it is never freed. free(a) releases the whole block no matter how many other pointers point into it. Nothing leaks; the bug is the later write through b.
  • Buffer overflow: b[0] lies past the end of the 4-int block, so the write lands outside it. b[0] is a[1], inside the 16-byte block. The problem is that the block was already freed.
  • No bug: only a was freed, so writing through b is still safe. Freeing releases the block, not a name. Every pointer into it, including b, now dangles.

char *buf = malloc(64); strcpy(buf, "os"); free(buf); free(buf); Which is TRUE?

  • It compiles; it's a run-time error that glibc's allocator usually catches, using its block metadata. gcc -Wall may print a warning, but it still builds. glibc's metadata shows the block is already free, so it usually aborts; it isn't guaranteed (undefined behaviour).
  • It usually fails to compile, because the compiler tracks which pointers have already been freed. It can't reject it: buf is a valid char *, so two free(buf) calls are legal C. It's a run-time error.
  • It compiles, and C guarantees the second free() is simply ignored, so it is harmless. It's undefined behaviour: often an abort, sometimes silent heap corruption. Only free(NULL) is guaranteed to do nothing.
  • It compiles; it's a run-time error that the OS kernel usually catches, because free() is a system call. free() is a library call. The allocator (glibc) notices, not the kernel.

Under the hood: the OS's part

The problem: malloc hands out heap memory, but where does malloc itself get memory from?

Key fact malloc() and free() are library calls (in the C library), not system calls. The library manages space inside your heap. It only asks the OS for more when it runs out.

To get more memory, the library uses real system calls:Bilal slides, Ch 14 pp.15–16

  • brk / sbrk move the program's break. The break is the address where the heap ends. brk(addr) sets it to an address. sbrk(increment) moves it by an amount. Moving it up grows the heap. Programmers should never call these directly; leave them to malloc.
  • mmap creates a brand-new anonymous memory region (not tied to any file) somewhere else in the address space. Large requests often use this. Your mmap_allocator.c and my_malloc.c (Lab 5) got their memory this way. It's also why va_explorer's 2 MiB block appeared far from the rest of the heap.

Two levels of memory management. OSTEP explains it like this:OSTEP §14.4 aside

  1. The OS level: the OS hands memory to a process, and takes all of it back (heap, stack, code) when the process exits.
  2. The library level: inside the process, malloc and free share out the heap. free() normally returns memory to the library (for the next malloc), not to the OS.

That's why a leak in a tiny program "doesn't matter": the OS cleans up at exit. A leak in a long-running server does matter, because it never exits.

In short: malloc/free are library calls. Underneath, the library uses the system calls brk/sbrk (move the end of the heap) and mmap (a new anonymous region). The OS reclaims everything when the process exits.

Are malloc() and free() system calls? If not, how does memory actually come from the OS?

No, they are library calls (C library). They manage space inside your heap and, when they need more, use real system calls: brk/sbrk (move the program break, where the heap ends) or mmap (a new anonymous region, used for large requests).

Why does a memory leak in a tiny program that runs for one second "not matter", while the same leak in a server does?

When a process exits, the OS reclaims all its memory (heap, stack, code), so the tiny program's leak vanishes. A server never exits, so leaked memory piles up until it runs out. (It's still a bug either way.)

Which statement about malloc(), free() and the OS is TRUE?

  • malloc() and free() are C library calls; when the heap runs out, the library asks the OS for more using brk/sbrk or mmap. The library manages space inside the heap and only makes a system call when it needs more (Bilal Ch 14 pp.16–17).
  • malloc() and free() are system calls; every call to malloc() traps into the kernel to get memory. They are library calls. Most mallocs never enter the kernel.
  • malloc() and free() are C library calls; every call to free() hands the block straight back to the OS with sbrk. free() normally returns the block to the library's free list for the next malloc, not to the OS.
  • malloc() and free() are C library calls; for small blocks programmers should call brk/sbrk directly, which is faster. Programmers should never call brk/sbrk directly; leave them to malloc.

Which statement about brk / sbrk is TRUE?

  • They move the program break, the address where the heap ends; moving the break up grows the heap. brk(addr) sets the break, sbrk(increment) moves it. The heap grows toward higher addresses, so the break moves up.
  • They move the program break, the address where the stack ends; moving the break down grows the stack. The break marks the end of the heap. The stack grows automatically as functions are called.
  • They move the program break, the address where the heap ends; moving the break down grows the heap. The heap grows toward higher addresses, so the break moves up.
  • They create a new anonymous region somewhere else in the address space, which is how large requests are served. That's mmap. brk/sbrk move the end of the existing heap.

  • After freeing, reuse gets small's address back.
Real bug in my_free (lines 79–81): it merges a block with block->next without checking that the two are next to each other in memory. Fresh start, 24-byte header, and suppose the first mmap returns page address 0x10000. What do my_malloc(40) and then my_malloc(8) return? How big is the free block left over?

First call: new page, header at 0x10000, returns 0x10018 (0x10000 + 24). split_block puts a free header at 0x10000 + 24 + 40 = 0x10040, size 4072 − 40 − 24 = 4008.
Second call: reuses that free block, so its header is at 0x10040 and it returns 0x10058 (0x10040 + 24). The leftover free block is 4008 − 8 − 24 = 3976 bytes.

Line 70 returns (void *)(block + 1). Why not block + HDR? How far would that move?

Pointer arithmetic counts in units of the pointed-to type. block is a MemBlock *, so block + 1 is already 24 bytes on. block + HDR = block + 24 would move 24 × 24 = 576 bytes, deep into the user's data. (Casting first works too: (char *)block + HDR.)

In my_free, what does line 76, (MemBlock *)ptr - 1, compute?

  • The address 24 bytes before ptr, where my_malloc put the block's header. Subtracting 1 from a MemBlock * steps back one whole header (sizeof(MemBlock) = 24).
  • The address 1 byte before ptr, where my_malloc put the block's header. Pointer arithmetic scales by the type: −1 on a MemBlock * is −24 bytes, not −1.
  • The address 24 bytes after ptr, where my_malloc put the block's header. The header sits in front of the data, so you step back.
  • The address 8 bytes before ptr, where my_malloc put the block's size field. It steps back the whole 24-byte header, and the header starts with size, not ends with it.

Practice

Answer from memory first, then check. Struggling a little is what makes it stick.

1. How many bytes should you malloc to hold a copy of the string "network"?

strlen("network") = 7, plus 1 for '\0' = 8. Use malloc(strlen(s) + 1).

2. On a 64-bit machine: long *v = malloc(20 * sizeof(long)); printf("%zu", sizeof(v)); What prints?

v is a pointer, so sizeof(v) is the size of a pointer: 8 bytes on a 64-bit machine. sizeof can't see how big the malloc'd block is.

3. Look at this code. On a typical Linux system, what does it most likely print?

char *msg = malloc(8);  strcpy(msg, "hi");
free(msg);
char *cmd = malloc(8);  strcpy(cmd, "ls");
msg[0] = 'r';
printf("%s\n", cmd);
malloc(8) right after freeing an 8-byte block usually gets that same block, so msg and cmd hold the same address. Writing 'r' through the dangling msg changes cmd's first letter: rs. (Verified on Linux; still undefined behaviour, not guaranteed.)

4. A program calls free(p) twice. When is this error detected, and by what?

The compiler sees two legal calls on a valid int *. Only at run time does the allocator, using its bookkeeping, notice the block is already free (glibc then aborts). It's undefined behaviour, so detection isn't guaranteed.

5. Which of these is a system call rather than a library call?

malloc, calloc, realloc and free are C library routines. They use the system calls brk/sbrk (and mmap) underneath to get memory from the OS.

6. Why should you write tmp = realloc(buf, n) instead of buf = realloc(buf, n)?

If realloc fails it returns NULL and leaves the old block alone. buf = realloc(...) would overwrite your only pointer to that block with NULL, which leaks it. (realloc may return the same address or a new one, so the first option is wrong too.)
7. Write from memory: allocate space for one double in a pointer called data, grow it to hold 10 doubles with realloc, then free it. Handle failures. 
double *data = malloc(sizeof(double));
if (data == NULL) return 1;
double *tmp = realloc(data, 10 * sizeof(double));
if (tmp == NULL) { free(data); return 1; }
data = tmp;
/* ... use data[0..9] ... */
free(data);
data = NULL;
Key marks: sizeof, NULL checks, realloc into a temp pointer, then assign, then one free of the final pointer.
8. A classmate's program uses a pointer after calling free() on it, and it prints the right value. They say "so it's fine". Give the three-part explanation.
(1) free() only marks the block free in the allocator. It doesn't erase the data, doesn't set the pointer to NULL, and the page stays mapped in the process, so accessing it doesn't fault. (2) It's still undefined behaviour: the next malloc() of a similar size will likely reuse that block, and then writes through the old pointer silently change the new owner's data (or the allocator's own metadata). (3) It may crash or print garbage on another run, compiler or system. Fix: set the pointer to NULL after free; detect with AddressSanitizer (heap-use-after-free) or valgrind.
