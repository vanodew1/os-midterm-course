Lesson 12 · Memory virtualization

Base and bounds: moving a program without it noticing

Every program thinks its memory starts at address 0. Two tiny registers in the CPU quietly add an offset to every address, and stop the program the moment it reaches outside its own box.

The one-sentence version On every memory access the hardware computes physical address = virtual address + base, after checking that the virtual address is less than bounds. If the check fails, it raises an exception and the OS takes over.OSTEP §15.3

Lesson 4: When the timer interrupt fires while a user process runs, what does the hardware do, and why does the OS need this timer at all?

The hardware saves the process's registers (onto its kernel stack), switches to kernel mode and jumps to the OS's timer handler (from the trap table). Without the timer, a process that never makes a system call could keep the CPU forever; the timer lets the OS regain control and maybe context-switch.

The goal: efficient, but controlled

Back in Lesson 4, limited direct execution (LDE) let a program run straight on the CPU, with the OS stepping in only at key moments such as a system call or a timer interrupt. We want the same deal for memory:Bilal slides, Ch 15

  • Efficiency: the program uses memory at full speed, so the hardware has to do the work.
  • Control: no program can touch memory that isn't its own, so the OS has to set things up and step in when something goes wrong.

The technique is called hardware-based address translation. On every instruction fetch, load and store, the hardware changes the virtual address the program used into the physical address where the data really lives.

Interposition OSTEP calls this interposition: something sits in the middle of every request and quietly changes it, without the client noticing. Think of a hotel switchboard. You dial "room 12", and the switchboard adds the floor offset and connects you to extension 3012. You never needed to know the real number.OSTEP §15 aside

What is "hardware-based address translation", and why is it done by hardware rather than by the OS?

On every instruction fetch, load and store, the hardware turns the program's virtual address into the physical address where the data really is. It must be hardware for efficiency: the OS can't run on every access. The OS keeps control by setting it up and handling faults (like LDE for memory).

Memory virtualization aims for efficiency and control, as LDE did for the CPU. Which is TRUE?

  • For efficiency, the hardware translates each access; for control, the OS sets up the translation and steps in when something goes wrong. Hardware is fast enough to run on every access; the OS manages it (sets registers, handles faults) without running on each access.
  • For efficiency, the OS translates each access; for control, the hardware sets up the translation and steps in when something goes wrong. Swapped. The hardware translates each access (fast); the OS sets things up and handles faults.
  • For efficiency, the hardware translates each access; for control, the OS checks every access and steps in when something goes wrong. The OS can't run on every access (that would kill efficiency). The hardware does the check too; the OS steps in only on a fault.
  • For efficiency, the hardware translates only loads and stores; for control, the OS sets up the translation and steps in when something goes wrong. Instruction fetches use virtual addresses too: the hardware translates every fetch, load and store.

OSTEP calls address translation an example of interposition. Which is TRUE?

  • The hardware sits between the process and memory and turns each virtual address into a physical one, without the process noticing. OSTEP's tip: the hardware interposes on each memory access. Its usual benefit is transparency: the client needs no changes.
  • The hardware sits between the process and memory and turns each physical address into a virtual one, without the process noticing. Reversed. The process issues virtual addresses; the hardware turns them into physical ones.
  • The OS sits between the process and memory and turns each virtual address into a physical one, without the process noticing. Wrong actor. Running OS code on every access would be far too slow; the hardware interposes.
  • The hardware sits between the process and memory and turns each virtual address into a physical one, after the process asks with a system call. No request is needed: interposition is transparent. The process just uses its addresses and never notices.

Three simplifying assumptions

To keep this first version simple, Bilal's slides (and OSTEP §15.1) assume:

  1. Each address space is placed contiguously (in one piece) in physical memory.
  2. Each address space is smaller than physical memory.
  3. Every address space is exactly the same size.

We relax these later. Segmentation (next lesson) drops the "one contiguous piece" assumption.

List the three simplifying assumptions behind the first version of base and bounds.

Each address space is (1) placed contiguously in physical memory, (2) smaller than physical memory, and (3) exactly the same size as every other.

Which list of the first base-and-bounds version's simplifying assumptions is TRUE? Each address space is …

  • … placed contiguously in physical memory, smaller than physical memory, and exactly the same size as every other. These are the three assumptions in OSTEP §15.1 and Dr. Bilal's slides.
  • … placed contiguously in physical memory, larger than physical memory, and exactly the same size as every other. Reversed. It is assumed to be smaller than (less than the size of) physical memory.
  • … placed as separate code, heap and stack pieces in physical memory, smaller than physical memory, and exactly the same size as every other. Splitting into pieces is segmentation, which relaxes this assumption. Here each address space is contiguous (one piece).
  • … placed contiguously in physical memory, smaller than physical memory, and sized to fit its own program. The third assumption is that every address space is exactly the same size.

Every address space is 16 KB and physical memory is 64 KB. Which situation breaks one of the three simplifying assumptions?

  • A's code and heap occupy 16–28 KB and its stack 44–48 KB, with B occupying 28–44 KB. A's address space is split into two pieces with B in between, so it is no longer contiguous: assumption 1 is broken (this is what segmentation allows).
  • A occupies 32–48 KB, and 10 KB of that, between its heap and its stack, is unused. Still one contiguous 16 KB piece, smaller than memory. The unused gap is wasted (internal fragmentation) but breaks no assumption.
  • A occupies 16–32 KB and B occupies 48–64 KB, with 32–48 KB free. Each is one contiguous 16 KB piece, smaller than 64 KB. A free gap between processes breaks no assumption.
  • A occupies 16–32 KB, and while it is not running the OS moves it to 48–64 KB. Relocation just changes the base; A is still one contiguous 16 KB piece. This breaks no assumption.

The running example: x = x + 3

The compiler turns this one line of C into three instructions. Assume the address of x is already in register ebx:Bilal slides, Ch 15

128: movl 0x0(%ebx), %eax   ; load x into eax
132: addl $0x03, %eax       ; add 3
135: movl %eax, 0x0(%ebx)   ; store eax back into x

Running it makes five memory accesses: fetch at 128, load from 15 KB (where x lives on the stack), fetch at 132 (the add touches no memory), fetch at 135, then store to 15 KB. From the program's point of view, its address space runs from 0 to 16 KB.

The problem: how do we move the process to 32 KB transparently, so its addresses (128, 15 KB…) still work? An early idea was static relocation: a loader rewrites every address in the program before it runs. It gives no protection, though, and the process can't easily be moved later.OSTEP §15.3 aside The fix is to do it in hardware, at run time.

The three instructions of x = x + 3 (a load, an add, a store) live at 128, 132 and 135, and x is at 15 KB. How many memory accesses does running them make, and what are they?

Five: fetch at 128, load from 15 KB, fetch at 132 (the add touches no data), fetch at 135, store to 15 KB. Every one of them gets translated.

What is static relocation, and what are its two problems?

A loader rewrites every address in the program before it runs, so it fits where it was placed. Problems: no protection (the program can still form any address) and the process can't easily be moved later.

The three instructions of x = x + 3 (a load at 128, an add at 132, a store at 135; x is at 15 KB) run once. Which is TRUE?

  • They make five memory accesses (three instruction fetches, one load, one store), and every one of them is translated. Fetch 128, load 15 KB, fetch 132, fetch 135, store 15 KB. Instruction fetches use virtual addresses too.
  • They make three memory accesses, one per instruction, and every one of them is translated. Each instruction is fetched from memory, and the load and store also touch data: five accesses.
  • They make six memory accesses (three instruction fetches and one data access each), and every one of them is translated. The add works only on a register (eax), so it has no data access: five in total.
  • They make five memory accesses, but only the load and the store are translated; instruction fetches use physical addresses. The PC holds a virtual address too, so every fetch is translated as well.

Dynamic relocation: base and bounds

Each CPU gets two registers inside its memory management unit (MMU):Bilal slides, Ch 15

RegisterHoldsUsed for
BaseWhere the process starts in physical memoryRelocation: physical = virtual + base
Bounds (or limit)The size of the address spaceProtection: 0 ≤ virtual < bounds

It is called dynamic relocation because it happens at run time, and the OS can change base whenever it likes.

Worked example (from the slides)

Base = 32 KB = 32,768, bounds = 16 KB = 16,384.Bilal slides, Ch 15

  1. Fetch at 128. 128 < 16,384 ✓, so PA = 128 + 32,768 = 32,896.
  2. Load from 15 KB. 15,360 < 16,384 ✓, so PA = 15 KB + 32 KB = 47 KB (48,128).
  3. VA 0 KB → 32 KB. VA 16 KB: 16,384 < 16,384? No, so it faults. The slides' "16 + 32 = 48 KB" is exactly the first byte past the process.

Why is VA = bounds already illegal? And in the size convention, does the bounds check use the virtual or the physical address?

The valid range is 0 ≤ VA < bounds, i.e. 0 … bounds − 1, so VA = bounds is the first byte past the process. In the size convention the check uses the virtual address, and is done before adding base.

Base = 36 KB, bounds = 6 KB (bounds = size). Which translation of virtual address 2,500 is TRUE?

  • 2,500 < 6,144, so it is legal and PA = 36,864 + 2,500 = 39,364. Check first (VA < bounds = 6 × 1024), then add base = 36 × 1024 = 36,864.
  • 2,500 < 6,144, so it is legal and PA = 36,864 − 2,500 = 34,364. You add the base: PA = VA + base = 39,364.
  • 2,500 < 6,144, so it is legal and PA = 6,144 + 2,500 = 8,644. Add the base (36,864), not the bounds. Bounds is only for the check.
  • 2,500 < 6,000, so it is legal and PA = 36,000 + 2,500 = 38,500. KB means 1024: base = 36,864 and bounds = 6,144, so PA = 39,364.

Base = 36 KB, bounds = 6 KB (bounds = size). Which translation of virtual address 6,144 is TRUE?

  • 6,144 is not < 6,144, so the hardware raises an out-of-bounds exception. Valid VAs are 0 … bounds − 1 = 0 … 6,143. VA = bounds is the first byte past the process.
  • 6,144 ≤ 6,144, so it is legal and PA = 36,864 + 6,144 = 43,008. The check is strict: VA < bounds. VA = bounds is already out of bounds.
  • 6,144 < 43,008 (base + bounds), so it is legal and PA = 36,864 + 6,144 = 43,008. Here bounds is a size, so compare the VA with 6,144, not with base + bounds.
  • 6,144 is not < 6,144, so the hardware clamps it to the last legal byte, PA = 43,007. Nothing is clamped: the hardware raises an exception and the OS takes over (usually killing the process).

In the size convention (Dr. Bilal's formula slide), which statement about the bounds register is TRUE?

  • It holds the size of the address space, and the hardware checks 0 ≤ VA < bounds before adding base. Bounds is for protection: check the virtual address first, then relocate with base.
  • It holds the size of the address space, and the hardware checks 0 ≤ PA < bounds after adding base. With bounds = size, the check uses the virtual address, before adding base. (Checking the PA is the end-address convention.)
  • It holds where the process starts in physical memory, and the hardware checks 0 ≤ VA < bounds before adding base. The physical start is the base register. Bounds holds the size.
  • It holds the size of the address space, and the hardware relocates with it: PA = VA + bounds. Relocation uses base: PA = VA + base. Bounds is only for the protection check.

Name at least four things the hardware must provide for base-and-bounds.

(1) Privileged (kernel) mode; (2) base/bounds registers in the MMU, one pair per CPU; (3) circuitry to add base and check bounds on every access; (4) privileged instructions to update base/bounds; (5) privileged instructions to register exception handlers; (6) the ability to raise exceptions (out of bounds, or a user trying to change base/bounds).

A user-mode program executes the instruction that sets the base register. What happens, and why must it?

The hardware raises an exception, because it's a privileged instruction; the OS handler typically kills the process. If users could set base, they could point it at any process's memory (or the OS's) and protection would be gone.

Why must the instructions that change the base and bounds registers be privileged?

  • A user process could otherwise point base at another process's (or the OS's) memory, so protection would be lost. Only the OS, in kernel mode, may set them. A user-mode attempt raises an exception.
  • A user process could otherwise point base at another process's memory, so the hardware silently ignores such attempts in user mode. The hardware doesn't ignore it: it raises an exception, and the OS usually terminates the process.
  • A user process could otherwise change them so often that translation slows down, so efficiency would be lost. The reason is protection: whoever controls base can reach any physical memory.
  • The OS has to change them on every memory access, and only kernel mode is fast enough for that. The hardware translates every access. The OS sets base/bounds only at a few moments (process start, context switch).

What the OS must do

Bonus: moving a process While a process is not running, the OS can move it. It copies the address space to a new spot and updates the saved base in the PCB. When the process resumes, the new base is loaded, and the process never notices.OSTEP §15.5

The OS switches from process A to process B. Exactly what does it do with the base and bounds registers?

There's only one pair per CPU, so the OS saves A's base and bounds into A's PCB (process structure) and loads B's values from B's PCB into the registers before returning into B.

A process is not running and the OS wants to move it from physical 16 KB to 48 KB. What steps does it take, and does the process notice?

It copies the address space to the new spot and updates the saved base in the PCB to 48 KB. When the process resumes, the new base is loaded and every address still works. The process never notices.

The OS switches the CPU from process A to process B. What does it do with base and bounds?

  • It saves A's base and bounds into A's PCB, then loads B's saved base and bounds into the registers. There is only one pair of registers per CPU, so each process's values live in its PCB while it isn't running.
  • Nothing: every process has its own base and bounds registers in the MMU, so they never need changing. There is only one pair per CPU, so the OS must save A's and restore B's.
  • It saves A's base and bounds into A's PCB, then copies B's address space into A's old physical slot. No copying is needed: B's memory stays where it is, and the OS just loads B's base and bounds.
  • It saves A's base and bounds into A's PCB, then sets base = 0 and bounds = all of RAM while B runs. That would let B reach everyone's memory. The OS loads B's own saved base and bounds.

A running process accesses a virtual address beyond its bounds. Which is TRUE?

  • The hardware raises an exception, switches to kernel mode and runs the OS's handler, which usually terminates the process. The handler was registered in the trap table at boot. The usual reaction is to kill the offending process and reclaim its memory.
  • The hardware raises an exception, switches to kernel mode and runs the OS's handler, which usually raises bounds so the access succeeds. Base and bounds has no "grow on demand". The usual reaction is to terminate the process.
  • The OS checks each address in software, notices the bad one and terminates the process before the access happens. The hardware does the check on every access. The OS only runs once the exception fires.
  • The hardware raises an exception, stays in user mode and jumps to the process's own error-handling code. It switches to kernel mode and runs the OS's handler from the trap table.

Process P is not running. The OS wants to move it from physical 16 KB to physical 64 KB. Which is TRUE?

  • The OS copies P's address space to 64 KB and updates the saved base in P's PCB to 64 KB; P never notices. When P next runs, the new base is loaded and every virtual address still works (OSTEP §15.5).
  • The OS copies P's address space to 64 KB and rewrites every address in P's code to add 48 KB. Rewriting addresses is static relocation. With base and bounds only the saved base changes.
  • The OS copies P's address space to 64 KB and updates the saved bounds in P's PCB to 64 KB. The size hasn't changed, so bounds stays the same. The base becomes 64 KB.
  • The OS updates the saved base in P's PCB to 64 KB; the hardware copies the data over on P's next access. The hardware never copies memory. The OS must copy the address space itself.

Process A is running normally under base and bounds (no system calls, timer interrupts or faults). Which is TRUE?

  • The OS translates each address in software, and the hardware only raises an exception if bounds is exceeded. Translation is done by hardware on every access; doing it in software would be far too slow.
  • The hardware adds base to each address, and the OS checks each result against bounds in software. The bounds check is hardware too. The OS isn't involved on each access, only on exceptions.

The catch: internal fragmentation

Base and bounds reserves the whole address space as one block, including the big gap between heap and stack that the program isn't using. That gap still takes real physical memory, in every process. Waste inside an allocated block like this is called internal fragmentation.OSTEP §15.6

Bilal's question: what if code, heap and stack each had their own base and bounds? Then the gap needs no physical memory at all. That idea is segmentation, the next lesson.

"What must happen to base/bounds on a context switch?" "What is internal fragmentation and why does base-and-bounds suffer from it?" Short definitions and arithmetic, so get the check-then-add order automatic.

Every process gets a fixed 32 KB slot. One uses 2 KB of code, 4 KB of heap and 2 KB of stack. How much is wasted, and what is that waste called?

Used = 2 + 4 + 2 = 8 KB, so 24 KB wasted (75% of the slot): the unused gap between heap and stack still occupies physical memory. Waste inside an allocated block is internal fragmentation.

Why can't plain base and bounds handle a 32-bit address space well, and what idea fixes this?

It needs the whole 4 GB address space as one contiguous physical block, nearly all of it the unused gap. Fix: give code, heap and stack their own base and bounds, which is segmentation.

Every process gets a fixed 16 KB slot. One process uses 3 KB of code, 2 KB of heap and 1 KB of stack. Which is TRUE?

  • 10 KB of the slot is wasted, inside the allocated block; this is internal fragmentation. Used = 3 + 2 + 1 = 6 KB, so 16 − 6 = 10 KB of free gap still takes physical memory.
  • 10 KB of the slot is wasted, inside the allocated block; this is external fragmentation. Waste inside an allocated block is internal. External is holes between blocks (segmentation).
  • 6 KB of the slot is wasted, inside the allocated block; this is internal fragmentation. 6 KB is what's used. The waste is 16 − 6 = 10 KB.
  • Nothing is wasted, because the free gap between heap and stack takes no physical memory. Base and bounds reserves the whole slot, gap included. Avoiding that is what segmentation is for.

Practice

Answer from memory first, then check. Struggling a little is what makes it stick.

1. A process has base = 18 KB and bounds = 6 KB (bounds = size). It loads from virtual address 2,500. What physical address is accessed?

Check: 2,500 < 6 × 1024 = 6,144 ✓. Translate: 2,500 + 18 × 1024 = 2,500 + 18,432 = 20,932.

2. Same process (base 18 KB, bounds 6 KB). It now stores to virtual address 6,200. What happens?

6,200 ≥ 6,144 (= 6 KB), so the check fails before any translation. The hardware raises an exception and the OS's handler runs, and will most likely kill the process. (24,632 is what you'd get if you forgot to check.)

3. A machine uses the other convention: bounds holds the physical address of the end of the address space. Base = 40,000 and bounds = 44,000. What is the largest legal virtual address?

Size = end − base = 44,000 − 40,000 = 4,000 bytes, so the legal VAs are 0 … 3,999. Check: 3,999 + 40,000 = 43,999 < 44,000 ✓, but 4,000 + 40,000 = 44,000 fails.

4. Process A is descheduled so B can run. Where are A's base and bounds values kept until A runs again?

There's only one base/bounds pair per CPU. On a context switch the OS saves A's values into A's process structure (PCB) and restores B's from B's PCB.

5. Why must the instructions that change the base and bounds registers be privileged?

If user code could set base and bounds, a process could point base at another process's memory (or at the OS) and read or overwrite it. Protection would be gone. In user mode, trying to change them raises an exception.

6. Each process gets a fixed 16 KB slot. A process uses 1 KB of code, 3 KB of heap and 2 KB of stack. How many KB of its slot are lost to internal fragmentation?

Used = 1 + 3 + 2 = 6 KB. Wasted = 16 − 6 = 10 KB. That's the free gap between heap and stack, reserved in physical memory but never used.

7. While process A runs normally, who translates each of its virtual addresses into physical ones?

Translation is done by the MMU hardware on every access, with no OS involvement. The OS only acts at boot, at process creation and termination, on context switches, and on exceptions. (A loader rewriting addresses would be static relocation.)
8. Name the OS's responsibilities for base-and-bounds, and say when each one happens.
Memory management: on process creation, find a free slot using the free list; on termination, reclaim the memory onto the free list. Base/bounds management: on every context switch, save the old process's base/bounds into its PCB and restore the new one's. Exception handling: install handlers at boot; when an out-of-bounds exception occurs, run the handler (usually terminate the process).
