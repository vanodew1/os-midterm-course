Lesson 13 · Memory virtualization

Segmentation: a base and bounds for every piece

Instead of moving the whole address space as one block, move code, heap and stack separately. The empty gap between them no longer costs any physical memory.

The one-sentence version Segmentation gives each logical segment (code, heap, stack) its own base and bounds (size) pair. The top bits of a virtual address say which segment, the rest is the offset inside it, and physical = base[segment] + offset, after a bounds check.OSTEP §16.1

Lesson 12: Base = 44 KB and bounds = 5 KB (bounds = size). Translate virtual address 5,000, then 5,200.

Bounds = 5 × 1024 = 5,120; base = 44 × 1024 = 45,056.
VA 5,000: 5,000 < 5,120 ✓ → PA = 45,056 + 5,000 = 50,056.
VA 5,200: 5,200 ≥ 5,120 → fault (out-of-bounds exception).

Lesson 5: STCF (shortest time-to-completion first). A arrives at 0 needing 8 units; B arrives at 2 needing 3. Draw the schedule and give the average turnaround time.

At t = 2, B (3 left) beats A (6 left), so B preempts. Schedule: A 0–2, B 2–5, A 5–11.
Turnaround: A = 11 − 0 = 11, B = 5 − 2 = 3. Average = 7. (Both response times are 0.)

Why: the free gap is real memory

With one base and bounds (Lesson 12), the "big chunk of free" between heap and stack "is not an illusion, it does take up physical memory".Bilal slides, Ch 16 A segment is simply a contiguous portion of the address space of a particular length. Bilal lists four: code, data, heap and stack. OSTEP and the quizzes use three: code, heap and stack. Place each one independently, and the gap needs nothing.

Translating when you know the segment

The key move: the offset is the distance from the start of that segment in the virtual address space, not from 0.Bilal slides, Ch 16

  1. Code, VA 100. Code starts at virtual 0, so offset = 100. PA = 32K + 100 = 32,768 + 100 = 32,868.
  2. Heap, VA 4200. Heap starts at virtual 4 KB, so offset = 4200 − 4096 = 104. PA = 34K + 104 = 34,816 + 104 = 34,920.
  3. Heap, VA 7 KB. The heap only runs from 4 KB to 6 KB, so 7 KB is past its end. The hardware detects this and raises a segmentation fault, the name for any access to an illegal address.
Trap Adding the base to the whole VA (34,816 + 4,200) is the #1 mistake. Always subtract the segment's virtual start first. The bit trick below does that subtraction for you.

What is a segment, and why does segmentation save physical memory compared with a single base and bounds?

A segment is a contiguous portion of the address space of a particular length (code, heap, stack). Each gets its own base and size, so each is placed separately and the free gap between heap and stack needs no physical memory.

Code is at virtual 0 (base 20 KB, size 2 KB). The heap starts at virtual 4 KB with base 10 KB and size 3 KB. Translate heap address VA 4,500.

Offset from the start of the heap's virtual range: 4,500 − 4,096 = 404. Check 404 < 3,072 ✓. PA = 10 × 1024 + 404 = 10,240 + 404 = 10,644. (Adding base to the whole VA, 10,240 + 4,500, is the classic mistake.)

Code: virtual 0–4 KB, physical base 20 KB, size 2 KB. Heap: virtual 4–8 KB, physical base 46 KB, size 3 KB, grows up. Which translation of heap address VA 5,000 is TRUE?

  • Offset = 5,000 − 4,096 = 904 < 3,072, so PA = 47,104 + 904 = 48,008. Offset is measured from the heap's virtual start (4 KB). Check against the heap's size, then add the heap's base (46 × 1024).
  • Offset = 5,000 < 8,192, so PA = 47,104 + 5,000 = 52,104. Adding base to the whole VA is the #1 slip. Subtract the heap's virtual start first: offset = 904.
  • Offset = 5,000 − 4,096 = 904 < 3,072, so PA = 20,480 + 904 = 21,384. 20 KB is the code segment's base. VA 5,000 is in the heap, so add the heap's base, 47,104.
  • Offset = 5,000 − 4,096 = 904 < 3,072, so PA = 47,104 − 904 = 46,200. The heap grows up, so you add the offset: 47,104 + 904 = 48,008.

Which segment? The explicit approach

A 16 KB address space has 16,384 = 214 bytes, so addresses are 14 bits. The explicit approach chops the address space up using the top few bits: the top 2 bits select the segment, and the low 12 bits are the offset.OSTEP §16.2

Rule of thumb: 210k + r = 2r × (KB, MB, GB for k = 1, 2, 3). So 229 = 29 MB = 512 MB, and 215 = 25 KB = 32 KB.

Example. A 32-bit address with a 3-bit selector has 23 = 8 segments. That leaves 29 offset bits, so the max segment size is 229 = 512 MB. In the 14-bit example: 22 = 4 segments, each at most 212 = 4 KB.

The explicit approach costs you two things (Zafar's slides). One selector value is wasted when there are only 3 segments, and no segment can grow past the max size (4 KB here), even if memory is free.

Decimal → binary, then split

Take VA = 5300 in our 14-bit system. Subtract the biggest powers of 2 that fit:

5300 = 4096 + 1024 + 128 + 32 + 16 + 4
     = 212 + 210 + 27 + 25 + 24 + 22
     = 01 0100 1011 0100 (14 bits; put a 1 at bits 12, 10, 7, 5, 4, 2)

Segment = 01 (heap). Offset = 0100 1011 0100 = 1024 + 128 + 32 + 16 + 4 = 1204.

Shortcut to check yourself Splitting the bits is the same as dividing by the max segment size: segment = ⌊VA / 2n⌋, offset = VA mod 2n. Here 5300 / 4096 = 1 remainder 1204. Equivalently, offset = VA − (start of that segment's virtual range) = 5300 − 4096. That's the "range" method the Quiz 6 solution uses.

  • Heap addresses are 4,096–8,191 and stack addresses are 12,288–16,383. Each selector value owns a 4 KB (4,096-byte) slice: 01 → 4 KB–8 KB, 11 → 12 KB–16 KB.
  • Heap addresses are 4,096–8,191 and stack addresses are 8,192–12,287. 8 KB–12 KB is selector 10, unused in this table. Stack is 11: 12,288–16,383.
  • Heap addresses are 4,000–7,999 and stack addresses are 12,000–15,999. KB means 1024: heap 4,096–8,191, stack 12,288–16,383.
  • Heap addresses are 0–4,095 and stack addresses are 12,288–16,383. 0–4,095 is selector 00, the code. The heap (01) is 4,096–8,191.

A 32-bit virtual address uses its top 4 bits as the segment selector. Which is TRUE?

  • There can be 16 segments, each at most 228 bytes = 256 MB. Segments = 2s = 24 = 16. Offset bits n = 32 − 4 = 28, so max size = 228 = 28 MB = 256 MB.
  • There can be 4 segments, each at most 228 bytes = 256 MB. 4 is the number of selector bits. Segments = 24 = 16.
  • There can be 16 segments, each at most 228 bytes = 512 MB. 228 = 28 × 220 = 256 MB. (512 MB is 229.)
  • There can be 16 segments, each at most 232 bytes = 4 GB. Only the 28 offset bits address bytes inside a segment: max size = 228 = 256 MB.

The hardware's code: SEG_MASK, SEG_SHIFT, OFFSET_MASK

// get top 2 bits of 14-bit VA
Segment = (VirtualAddress & SEG_MASK) >> SEG_SHIFT
// now get offset
Offset  = VirtualAddress & OFFSET_MASK
if (Offset >= Bounds[Segment])
    RaiseException(PROTECTION_FAULT)
else
    PhysAddr = Base[Segment] + Offset
    Register = AccessMemory(PhysAddr)

Exam: why is the shift needed? Masking only zeroes out the offset bits. The segment bits stay in their high positions (bits 13–12), so the result is 4096, not 1. Shifting right by SEG_SHIFT moves them down to the lowest bits, giving a small number (0–3) that can index the Base[] and Bounds[] arrays.

General recipe for s selector bits and n offset bits: SEG_SHIFT = n; OFFSET_MASK = 2n − 1 (n ones); SEG_MASK = s ones followed by n zeros. For example, a 32-bit address with 2 selector bits gives SEG_SHIFT = 30, OFFSET_MASK = 0x3FFFFFFF, SEG_MASK = 0xC0000000.

14-bit virtual addresses with a 2-bit segment selector at the top. Which set of constants is TRUE?

  • SEG_MASK = 0x3000, SEG_SHIFT = 12, OFFSET_MASK = 0xFFF. SEG_MASK = 11 0000 0000 0000 (bits 13–12); shift by the 12 offset bits; OFFSET_MASK = 12 ones.
  • SEG_MASK = 0x3000, SEG_SHIFT = 2, OFFSET_MASK = 0xFFF. Shift by the number of offset bits (12), not selector bits, to bring bits 13–12 down to the bottom.
  • SEG_MASK = 0xC000, SEG_SHIFT = 12, OFFSET_MASK = 0xFFF. 0xC000 is the top 2 bits of a 16-bit address. For 14 bits the top two are bits 13–12: 0x3000.
  • SEG_MASK = 0x3000, SEG_SHIFT = 12, OFFSET_MASK = 0x3FFF. 0x3FFF is all 14 bits. The offset is only the low 12 bits: 0xFFF.

14-bit VA 7,000 with SEG_MASK = 0x3000, SEG_SHIFT = 12, OFFSET_MASK = 0xFFF. Which is TRUE?

  • VA & SEG_MASK = 4,096; shifting right by 12 gives segment 1; VA & OFFSET_MASK = 2,904. 7,000 = 01 1011 0101 1000. Masking keeps 01 in bits 13–12 (= 4,096); the shift brings it down to 1. Offset = 7,000 − 4,096.
  • VA & SEG_MASK = 1, which is already the segment number; VA & OFFSET_MASK = 2,904. Masking only zeroes the other bits; the selector stays in its high position, so the result is 4,096. The shift turns it into 1.
  • VA & SEG_MASK = 4,096; shifting right by 12 gives segment 1; VA & OFFSET_MASK = 7,000. OFFSET_MASK strips the selector bits: 7,000 & 0xFFF = 2,904.

Stack translation (grows down)

The stack grows backwards, toward lower addresses. So the hardware needs one more bit per segment: grows positive? (1 = up, 0 = down). For the stack, base is the top (the high end) of its physical region, and it extends downward by size.Bilal slides, Ch 16

The recipe (OSTEP and Quiz 6 convention)

  1. Offset = VA − start of the stack's virtual range (or: the low n bits).
  2. Negative offset = offset − max segment size (2n, here 4096). This is how far below the top of the 4 KB slot the address is.
  3. Check: |negative offset| ≤ size. Otherwise, segmentation fault.
  4. PA = base + negative offset.

VA 14000: top bits 11, so Stack. Offset = 14000 − 12288 = 1712. Negative offset = 1712 − 4096 = −2384. |−2384| ≤ 3072 ✓. PA = 53,248 + (−2,384) = 50,864.

VA 12500: offset = 212. Negative offset = 212 − 4096 = −3884. |−3884| > 3072, so segmentation fault. It's too far below the top of the stack.

Bilal's way gives the same answer Bilal's slide: VA 15 KB, stack base 28 KB, size 2 KB. He computes 16 KB − 15 KB = 1 KB (the distance from the top of the virtual space), then PA = 28 KB − 1 KB = 27 KB. OSTEP's way: offset = 3 KB, negative offset = 3 KB − 4 KB = −1 KB, PA = 28 KB + (−1 KB) = 27 KB. Both are "base minus distance from the top". In a quiz, write it the Quiz 6 way: offset → offset − max segment size → |neg| ≤ size check → base + neg. Showing the bounds check earns marks.
Traps (1) Subtract the max segment size (2n = 4096), not the stack's actual size (3 KB). (2) The bounds check uses the absolute value against the actual size. (3) In your Lab 6 mmu_segmented.c the stack offset was already measured downward from base (PA = base − offset). Exam questions give a raw VA, so convert first.

A stack segment has base B and size S, and grows down (negative direction). Which statement is TRUE?

  • B is the top (high end) of the stack's physical region; its valid bytes run from B − S up to B − 1. PA = B + negative offset, with −S ≤ negative offset ≤ −1. The highest virtual address (offset = max segment size − 1, negative offset −1) lands at B − 1.
  • B is the bottom (low end) of the stack's physical region; its valid bytes run from B up to B + S − 1. That's a segment that grows up (code, heap). For the stack, base is the top.
  • B is the top (high end) of the stack's physical region; its valid bytes run from B up to B + S − 1. If B is the top, the bytes lie below it: B − S … B − 1.
  • B is the top (high end) of the stack's physical region; its valid bytes run from B − 4 KB (the max segment size) up to B − 1. Only the stack's actual size S is backed by memory: B − S … B − 1. The 4 KB slot is just the virtual range.

Why does mmu_segmented.c never use SEG_MASK or SEG_SHIFT?

  • Its caller passes the segment number and the offset as two separate arguments, so there are no selector bits to extract. An exam question gives one raw VA instead; then you mask and shift to split it.
  • Its caller passes one raw virtual address, and line 93 extracts the segment with SEG_MASK. Line 93 just copies p->segments[segment]; the segment arrives ready-made as an argument.
  • It uses the implicit approach, so the segment is chosen by how the address was formed. Nothing is inferred: the segment is passed explicitly as the second argument.
  • Its caller passes the segment number and offset separately, so the stack needs the max segment size instead. The lab's stack uses base − offset; max segment size appears only in the exam's raw-VA method.

The implicit approach (briefly)

Instead of using address bits, the hardware works out the segment from how the address was formed:OSTEP §16.2

  • It came from the program counter (an instruction fetch): code segment.
  • It was based on the stack or base pointer: stack segment.
  • Anything else: heap.

No selector bits means no wasted selector slot, and every segment can use the full address width. The cost is extra hardware logic.

In the implicit approach there are no selector bits. How does the hardware decide the segment?

From how the address was formed: from the program counter (instruction fetch) → code; based on the stack or base pointer → stack; anything else → heap.

In the implicit approach, how does the hardware decide which segment an address is in?

  • From how the address was formed: from the program counter → code; based on the stack or base pointer → stack; otherwise → heap. OSTEP §16.2: no selector bits, so the hardware looks at where the address came from.
  • From the top bits of the virtual address: 00 → code, 01 → heap, 11 → stack. Using the top bits is the explicit approach. Implicit uses how the address was formed.
  • From how the address was formed: from the program counter → code; based on the stack or base pointer → heap; otherwise → stack. Addresses based on the stack or base pointer belong to the stack; everything else is the heap.

Add a few protection bits per segment (read / write / execute). Mark code read-execute, and the OS can safely share one physical copy of the code between processes running the same program. Each process still thinks the code is its own private memory.Bilal slides, Ch 16

The hardware now checks permissions as well as bounds. Writing to a read-only segment, or executing from a non-executable one, raises an exception.

What makes it safe for the OS to share one physical copy of a program's code between processes, and what happens if a process writes to it?

Per-segment protection bits: the code segment is marked read-execute (no write), so no process can change the shared copy. A write to it makes the hardware raise an exception. Each process still thinks the code is its own private memory.

Which statement about code sharing with segmentation is TRUE?

  • Code is marked read-execute, so several processes can safely share one physical copy; a write to it raises an exception. Per-segment protection bits make sharing safe, and each process still thinks the code is its own private memory.
  • Code is marked read-write, so several processes can share one physical copy and see each other's changes. Shared code is marked read-execute (no write), so no process can change the shared copy.
  • Code is marked read-execute, so several processes can safely share one physical copy; a write to it is silently ignored. The hardware checks the protection bits and raises an exception on a write.
  • Code is marked read-execute, so several processes can safely share one physical copy, though each can tell it is shared. Sharing stays transparent: each process still thinks the code is its own private memory.

Coarse-grained vs fine-grained segmentation: what's the difference, and where is the segment information kept?

Coarse: a few large segments (code, heap, stack), kept in segment registers in the MMU. Fine: many small segments (early systems had thousands), which need a segment table in memory.

Which statement about coarse-grained vs fine-grained segmentation is TRUE?

  • Coarse-grained has a few large segments kept in MMU registers; fine-grained has many small segments, kept in a segment table in memory. Code/heap/stack fit in a few base-bounds register pairs. Thousands of segments need a segment table in memory (with hardware support).
  • Coarse-grained has many small segments kept in MMU registers; fine-grained has a few large segments, kept in a segment table in memory. Sizes swapped. Coarse = a few large chunks (code, heap, stack); fine = many small ones.
  • Coarse-grained has a few large segments kept in a segment table in memory; fine-grained has many small segments, kept in MMU registers. Locations swapped. A few segments fit in MMU registers; thousands of segments don't, so fine-grained needs a table in memory.
  • Coarse-grained has a few large segments kept in MMU registers; fine-grained has many small segments, needing no extra hardware support. Supporting many segments needs further hardware support: a segment table in memory that the hardware uses.

  • That is coarse-grained segmentation: the compiler chops code and data into many small segments, tracked in a segment table in memory. Many small segments is fine-grained. Coarse-grained means a few large ones (code, heap, stack).
  • That is fine-grained segmentation: the compiler chops code and data into many small segments, tracked in one register pair each. There aren't thousands of register pairs in the MMU; the segment info lives in a segment table in memory.
  • That is fine-grained segmentation: the OS chops each program into many small segments as it loads it, tracked in a segment table in memory. Wrong actor. OSTEP: the B5000 expected the compiler to chop code and data into segments, which the OS and hardware then support.

What the OS must do now

  1. Context switch: save and restore all the segment registers (base, size, direction, protection) in each process's PCB. Otherwise the next process would run with the wrong mappings.
  2. Growing a segment: when malloc() needs more heap, the library calls sbrk(). The OS grows the heap segment if there's room, and otherwise the request fails and malloc() returns NULL.
  3. Managing free physical memory: segments now have different sizes, so free memory breaks into holes.

External fragmentation

External fragmentation is little holes of free space between allocated segments, which make it hard to place new segments.Bilal slides, Ch 16

Internal fragmentation (Lesson 12)External fragmentation (here)
Where the waste isInside an allocated blockBetween allocated blocks
Caused byFixed-size allocations bigger than needed (base and bounds)Variable-sized allocations (segmentation)

Two fixes, both imperfect

  1. Compaction: stop the processes, copy their segments together into one contiguous region, and update their segment base registers. It leaves one big free block, but it's costly (lots of copying and CPU time), and it can ironically make growing existing segments harder.
  2. Free-list management algorithms: best-fit, worst-fit, first-fit, buddy algorithm. They try to keep large free extents available. But no matter how smart the algorithm, external fragmentation still exists; they only minimise it. (Details are in the next chapter, Free-Space Management.)

Free memory has holes of 6 KB, 10 KB and 4 KB between segments. A new 12 KB segment is requested. Can it be placed? Name the problem, and the two ways the OS fights it.

No: 20 KB is free in total, but no single hole is 12 KB. That's external fragmentation: free space split into holes between variable-sized segments. Fixes: (1) compaction: stop processes, copy segments together, update their bases (expensive); (2) free-list algorithms (best-fit, worst-fit, first-fit, buddy), which reduce it but never remove it.

Internal vs external fragmentation: where is the waste, and which scheme causes each?

Internal: waste inside an allocated block; caused by fixed-size allocations bigger than needed (base and bounds). External: waste between allocated blocks; caused by variable-sized allocations (segmentation).

With segmentation, what must the OS save and restore on a context switch, and what happens when malloc needs a bigger heap?

Context switch: all the segment registers (base, size, grows-positive bit, protection) into/from each process's PCB.
Heap growth: malloc calls sbrk(); the OS grows the heap segment if there's room, otherwise it fails and malloc returns NULL.

  • No hole can hold it as memory stands: 18 KB is free in total, but no single hole is 10 KB. This is internal fragmentation. Waste between allocated blocks is external. Internal is waste inside a block (base and bounds).
  • It can be placed as memory stands: 18 KB is free in total, and the segment is split across the holes. A segment is one contiguous range with a single base, so it can't be split.

Practice

Answer from memory first, then check. Struggling a little is what makes it stick.

1. A system has 32-bit virtual addresses. The top 3 bits select the segment. How many segments can be identified?

23 = 8 segments.

2. Same system (32-bit, 3 selector bits). What is the maximum size of one segment, in MB?

Offset bits = 32 − 3 = 29. Max size = 229 = 29 × 220 = 512 MB.

3. In a 14-bit system, write virtual address 9500 as 14 bits (only 0s and 1s).

9500 = 8192 + 1024 + 256 + 16 + 8 + 4 = 213 + 210 + 28 + 24 + 23 + 22 → 10 0101 0001 1100. The selector is 10 (segment 2) and the offset is 1308 (9500 − 8192). In the OSTEP layout, selector 10 is unused, so this access would fault.

4. After computing VA & SEG_MASK, why does the hardware still shift right by SEG_SHIFT?

The mask already cleared the offset bits, but the segment bits are still at positions 13–12, so the value is a large number such as 4096 or 12288. Shifting right by 12 moves them to bits 1–0, giving 0–3, which can index the segment table.

5. Translate virtual address 5,000 (decimal) to a physical address.

5,000 is in 4–8 KB, so Heap. Offset = 5,000 − 4,096 = 904. Check 904 < 2,048 ✓. PA = 30 × 1024 + 904 = 30,720 + 904 = 31,624.

6. Translate virtual address 15,000 (decimal) to a physical address.

15,000 is in 12–16 KB, so Stack. Offset = 15,000 − 12,288 = 2,712. Negative offset = 2,712 − 4,096 = −1,384. Check |−1,384| ≤ 2,048 ✓. PA = 61,440 + (−1,384) = 60,056.

7. What happens when the process accesses virtual address 13,000?

Stack: offset = 13,000 − 12,288 = 712. Negative offset = 712 − 4,096 = −3,384. |−3,384| > 2,048 (the stack's size), so it's out of bounds: segmentation fault. (58,056 = 61,440 − 3,384 is what you'd get by skipping the check. 62,152 adds the positive offset to base, which is the wrong direction.)
8. What is external fragmentation, why does segmentation cause it, and what are the two ways the OS fights it?
External fragmentation means free memory is split into small, non-contiguous holes between segments, so a large request can fail even though enough total memory is free. Segmentation causes it because segments have variable sizes. Fixes: (1) compaction: stop processes, copy segments together, update base registers (expensive); (2) free-list algorithms such as best-fit, worst-fit, first-fit and buddy, which reduce but never eliminate it.
