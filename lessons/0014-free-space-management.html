Lesson 14 · Memory virtualization

Free-space management: how malloc finds you a chunk

Lesson 13 ended with external fragmentation. This chapter is about the allocator that has to live with it, whether that's malloc() managing your heap or the OS placing segments.

The one-sentence version An allocator keeps a free list of the free chunks. It splits a chunk to hand out part of it, coalesces neighbouring free chunks when memory comes back, keeps a small header before each chunk so free(ptr) knows its size, and picks a chunk with a policy: best fit, worst fit, first fit or next fit. Other approaches are segregated lists (slab) and the buddy allocator.OSTEP Ch 17

Lesson 13: What is external fragmentation, and why does segmentation cause it?

Free memory gets chopped into small holes between allocated pieces, so a big request can fail even when enough total memory is free. Segmentation causes it because segments have variable sizes.

The problem: free, but not in one piece

The problem: how should free space be managed when requests come in different sizes? OSTEP §17 crux

If every chunk were the same size, this would be easy: keep a list and hand out the first one. That's what paging does (Lesson 15). It gets hard when the sizes vary, which is exactly what happens with malloc()/free() and with segmentation.

The book's picture is a 30-byte heap:

There are two kinds of waste. Learn the difference:

Where the waste isExample
External fragmentationBetween chunks: free holes too small to useThe 15-byte request above
Internal fragmentationInside a handed-out chunk: you got more than you asked forAsk for 7 KB, get an 8 KB block (buddy, below)

The book makes three assumptions. (1) The interface is malloc(size) and free(ptr), and free is not told the size. (2) Once memory is handed out it can't be moved, so no compaction in a C library. The OS can compact segments. (3) The heap is one fixed-size region. In real life it can grow with sbrk. OSTEP §17.1

In short: variable sizes make free space fragment. External = holes between chunks; internal = waste inside a chunk.

A heap has free holes of 12 and 8 bytes, with used memory between them. Will malloc(16) succeed? Name the problem.

No. 20 bytes are free, but no single hole holds 16. That's external fragmentation.

Which statement is TRUE?

  • Internal fragmentation is unused space inside a chunk the allocator handed out. Right: "the waste occurs inside the allocated unit" (§17.1).
  • External fragmentation is unused space inside a chunk the allocator handed out. That's internal. External fragmentation is the holes between chunks.
  • Internal fragmentation is unused space between the chunks the allocator handed out. Swapped. Holes between chunks = external.
  • A C malloc library fixes fragmentation by compacting the chunks it handed out. It can't move handed-out memory: the program holds pointers to it. Only the OS can compact (segments).

Splitting and coalescing

The problem: a request is usually smaller than any free chunk, and freed chunks come back in pieces.

Same 30-byte heap. Its free list has two nodes, one per free hole:

head → [addr 0, len 10] → [addr 20, len 10] → NULL

Splitting. Someone calls malloc(1). The allocator takes a chunk that fits, gives the front part to the caller and keeps the rest on the list. If it uses the second chunk, malloc returns 20 and the list becomes:

head → [addr 0, len 10] → [addr 21, len 9] → NULL

Coalescing. Go back to the original heap and free the used middle chunk (bytes 10–19). If the allocator just adds it to the list, you get:

head → [10, len 10] → [0, len 10] → [20, len 10] → NULL

The whole heap is free, yet malloc(20) fails, because the list sees three 10-byte pieces. Coalescing fixes this: when a chunk is freed, check the addresses next to it, and merge it with any free neighbour:

head → [addr 0, len 30] → NULL

In short: split when a chunk is bigger than the request; coalesce neighbouring free chunks on free, or large requests fail for no good reason.

Free list: [addr 0, len 10] → [addr 20, len 10]. The allocator serves malloc(4) from the first chunk. What does malloc return, and what's the new list? (No headers.)

Returns 0. List: [addr 4, len 6] → [addr 20, len 10].

A heap is 0–40. Free: 0–10 and 20–30. Used: 10–20 and 30–40. The program frees 10–20. With coalescing, which free list is TRUE?

  • One node: addr 0, len 30. 10–20 sits between two free chunks, so all three merge into 0–30. 30–40 is still used.
  • One node: addr 0, len 40. 30–40 is still used, so the merge stops at 30.
  • Two nodes: addr 0, len 20 and addr 20, len 10. 20–30 is free and right next to 10–20, so it merges too. Coalescing merges with both neighbours.
  • Three nodes: addr 0, addr 10, addr 20, each len 10. That's the list without coalescing.

The header: how free(ptr) knows the size

The problem: free(ptr) gets no size. How does the library know how big the chunk is?

It hides a small header right before the memory it hands you. The book's header holds the size and a magic number (for a sanity check): OSTEP §17.2, Fig 17.2

typedef struct { int size; int magic; } header_t;   // 8 bytes

void free(void *ptr) {
    header_t *hptr = (header_t *) ptr - 1;   // step back one header
    assert(hptr->magic == 1234567);
    ...
}
The detail they testWhen you ask for N bytes, the library looks for a free chunk of N + header size, not N.

The free list lives inside the free space itself. The library can't call malloc to make list nodes, so each free chunk starts with a node: struct { int size; node_t *next; }, also 8 bytes in the book. OSTEP §17.2

Trace the book's example: a 4 KB (4,096-byte) heap at virtual address 16 KB (16,384), with 8-byte headers.

StepWhat happensFree chunk size
StartOne free node: 4,096 − 8 (its node header)4,088
malloc(100)Uses 100 + 8 = 108 bytes; returns 16,384 + 8 = 16,3924,088 − 108 = 3,980
2 more malloc(100)Each uses 108; 324 bytes used in total3,980 − 216 = 3,764
free(16500)The middle chunk: 16,384 + 108 + 8 = 16,500. It goes on the head of the list.100 and 3,764

In short: header = size + magic, sitting just before ptr; free finds it at ptr − 1. A request for N needs N + header bytes.

8-byte headers. A fresh 4,096-byte heap starts at address 8,192 (free chunk = 4,088). The program calls malloc(200) and then malloc(50). What does each call return, and how big is the free chunk afterwards?

1st: uses 208, returns 8,192 + 8 = 8,200.
2nd: starts at 8,192 + 208 = 8,400, returns 8,400 + 8 = 8,408, uses 58.
Free = 4,088 − 208 − 58 = 3,822.

Headers are 8 bytes. A program calls malloc(64). Which is TRUE?

  • The library searches for a 72-byte chunk and stores the size just before ptr. N + header = 64 + 8 = 72, and the header sits right before the returned pointer.
  • The library searches for a 64-byte chunk and stores the size just before ptr. It needs room for the header too: 72.
  • The library searches for a 72-byte chunk and stores the size just after ptr. The header is before ptr; free uses (header_t*)ptr − 1.
  • The library searches for a 64-byte chunk and free() gets the size from its argument. free(void *ptr) takes no size; that's why the header exists.

Picking a chunk: best, worst, first, next fit

The problem: several free chunks fit the request. Which one should the allocator use?

PolicyPicksGoodBad
Best fitThe smallest chunk that fitsLittle wasteSearches the whole list; leaves tiny leftover slivers
Worst fitThe largest chunkLeftovers stay bigSearches the whole list; studies show it does badly (more fragmentation)
First fitThe first chunk that fitsFast: stops earlyClutters the front of the list with small pieces
Next fitFirst fit, but starts where the last search stoppedFast; spreads searches over the listPerformance similar to first fit

First fit works better if the list is kept in address order, which also makes coalescing easier. OSTEP §17.3

The book's example: free list 10 → 30 → 20, request 15 (ignore headers).

In short: best = smallest that fits; worst = biggest; first = first that fits; next = first fit starting where you left off. Best/worst scan everything; first/next are fast.

Free list: 25 → 8 → 40 → 12. Request 10. Give the list after best fit, worst fit and first fit.

Best (12): 25, 8, 40, 2.
Worst (40): 25, 8, 30, 12.
First (25): 15, 8, 40, 12.

Free list: 18 → 6 → 11 → 30. Request 9. Which is TRUE?

  • Best fit picks 11, leaving 18 → 6 → 2 → 30. The chunks that fit are 18, 11 and 30. The smallest is 11; 11 − 9 = 2.
  • Best fit picks 6, leaving 18 → 0 → 11 → 30. 6 < 9 doesn't fit. Best fit chooses the smallest chunk that fits.
  • Best fit picks 18, leaving 9 → 6 → 11 → 30. 18 is what first fit picks. Best fit scans the whole list and picks 11.
  • Best fit picks 30, leaving 18 → 6 → 11 → 21. That's worst fit (largest chunk).

Which statement about the policies is TRUE?

  • First fit is fast because it stops searching at the first chunk that fits. Right: no exhaustive search (§17.3).
  • Best fit is fast because it stops searching at the first chunk that fits. Best fit must scan the whole list to be sure it has the smallest.
  • Worst fit is the best policy because it leaves large leftover chunks. That's the idea, but the book says studies show it performs badly: more fragmentation and high overhead.
  • Next fit always starts its search at the head of the free list. Next fit starts where the last search stopped; that's the whole point.

Other approaches: segregated lists, slab, buddy

The problem: searching lists is slow, and coalescing is fiddly. Can we design around that?

Segregated lists. If an app often asks for one particular size, keep a separate list just for that size. Other requests go to a general allocator. Those requests are fast (no search) and fragmentation is less of a concern. The hard question: how much memory to give each pool? OSTEP §17.4

Slab allocator (Jeff Bonwick, Solaris kernel). At boot it makes object caches for common kernel objects (locks, inodes…): one segregated list per size. A cache that runs low asks the general allocator for more slabs. It also keeps free objects pre-initialized, which saves the cost of building and tearing them down each time.

Binary buddy allocator. Think of free memory as one block of size 2N. For a request, keep halving until one more split would be too small. Then hand out that block.

  • Cost: blocks are only powers of two, so you get internal fragmentation (7 KB → 8 KB block).
  • Benefit: coalescing is easy. When the 8 KB block is freed, check its buddy. If the buddy is free, merge into 16 KB, check that block's buddy, and keep going up the tree until a buddy is in use.
  • Why it's easy to find the buddy: the addresses of a buddy pair differ by a single bit, and which bit depends on the level in the tree.

Other ideas: plain lists don't scale, so advanced allocators use balanced binary trees, splay trees or partially-ordered trees. There are also allocators built for multiprocessors (Hoard, jemalloc).

In short: segregated lists/slab = a fast pool per popular size. Buddy = halve until it just fits; easy coalescing (buddies differ by one address bit), but internal fragmentation.

Buddy allocator over 32 KB. Request 3 KB. Which block size is handed out, how much is wasted, and what splits happen?

32 → 16 → 8 → 4 KB (2 KB would be too small). Waste = 4 − 3 = 1 KB internal fragmentation.

Which statement about the buddy allocator is TRUE?

  • It suffers internal fragmentation because it only hands out power-of-two blocks. Right (§17.4): a 7 KB request gets an 8 KB block.
  • It suffers external fragmentation because it only hands out power-of-two blocks. The waste is inside the handed-out block, so it's internal fragmentation.
  • It suffers internal fragmentation because finding a block's buddy needs a full list search. Finding the buddy is cheap: the two addresses differ by one bit.
  • It avoids all fragmentation because buddies are always coalesced when freed. Coalescing helps, but rounding up to powers of two still wastes space inside blocks.

Final practice

1. Free list 10 → 30 → 20 (the book's), request 15, best fit. What size is the leftover chunk?

Best fit picks 20 (smallest that fits). 20 − 15 = 5. The list becomes 10, 30, 5.

2. A 4,096-byte heap, 8-byte headers, one free node to start (4,088). After malloc(100) and malloc(100), then free of the first one, how big is the big free chunk at the end of the heap?

Each malloc uses 108, so the end chunk is 4,088 − 216 = 3,872. Freeing the first chunk adds a separate 100-byte node; it's not next to the end chunk, so they can't coalesce.

3. Why does a C malloc library build its free list inside the free chunks?

You can't call malloc() from inside malloc() to get list nodes, so each free chunk starts with its own {size, next} node (§17.2).

4. The heap runs out of space. What do most traditional allocators do?

They call something like sbrk. The OS finds free physical pages, maps them in, and the heap grows. (Simply returning NULL is also allowed.)
5. Explain splitting and coalescing in one sentence each, and say why coalescing matters.
Splitting: when a free chunk is bigger than the request, hand out the front part and leave the rest on the free list. Coalescing: when freeing, merge the chunk with free chunks right next to it. Without coalescing, a fully free heap can look like many small pieces and large requests fail.
