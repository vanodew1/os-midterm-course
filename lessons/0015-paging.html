Lesson 15 · Memory virtualization

Paging: chop memory into same-size pieces

Segmentation used variable-sized pieces, and Lesson 14 showed how that fragments memory. Paging takes the other approach: every piece is the same size.

The one-sentence version Split the address space into fixed-size pages and physical memory into same-size page frames. A per-process page table maps each virtual page number (VPN) to a physical frame number (PFN). To translate, swap the VPN for the PFN and keep the offset. The catches: page tables are big, and every access needs an extra memory read.OSTEP Ch 18

Lesson 14: Free list 10 → 30 → 20, request 15. What do best fit and worst fit leave?

Best fit (20): 10, 30, 5. Worst fit (30): 10, 15, 20.

Lesson 13: in a 14-bit address with a 2-bit segment selector, what are the remaining 12 bits called?

The offset within the segment. Paging splits the address the same way: VPN on top, offset below.

The idea: pages and frames

The problem: how can we virtualize memory with fixed-size pieces, to avoid segmentation's problems? OSTEP §18 crux

Instead of code/heap/stack segments of any size, split the address space into fixed-size pages. Treat physical memory as an array of same-size slots called page frames. Any page can go in any frame.

The book's tiny example: a 64-byte address space with 16-byte pages (4 pages), placed in a 128-byte physical memory (8 frames):

Two big wins: OSTEP §18.1, §18.6

  • Flexibility. No assumptions about which way the heap and stack grow. Unused pages simply aren't mapped, so a sparse address space is fine.
  • Simple free-space management. To place 4 pages, the OS grabs any 4 free frames off a free list. All the pieces are the same size, so there's no external fragmentation.

Where each page lives is recorded in the page table, and there is one page table per process. A different process has its own table, with its own mappings.

In short: pages (virtual) and frames (physical) are the same fixed size. The per-process page table says which frame holds each page. Fixed size means no external fragmentation.

Which statement is TRUE?

  • Each process has its own page table, mapping its virtual pages to physical frames. Right: "this page table is a per-process data structure" (§18.1).
  • All processes share one page table, mapping virtual pages to physical frames. Each process maps the same VPNs to different frames, so each needs its own table.
  • Each process has its own page table, mapping physical frames to virtual pages. Backwards: it's indexed by VPN and gives a PFN.
  • Paging causes external fragmentation because pages can go in any free frame. Fixed-size units mean no external fragmentation (§18.6).

Translating an address: VPN + offset

The problem: the program uses virtual address 21. Which physical byte is that?

Split the virtual address into two parts:

  • Offset = which byte inside the page. Page size 2n → n offset bits. 16-byte pages → 4 bits.
  • VPN = which page. It's all the bits above the offset. 64-byte space = 6 bits total → 6 − 4 = 2 VPN bits (4 pages).

The hardware does this with masks and shifts, just like SEG_MASK in Lesson 13: OSTEP §18.4

VPN      = (VirtualAddress & VPN_MASK) >> SHIFT    // SHIFT = # offset bits
offset   = VirtualAddress & OFFSET_MASK
PhysAddr = (PFN << SHIFT) | offset

In the book's example, VPN_MASK = 0x30 (110000), SHIFT = 4 and OFFSET_MASK = 0x0F. In plain decimal it's the same as PA = PFN × page size + offset: 7 × 16 + 5 = 117.

Exam trapThe offset is never translated. Only the page number changes. If your PA's low bits differ from the VA's low bits, something went wrong.

Try VA 0, 21, 47 and 63 in the book's page table above. Then try the practice table at the end.

In short: offset bits = log2(page size); VPN = the rest. Look up VPN → PFN, then PA = PFN × page size + offset.

Book's table (VP0→3, VP1→7, VP2→5, VP3→2), 16-byte pages. Translate VA 40.

40 = 10 1000 → VPN 2, offset 8. VP2 → PFN 5. PA = 5 × 16 + 8 = 88 (101 1000).

32-bit virtual addresses, 4 KB pages. How many offset bits and VPN bits?

4 KB = 212 → 12 offset bits; VPN = 32 − 12 = 20 bits (about a million pages).

64-byte address space, 16-byte pages, page table VP0→3, VP1→7, VP2→5, VP3→2. Which translation of VA 50 is TRUE?

  • VPN 3, offset 2, so PA = 2 × 16 + 2 = 34. 50 = 11 0010: VPN 3 → PFN 2; keep offset 2.
  • VPN 3, offset 2, so PA = 3 × 16 + 2 = 50. You used the VPN instead of the PFN, which just gives back the VA. VP3 → PFN 2.
  • VPN 2, offset 2, so PA = 5 × 16 + 2 = 82. 50 ÷ 16 = 3 remainder 2, so the VPN is 3, not 2.
  • VPN 3, offset 2, so PA = 2 × 16 + 50 = 82. Add the offset (2), not the whole VA.

A 6-bit virtual address with 16-byte pages. Which set of constants is TRUE?

  • VPN_MASK = 0x30, SHIFT = 4, OFFSET_MASK = 0x0F. 4 offset bits (16 = 24); the VPN is the top 2 bits: 110000 = 0x30.
  • VPN_MASK = 0x0F, SHIFT = 4, OFFSET_MASK = 0x30. Swapped: the VPN is the high bits (0x30), the offset the low bits (0x0F).
  • VPN_MASK = 0x30, SHIFT = 2, OFFSET_MASK = 0x0F. SHIFT = number of offset bits = 4, not the number of VPN bits.
  • VPN_MASK = 0x3C, SHIFT = 4, OFFSET_MASK = 0x03. That splits off only 2 offset bits, which would mean 4-byte pages.

Where page tables live, and why they're big

The problem: a page table needs one entry per virtual page. How many is that?

The book's numbers: a 32-bit address space, 4 KB pages → 20-bit VPN → 220 ≈ 1 million entries. At 4 bytes per page-table entry (PTE):

220 × 4 B = 4 MB per process → 100 processes = 400 MB just for translations. OSTEP §18.2

That's far too big to keep on-chip in the MMU, so page tables are stored in memory. For now, assume they sit in the OS's physical memory.

RecipeEntries = 2VPN bits = address-space size ÷ page size. Table size = entries × PTE size.

In short: linear page table size = (# virtual pages) × (PTE size). That's 4 MB per process for 32-bit addresses with 4 KB pages, so tables live in memory, not in the MMU.

32-bit address space, 8 KB pages, 4-byte PTEs. How big is one linear page table?

8 KB = 213 → 13 offset bits → 19 VPN bits → 219 = 524,288 entries × 4 B = 2 MB.

32-bit address space, 4 KB pages, 4-byte PTEs. Which is TRUE?

  • Each process's linear page table is 4 MB and is stored in memory. 220 × 4 B = 4 MB; that's too big for the MMU, so it lives in memory (§18.2).
  • Each process's linear page table is 4 KB and is stored in memory. 4 KB is the page size. The table has 220 entries × 4 B = 4 MB.
  • Each process's linear page table is 4 MB and is stored in the MMU. Too big for special on-chip hardware; it's kept in memory.
  • All processes together share one 4 MB linear page table in memory. It's per process: 100 processes = 400 MB.

What's in a page-table entry (PTE)

The problem: besides the PFN, what does the OS need to know about each page?

The simplest page table is a linear page table: an array indexed by VPN. Each PTE holds the PFN plus some bits: OSTEP §18.3

BitMeaningIf it's a problem…
ValidIs this translation in use at all? The unused gap between heap and stack is marked invalid.Access → trap to the OS, which likely kills the process. Lets a sparse address space need no frames for the gap.
ProtectionCan the page be read, written or executed?Disallowed access → trap to the OS
PresentIn physical memory, or swapped out to disk?(Swapping comes in later chapters)
DirtyHas the page been modified since it was brought into memory?
Reference (accessed)Has the page been accessed? Shows which pages are popular.Used later for page replacement

x86 PTE (Fig 18.5): P (present), R/W (are writes allowed?), U/S (can user mode access it?), PWT/PCD/PAT/G (caching), A (accessed), D (dirty), and the PFN in bits 31–12. Note that x86 has no separate valid bit: P = 1 means present and valid. If P = 0, the OS traps and checks its own records to decide whether the page is swapped out or simply illegal.

In short: PTE = PFN + valid, protection, present, dirty and reference bits. Valid is what makes sparse address spaces cheap.

Which statement is TRUE?

  • The dirty bit says whether the page was modified since it was brought into memory. Right (§18.3).
  • The present bit says whether the page was modified since it was brought into memory. That's the dirty bit. Present = in memory vs on disk.
  • The reference bit says whether the page was modified since it was brought into memory. Reference = accessed at all (read or write), not modified.
  • The valid bit says whether the page was modified since it was brought into memory. Valid = is this translation in use. Invalid pages (like the heap–stack gap) trap.

Why does the valid bit save memory?

Unused pages (like the big gap between heap and stack) are marked invalid, so they need no physical frames. Touching one traps to the OS.

Paging is also too slow

The problem: the page table is in memory. So every memory access needs a memory access first.

The hardware keeps a page-table base register (PTBR) holding the physical address of the current process's table. For every access: OSTEP Fig 18.6

VPN     = (VirtualAddress & VPN_MASK) >> SHIFT
PTEAddr = PTBR + (VPN * sizeof(PTE))      // where the PTE is
PTE     = AccessMemory(PTEAddr)           // ← the EXTRA memory read
if (PTE.Valid == False)            RaiseException(SEGMENTATION_FAULT)
else if (!CanAccess(PTE.ProtectBits)) RaiseException(PROTECTION_FAULT)
else  PhysAddr = (PTE.PFN << PFN_SHIFT) | offset
      Register = AccessMemory(PhysAddr)

So every load, store and instruction fetch costs two memory reads: one for the PTE, then the real one. The book says this likely slows the process down by a factor of two or more.

The book's memory trace (array.c)

for (i = 0; i < 1000; i++) array[i] = 0; compiles to a 4-instruction loop: mov (stores to the array), inc, cmp, jne. With a 64 KB address space and 1 KB pages: OSTEP §18.5

  • Code at VA 1024 → VPN 1 → PFN 4. The array is at VA 40000–44000 → VPNs 39–42 → PFNs 7–10. The page table is at physical 1 KB.
  • Each loop iteration makes 4 instruction fetches + 1 array store = 5 real accesses, and each needs a page-table lookup first: +5.

In short: PTE address = PTBR + VPN × PTE size. Each access needs one extra memory read for the PTE, so paging as described is too slow and its tables are too big. Ch 19 (TLBs) fixes the speed.

PTBR = 2048, PTEs are 4 bytes. Where is the PTE for VPN 5?

2048 + 5 × 4 = 2068.

In the array trace, VA 40000 with 1 KB pages: which VPN and offset? With VPN 39 → PFN 7, what is the PA?

40000 ÷ 1024 = 39 remainder 64 → VPN 39, offset 64. PA = 7 × 1024 + 64 = 7232 (matches Fig 18.7).

A loop has 5 instructions; 2 of them load from memory. With a linear page table and no other help, which is TRUE per iteration?

  • There are 14 memory accesses: 7 real ones and 7 page-table lookups. 5 fetches + 2 loads = 7 real accesses, and each needs one PTE read first: 7 + 7 = 14.
  • There are 12 memory accesses: 7 real ones and 5 page-table lookups. The data loads need translating too, not just the fetches: 7 lookups.
  • There are 7 memory accesses: the page-table lookups are done in the MMU. The table is in memory, so every lookup is a memory access.
  • There are 10 memory accesses: 5 real ones and 5 page-table lookups. That ignores the 2 explicit loads. 10 is the book's loop, which had 4 instructions and 1 store.

Final practice

For 1–3: a 7-bit virtual address and 32-byte pages. Page table: VP0 → 5, VP1 → 2, VP2 → invalid, VP3 → 6. Use the translator to check yourself after you answer.

1. Translate VA 100.

100 = 11 00100 → VPN 3, offset 4. VP3 → PFN 6. PA = 6 × 32 + 4 = 196.

2. Translate VA 45.

45 = 01 01101 → VPN 1, offset 13. VP1 → PFN 2. PA = 2 × 32 + 13 = 77.

3. What happens on an access to VA 70?

70 = 10 00110 → VPN 2, which is invalid → trap to the OS (segmentation fault). 166 = 5 × 32 + 6 uses the wrong PFN; 70 is "no translation"; 198 = 6 × 32 + 6 uses VP3's frame.

4. A 16-bit address space with 1 KB pages. How many entries are in the linear page table?

1 KB = 210 → 10 offset bits → 6 VPN bits → 26 = 64 entries (64 KB ÷ 1 KB).
5. Name paging's two advantages and its two problems (from the chapter summary).
Advantages: (1) no external fragmentation, because the units are fixed-size; (2) flexible, supporting sparse address spaces. Problems: (1) slow: an extra memory access per reference to read the page table; (2) memory waste: big page tables (4 MB per process for 32-bit addresses with 4 KB pages).
